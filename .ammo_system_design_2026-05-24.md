## Section 1 — How VT2's ammo / energy / overcharge actually works

### 1.1 Ammo (`GenericAmmoUserExtension`)

File: `scripts/unit_extensions/generic/generic_ammo_user_extension.lua`

**Consumption entry point**: `use_ammo(self, ammo_used, given, check_ammo_immediately)`
(line 425).

The cost math is:

```lua
-- generic_ammo_user_extension.lua:430
local extra_ammo_used =
    math.round(ammo_used * buff_extension:apply_buffs_to_value(1, "ammo_used_multiplier"))
    - ammo_used
-- ...
ammo_used = ammo_used + extra_ammo_used      -- (line 440)
```

- `ammo_used` from the caller is an **integer ≥ 1** (action templates pass `1` or
  `2` per shot).
- `apply_buffs_to_value(1, "ammo_used_multiplier")` returns the multiplier
  applied to `1`. For 20 ct_meta_ammo stacks at -0.05 each it returns `0`.
  `math.round(1 * 0) - 1 = -1`, so `extra_ammo_used = -1`, so
  `ammo_used = 1 + (-1) = 0`.
- `self._shots_fired = self._shots_fired + ammo_used` (line 452). When this is
  `0`, no ammo is deducted in the next `_check_ammo()` pass.

**`math.round` is the only clamp.** There is no `math.max(1, ...)` or `math.max(0, ...)`
floor. `_shots_fired` going to zero per-shot means the magazine never empties,
no reload anim ever triggers, and the mag UI freezes at full. The
`fassert(self:ammo_count() >= 0, "ammo went below 0")` at line 483 is satisfied
because `ammo_count` simply stays at full.

**Network-side**: ammo state is networked via `ammo_count` flow var
(line 666) and proc events; no engine cap on the per-shot consumption value
itself. `_max_ammo` is computed via `math.ceil(... "total_ammo")` at line 96 —
local to extension, **not networked through a typed channel** (unlike
`max_overcharge` / `max_energy`).

**Network constraints**:
- `total_ammo` capacity → uncapped (no `NetworkConstants.max_ammo`).
- `ammo_used_multiplier` cost → no engine cap; **the bug is purely a Lua-design
  problem**, not an engine-bound.

### 1.2 Energy (`PlayerUnitEnergyExtension` — Moonfire Bow)

File: `scripts/unit_extensions/default_player_unit/energy/player_unit_energy_extension.lua`

**Consumption entry point**: `drain(self, amount)` (line 85).

```lua
-- player_unit_energy_extension.lua:95
amount = amount * buff_extension:apply_buffs_to_value(1, "ammo_used_multiplier")
-- ...
local new_energy_amount = energy - amount      -- (line 99)
new_energy_amount = math.clamp(new_energy_amount, 0, energy)
```

- `amount` is a **float**, can be sub-integer.
- Cost multiplier comes from the same `ammo_used_multiplier` stat_buff key as
  ammo above. So ct_meta_ammo at 20 stacks → `amount * 0 = 0` per shot →
  infinite Moonfire Bow draws.
- `math.clamp(... 0, energy)` only clamps the result, not the input. Zero drain
  means `_recharge_delay_timer` is still pushed (line 103), but recharge would
  be irrelevant since no energy was lost.

**No floor on the consumed `amount`. Same divergence bug as ammo.**

`max_energy` IS networked: `fassert(max_energy >= NetworkConstants.max_energy.min and ...max)`
at line 43. That's a separate concern (the v0.7.72 burn). The consumption side
is local, no engine cap.

### 1.3 Overcharge (`PlayerUnitOverchargeExtension` — Sienna staves, drakefire)

File: `scripts/unit_extensions/default_player_unit/charge/player_unit_overcharge_extension.lua`

**Consumption entry point**: `add_charge(self, overcharge_amount, charge_level, overcharge_type)`
(line 330).

```lua
-- player_unit_overcharge_extension.lua:340
overcharge_amount = self._buff_extension:apply_buffs_to_value(overcharge_amount, "reduced_overcharge")

-- player_unit_overcharge_extension.lua:343 (inside the if-not-ignored branch)
if buff_extension and not self._ignored_overcharge_types[overcharge_type] then
    overcharge_amount = overcharge_amount * buff_extension:apply_buffs_to_value(1, "ammo_used_multiplier")
    ...
end
```

**TWO stat_buff hops, both vulnerable to the same divergence**:

1. `reduced_overcharge` is applied as a **direct multiplier** on the value
   (`apply_buffs_to_value(overcharge_amount, "reduced_overcharge")`). At 20
   stacks of -0.05 → `final = overcharge_amount * (1 + (-1.0)) = 0`.
2. `ammo_used_multiplier` then multiplies the result by another factor pulled
   the same way.

So with ct_meta_ammo's current shape (one stack adds -0.05 to BOTH), at 20
stacks `add_charge` deposits zero overcharge per cast → infinite spam on
Sienna, drakefire, Necromancer staves. **The Sienna case is even worse than
ammo** because `_ignored_overcharge_types = { charging, damage_to_overcharge,
drakegun_charging, flamethrower }` (line 82) — those bypass the
`ammo_used_multiplier` path but **NOT** the `reduced_overcharge` path. So the
reduced_overcharge multiplier alone is enough to crater overcharge to zero,
even before ammo_used_multiplier compounds it for non-channelled actions.

No floor on `overcharge_amount` after the multipliers. `max_value` is networked
(`fassert` at line 110), but that's bar-size, not per-cast consumption. **No
engine cap on the input value.**

`stacking_multiplier` resolution (buff_extension.lua:1391-1448) is **purely

```lua
-- buff_extension.lua:1397-1432 (key lines)
local root_multiplier = 1
...
for index, stat_buff_data in pairs(stat_buffs) do
    local multiplier = stat_buff_data.multiplier
    ...
    if index == 0 then  -- index 0 is the root accumulator
        root_multiplier = root_multiplier + multiplier
        ...
    else
        multiplier = multiplier + 1
        final_value = final_value * multiplier + bonus
    end
end

final_value = final_value * root_multiplier + root_bonus
```

And on `add_buff` (line 670, 683-686), all stacking_multiplier entries with
the same stat_buff name collapse to **index 0** unless explicitly tagged as
`stacking_multiplier_multiplicative` (which `ammo_used_multiplier`,
`reduced_overcharge`, and `total_ammo` are NOT — they're plain
`stacking_multiplier`). So 20 stacks of -0.05 sum to **a single index-0 entry
with multiplier = -1.0**, yielding `root_multiplier = 0`.

**This is the root cause.** The engine cannot floor it without engine changes;
it has to be floored by a custom Lua hook on the consumer side.

## Section 3 — Proposed redesign options

### Constraints recap (from user)

- **A. Convergent**: must diminish per-stack, not diverge linearly.
- **B. Hard floor**: cost-per-shot must never round to 0 or below 1
  (for integer ammo) / below an explicit per-system floor (for energy /
  overcharge).
- **C. Universal**: same shape used for ammo + energy + overcharge.

### Candidate 1 — Multiplicative-decay (geometric)

Each stack multiplies cost by `(1 - X)` where `X` is small.
At N stacks: `cost = base * (1 - X)^N`.

Math (X = 0.03):

| N | (1-0.03)^N | cost |
|---:|---:|---:|
| 5  | 0.859 | 85.9% |
| 10 | 0.737 | 73.7% |
| 20 | 0.544 | 54.4% |
| 50 | 0.218 | 21.8% |
| 100 | 0.048 | 4.8% |
| ∞ | 0 | 0 (asymptotic, never reaches) |

**Pros**: Mathematically clean. Asymptotically approaches 0 but never reaches
exactly. Easy to express as "you fire more shots per magazine".

**Cons**: At 100 boons cost is 4.8% which still triggers integer rounding
issues for ammo (`math.round(1 * 0.048) = 0` → infinite ammo). Approaching
zero, even slowly, **still violates Constraint B** for integer ammo. Need a
hard floor anyway to be safe — so the geometric formula is doing work that the
floor would do alone. Reject this candidate.

### Candidate 2 — Hyperbolic with floor (recommended)

Bonus diminishes hyperbolically and never exceeds a hardcoded cap. Cost has an
explicit minimum.

Formula:

```
bonus_fraction = (N * step) / (1 + N * step / cap)  -- approaches `cap` as N→∞
effective_cost = max(base * (1 - bonus_fraction), base * floor)
```

Where `step` = per-stack bonus (0.05 keeps the current "feel"),
`cap` = asymptotic limit (e.g. 0.75 → "at infinite stacks you save up to 75%"),
`floor` = minimum cost (e.g. 0.25 → "cost never drops below 25% of base").

Math (step = 0.05, cap = 0.75, floor = 0.25):

| N | (N*step) | (N*step)/(1+N*step/cap) | cost factor |
|---:|---:|---:|---:|
| 1  | 0.05 | 0.047 | 0.953 (95.3%) |
| 5  | 0.25 | 0.188 | 0.812 (81.2%) |
| 10 | 0.50 | 0.300 | 0.700 (70.0%) |
| 20 | 1.00 | 0.429 | 0.571 (57.1%) |
| 50 | 2.50 | 0.577 | 0.423 (42.3%) |
| 100 | 5.00 | 0.652 | 0.348 (34.8%) |
| ∞  | ∞    | 0.750 | **0.250 (25.0% — clamped by floor)** |

The asymptotic `cap = 0.75` means even before the floor, infinite stacks
saturate at 25% cost. The floor is belt-and-braces — even if `cap` were
miscalibrated, cost never goes below 25%.

For integer ammo, `math.round(1 * 0.25) = 0`. So **for the ammo path
specifically we round up at the last step**: `effective_cost =
math.max(math.ceil(base * effective_cost_factor), 1)`. For energy / overcharge,
keep the float multiplier with a small absolute floor (`floor = 0.25` ≈ 25%
of base cost per cast).

**Pros**:
- Convergent (Constraint A): per-stack bonus is hyperbolic, each new stack
  adds less than the previous.
- Hard floor (Constraint B): explicit `floor` prevents reaching 0.
- Universal (Constraint C): same formula works for ammo (with integer ceil),
  energy (float clamp), overcharge (float clamp).
- Predictable: cap + floor are independently tunable; cap shapes the curve,
  floor enforces the safety bound.

**Cons**: Slightly opaque to players. UI tooltip should say "X% cost
reduction, diminishing returns, max ~75%". Acceptable per ct_meta convention.

### Candidate 3 — Floor-clamped linear

Keep the current linear math, but clamp at a known floor.

```
effective_cost = max(base * (1 - 0.05 * N), base * 0.25)
```

Math:

| N | linear factor | clamped |
|---:|---:|---:|
| 5  | 0.75 | 0.75 |
| 10 | 0.50 | 0.50 |
| 15 | 0.25 | 0.25 (floor hit) |
| 20 | 0.00 | 0.25 (clamped) |
| 50 | -1.50 | 0.25 (clamped) |

**Pros**: Trivially simple. Easy to communicate: "5% off per boon, max 75%
off".

**Cons**: Hits the cap abruptly at N=15. Once you have 15 boons, every
subsequent boon is dead for this stat — feels bad. Acceptable but less
elegant than hyperbolic.

### Recommendation: **Candidate 2 (Hyperbolic with floor)**

Reasoning:

1. Best satisfies all three constraints simultaneously.
2. Per-stack improvement diminishes smoothly — every boon still feels
   meaningful at high stack counts, just less so.
3. Single formula reusable across ammo / energy / overcharge with only the
   integer-vs-float rounding strategy varying. Easy to wrap in a shared helper
   in mod scope.
4. Tunables (`step`, `cap`, `floor`) are independent — fix-agent can tweak the
   feel without touching architecture.

### Recommended parameters

```
step  = 0.05    -- preserve the "+5% per boon" feel from current copy
cap   = 0.75    -- max 75% cost reduction at infinite stacks
floor = 0.25    -- minimum cost is 25% of base
```

These give a curve that reaches 50% cost at 10 stacks (typical mid-run), 57%
at 20 stacks (typical late-run), 35% at 100 stacks (hypothetical edge case),
and never drops below 25%.

## Section 3.5 — Implementation shape

`stacking_multiplier` cannot express this curve — its resolution is hardcoded
linear in `buff_extension.lua:1391-1448`. The redesign MUST:

1. **Stop applying `ammo_used_multiplier` / `reduced_overcharge` as stat_buffs
   on the ct_meta_ammo stack template**. Remove those entries.
2. **Hook the three consumption call sites directly** and read the active
   ct_meta_ammo stack count from the `BuffExtension` (the `_1` sub-buff stack
   counter we already maintain — see `_make_meta_proc` at chaos_wastes_tweaker
   line ~5597).
3. **Apply the hyperbolic+floor math at consumption time**.

### Shared helper

```lua
-- file-scope, near CT_META_BOONS at chaos_wastes_tweaker.lua:~5475
local CT_META_AMMO_STEP  = 0.05
local CT_META_AMMO_CAP   = 0.75
local CT_META_AMMO_FLOOR = 0.25

-- Returns the cost multiplier (0..1) for N active ct_meta_ammo stacks.
-- Hyperbolic-saturating with a hard floor; never zero, never negative.
local function _ct_meta_ammo_cost_multiplier(num_stacks)
    if not num_stacks or num_stacks <= 0 then return 1.0 end
    local raw = (num_stacks * CT_META_AMMO_STEP)
              / (1 + num_stacks * CT_META_AMMO_STEP / CT_META_AMMO_CAP)
    local cost = 1.0 - raw
    if cost < CT_META_AMMO_FLOOR then cost = CT_META_AMMO_FLOOR end
    return cost
end

-- Reads the current ct_meta_ammo stack count for the unit (or 0 if none).
-- The "_1" suffix is the first sub-buff's name; we use stack count from one
-- sub-buff as the canonical count (all sub-buffs increment in lockstep — same
-- assumption as _make_meta_proc).
local function _ct_meta_ammo_stack_count(unit)
    local buff_ext = ScriptUnit.has_extension(unit, "buff_system")
    if not buff_ext then return 0 end
    return buff_ext:num_buff_stacks("ct_meta_ammo_stack_1") or 0
end
```

### Hook 1 — ammo (`GenericAmmoUserExtension.use_ammo`)

`scripts/unit_extensions/generic/generic_ammo_user_extension.lua:425-488`.

```lua
mod:hook("GenericAmmoUserExtension", "use_ammo", function(orig_use_ammo, self, ammo_used, given, check_ammo_immediately)
    local owner = self.owner_unit
    local num_stacks = _ct_meta_ammo_stack_count(owner)
    if num_stacks <= 0 then
        return orig_use_ammo(self, ammo_used, given, check_ammo_immediately)
    end

    -- Compute our discount factor and scale `ammo_used`, then call original
    -- with the discounted amount. Vanilla's own ammo_used_multiplier path
    -- (line 430) still runs internally, but we've removed our contribution
    -- from that stat_buff so it composes correctly with vanilla buffs like
    -- Hand of Drakira (boon_range_01) or no_ammo_consumed.
    local cost_factor = _ct_meta_ammo_cost_multiplier(num_stacks)
    -- Floor + ceil so integer ammo never rounds to 0 from our contribution.
    local discounted = math.max(1, math.ceil(ammo_used * cost_factor))
    return orig_use_ammo(self, discounted, given, check_ammo_immediately)
end)
```

**Floor justification**: `ammo_used * cost_factor` with cost_factor ≥ 0.25 and
`ammo_used ≥ 1` is `≥ 0.25`, ceil → `≥ 1`. With `math.max(1, ...)` the floor
is doubly enforced.

### Hook 2 — energy (`PlayerUnitEnergyExtension.drain`)

`scripts/unit_extensions/default_player_unit/energy/player_unit_energy_extension.lua:85-104`.

```lua
mod:hook("PlayerUnitEnergyExtension", "drain", function(orig_drain, self, amount)
    local num_stacks = _ct_meta_ammo_stack_count(self.unit)
    if num_stacks <= 0 then
        return orig_drain(self, amount)
    end
    local cost_factor = _ct_meta_ammo_cost_multiplier(num_stacks)
    local discounted = amount * cost_factor
    -- Floor in absolute terms so a Moonfire cost of e.g. 1.0 never goes to
    -- zero. cost_factor floor is 0.25; for a typical Moonfire cost of 1-3
    -- this means minimum drain is 0.25-0.75. No `math.max` needed because
    -- the inner orig_drain already clamps `[0, energy]`, but the FLOOR on
    -- cost_factor is what prevents zero-drain runaway.
    return orig_drain(self, discounted)
end)
```

### Hook 3 — overcharge (`PlayerUnitOverchargeExtension.add_charge`)

## Section 5 — Does `total_ammo` need retrofit?

**No** — keep it as-is.

### Why it's safe

`total_ammo` only INCREASES capacity (multiplier > 0). The vanilla resolution
is:

```lua
-- generic_ammo_user_extension.lua:96
self._max_ammo = math.ceil(buff_extension:apply_buffs_to_value(self._original_max_ammo, "total_ammo"))
```

At N stacks of +0.05: `root_multiplier = 1 + 0.05*N`. With 20 stacks
`_max_ammo = ceil(original * 2.0)` = +100%. With 50 stacks `_max_ammo =
ceil(original * 3.5)` = +250%.

- **No zero-crossing**: positive contributions never reach a degenerate floor.
- **No engine cap on `_max_ammo`**: it's a local field, computed
  `math.ceil(...)` at apply time; not networked through any
  `NetworkConstants.max_*` channel (greppable: `NetworkConstants.max_ammo`
  does not exist). Confirmed against
  `scripts/network_lookup/network_constants.lua`.
- **No frame-by-frame fassert**: `_apply_buffs` runs only on
  `apply_buffs` / `refresh_buffs`, not in `update`. So even at extreme stacks
  there's no per-frame validator to trip (unlike `max_overcharge`
  fassert at `player_unit_overcharge_extension.lua:110`).
- **Vanilla magnitudes already reach +100%** (Waystalker passive,
  `talent_settings_kerillian.lua:217-218`). +200% / +300% is gaudy but
  functionally equivalent.

### Possible balance concern (not a safety issue)

At 50 boons +250% magazine size might dwarf typical pickup amounts, making
ammo pickups feel insignificant. **That's a balance question, not a
correctness one** — the user can soft-cap it later if desired. No engine-side
need to fix.

If the user later wants to soft-cap `total_ammo` too, the same hyperbolic
helper works — just inverted (saturating UPWARD instead of downward):

```lua
local bonus = (N * step) / (1 + N * step / cap)
self._max_ammo = math.ceil(orig * (1 + bonus))
```

But that's a future call; **for v0.7.103 leave `total_ammo` alone**.

## TL;DR

- **Root cause**: VT2's `stacking_multiplier` resolution is linear-additive
  (`buff_extension.lua:1391-1448`). 20 stacks of `-0.05` → multiplier of `0`
  → free shots/casts. The bug exists in both `ammo_used_multiplier` and
  `reduced_overcharge` paths because both stat_buffs share the same resolver.
- **Vanilla never stacks these stat_buffs** (every vanilla source uses
  `max_stacks = 1`). The ct_meta architecture is in unexplored territory.
- **Fix**: drop the broken stat_buffs from `CT_META_BOONS[2]`; hook the three
  consumption call sites directly; apply a hyperbolic-saturating cost factor
  with a hard floor of 25%. Same helper, three hooks, universal across ammo /
  energy / overcharge.
- **`total_ammo` is safe** — positive-only growth, no engine cap, no
  zero-crossing. Leave it alone.
