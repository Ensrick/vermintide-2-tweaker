## 0. Safety rules and shared reads (binding for every card in this file)

### 0.1 Why this bucket needs its own rules

These mods write the player's saved inventory and loadouts. Two facts decide the rules:

- The isolated rig profile isolates local files only: `user_settings.config` (every VMF mod setting, including the stores L1 to L5 below) and the local save (`PlayerData`, L6). The rig copies the owner's settings and save into that profile and never writes them back, so a boot starts with the owner's real store contents, not empty stores.
- The backend account is not isolated. The modded realm signs in to the owner's real account. The engine itself sends career loadouts with the cloud script `updateHeroAttributes` whenever `mirror._career_data` differs from `mirror._career_data_mirror` (`Vermintide-2-Source-Code/scripts/managers/backend_playfab/playfab_mirror_base.lua:2885-2900`; the slot comparison is at `:3482-3491`). Only statistics, weave data and weapon poses are behind `read_only_backend` (`:2826`, `:2839`, `:2857`). So a rig script can damage the owner's official loadouts without ever calling a commit function, simply by leaving a changed row behind.

### 0.2 Rules

1. Run only in the rig's isolated profile. One stream of a mod pair per boot (both trees register the same chat commands).
2. A script never calls any of: `Managers.backend:commit`, `BackendManagerPlayFab.commit`, `PlayFabMirrorBase.commit`, `_commit_internal`, `_queue_commit`, `_check_career_data` (it is not a pure read: it writes `_characters_data`, `playfab_mirror_base.lua:3498-3505`), `Managers.save:auto_save`, the chat command `/scrub_official_loadouts apply` (its `apply` branch performs an official write, `gui_tweaker/scripts/mods/gui_tweaker/_gut_native_loadout_commands.lua:146-152`), `/mp_reset`, and `/cim_craft_standard` (static evidence suggests it asserts until fix card WP-CIM-03 lands).
3. Every case that equips, crafts, deletes, designates a bot, adds a loadout row or switches a row does this, in order: `snap = OM.snapshot()`; the step; `OM.assert_clean(T, label)` after each such step; at the end `OM.assert_untouched(T, snap)` then `OM.restore(snap)`. The helper is in 0.4.
4. Equip only while public Tweaker: GUI is loaded with `gut_use_non_modded_loadouts = false` (store mode), unless the card says it is the read-only-mode case. Set `T.set("cim", "auto_equip_new_weapons", false)` so a craft never equips by itself (option at `crafting_in_modded/scripts/mods/crafting_in_modded/crafting_in_modded_data.lua:112`; the write it guards is `_cim_modded_loadout_owner.lua:504`).
5. Destructive mod commands (`/forge_delete_all CONFIRM`, `/forge_delete`, `/reset_modded_loadouts`) may run, because they change the isolated profile's settings only. The case must create its own throwaway items first and assert that nothing else was removed.
6. A case cannot edit a VMF setting table in place: `mod:get` returns a copy. Set up store state only through the mod's own command or writer (`/reset_modded_loadouts`, `/forge`, an equip through E1).
7. A baseline that is already dirty is INCONCLUSIVE, not FAIL: start each case with `T.require(OM.baseline_clean(), "official mirror clean at case start")`. If it is false, report it: the account already carries mod-minted ids in official loadouts.

### 0.4 The official-save invariant, as a scripted assertion

Put this helper at `qa/runtime/_shared/d4_official_mirror.lua` and load it in every case as `OM`. It reads raw fields only. It never calls an items-interface method (those re-enter Tweaker: GUI's read hooks).

```lua
local OM = {}
local function mirror() return Managers.backend:get_backend_mirror() end      -- backend_manager_playfab.lua:1222
local function is_slot(key) return type(key) == "string" and key:sub(1, 5) == "slot_" end

-- true when `id` could not have come from the official account
function OM.minted(id)
    if type(id) ~= "string" then return false end
    local row = rawget(mirror()._inventory_items, id)                           -- B4
    if row == nil then return true, "not in _inventory_items" end               -- vanilla's own broken-slot rule, playfab_mirror_base.lua:1617
    local custom = type(row.CustomData) == "table" and row.CustomData
    if custom and custom.cim_provider ~= nil then return true, "cim row" end    -- _cim_synthetic_item_contract.lua:353
    if id:match("^cwv_.+_%d%d%d$") then return true, "cwv id" end               -- _gut_native_loadout_policy.lua:17-19
    for _, mod_id in ipairs({ "cim", "cim_dev" }) do
        local owner = get_mod(mod_id)
        local store = owner and owner:get("forged_weapons")                     -- L3
        if type(store) == "table" and store[id] ~= nil then return true, mod_id .. " forged_weapons" end
    end
    return false
end

function OM.snapshot()
    local out = {}
    for career, rows in pairs(mirror()._career_data) do                         -- B1
        out[career] = {}
        for index, row in pairs(rows) do
            out[career][index] = {}
            for key, value in pairs(row) do out[career][index][key] = value end
        end
    end
    return out
end

local function walk(fn)
    local m = mirror()
    for career, rows in pairs(m._career_data) do
        for index, row in pairs(rows) do
            local acked = m._career_data_mirror[career] and m._career_data_mirror[career][index]   -- B2
            for key, value in pairs(row) do fn(career, index, key, value, acked and acked[key]) end
        end
    end
end

function OM.baseline_clean()
    local clean = true
    walk(function(_, _, key, value, acked)
        if is_slot(key) and (OM.minted(value) or value ~= acked) then clean = false end
    end)
    return clean
end

-- INV-A: no slot of any official row holds a mod-minted id.
-- INV-B: no official row differs from the acknowledged copy, so the engine's next commit sends no loadout.
-- slots_only = true limits INV-B to item slots (use it only in a case that changes talents on purpose).
function OM.assert_clean(T, label, slots_only)
    walk(function(career, index, key, value, acked)
        local where = string.format("%s %s[%s].%s", label, career, tostring(index), key)
        if is_slot(key) then
            local minted, why = OM.minted(value)
            T.expect(not minted, "INV-A " .. where .. " holds a mod-minted id (" .. tostring(why) .. ")")
        end
        if is_slot(key) or not slots_only then
            T.expect(value == acked, "INV-B " .. where .. " differs from _career_data_mirror (pending official write)")
        end
    end)
end

function OM.assert_untouched(T, snap)
    walk(function(career, index, key, value)
        local before = snap[career] and snap[career][index] and snap[career][index][key]
        T.expect(value == before, string.format("official row changed during the case: %s[%s].%s", career, tostring(index), key))
    end)
end

-- Cleanup only. Raw field writes back to the snapshot, so the engine has nothing to send. Not a commit.
function OM.restore(snap)
    local m = mirror()
    for career, rows in pairs(snap) do
        for index, row in pairs(rows) do
            for key, value in pairs(row) do
                if m._career_data[career] and m._career_data[career][index] then
                    m._career_data[career][index][key] = value
                end
            end
        end
    end
end
return OM
```

Known limits of `OM.minted`: Weapons of Chaos relic ids and Modded Progression Fresh-profile ids have no pattern here `[unverified]`; the "not in `_inventory_items`" test still catches an id that the official sign-in would treat as broken.

## 4. Patch-day canary

Three offline checks written during this audit. They ask one question: does the mod code still name things that exist in the current game? Fix card WP-T-04 turns the first two into one command (`qa/check_patch_day.ps1`); this section is the source description for that card.

Why: each game update since August broke features in this bucket and a tester noticed weeks later (#624, #1465, #1671, #1684, #1686, #1688, #1692, #1693, #1694, #1695).

| Check | What it proves | Script (audit workspace `scripts/`) | Result on 2026-11-13 (decompile `93dea911`) |
|---|---|---|---|
| Hook targets | Every literal `mod:hook`, `mod:hook_safe`, `mod:hook_origin` target `("Class", "method")` is defined in the decompile, directly or through `class(Child, Parent)` | `D4_hook_targets.py <mod_dir> ...` | `modded_progression` 52 of 52, `career_tweaker` 24 of 24, `gui_tweaker` 83 of 83, `gui_tweaker_dev` 85 of 85, `crafting_in_modded` and `crafting_in_modded_dev` 108 of 109 with the one miss allow-listed (a guarded dead branch, `crafting_in_modded/scripts/mods/crafting_in_modded/_cim_standard_forge_presentation.lua:260-262`) |
| Icon atlas names | Every literal `icon = "<name>"` in a mod exists in `Vermintide-2-Source-Code/scripts/ui/atlas_settings/gui_icons_atlas.lua` | `D4_icon_atlas_check.sh <mod_dir>` | `career_tweaker`: 6 distinct names, 0 missing |
| Chaos Wastes trait families | Every category of `morris_weapon_traits.combinations` in the decompile is mapped to melee or ranged in Crafting in Modded's slot policy | `D4_cw_trait_families.py` | 9 categories, 0 unmapped, both streams |

How to run. All three read two folders and write nothing. Set `VT2_REPO_ROOT` to the mod repo and `VT2_DECOMPILE_ROOT` to `<repos>/Vermintide-2-Source-Code` (the defaults assume both sit under the user's `source/repos`). Each exits 0 when clean and 1 on a finding.

When to run. After every game update, in this order: pull the new decompile; run the checks for every mod in `tools/mod-inventory.psd1`; only then run the rig's canary plan and trust rig results. A finding blocks every ship until it is fixed or allow-listed with a reason. Also run them in the normal offline QA whenever the decompile folder is present, so a mod change that names a missing method fails before it ships.

Known limits, so nobody over-trusts a green result:
- Hook targets: only string-literal targets are checked. Hooks whose class is a variable are counted, not resolved: 23 sites in `modded_progression`, 7 in `career_tweaker`, 16 in `crafting_in_modded`, 57 in `gui_tweaker`. WP-T-09 (record hooks at registration and check them in game) covers those. A renamed method with a changed signature still resolves.
- Icon names: validated for `career_tweaker` only. On `crafting_in_modded` and `modded_progression` it reports names that live in other atlas files or are test fixtures (`rt_icon`, `issue246_test_icon`, `athanor_icon_upgrade`, `es_handgun_01`, `shillings`). Widen the atlas list and exclude fixtures before using it there; do not allow-list them blindly.
- Trait families: covers the Chaos Wastes table only, not a new boon family added to the base trait table. It is not part of WP-T-04 yet; add it as a third part.
- Not covered at all: realm flags and settings globals (the cause of #1465 and #1688), removed utility functions (the cause of #1695), removed UI definitions. Two more static checks would cover the known cases: a reviewed list of every read of `eac-untrusted` outside the shared realm library, and a list of the vanilla globals each mod reads, checked against the decompile.
