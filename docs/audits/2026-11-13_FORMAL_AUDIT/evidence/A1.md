## 2. Architecture as built

### 2.1 Entry and load order

`weapon_tweaker/weapon_tweaker.mod` registers `new_mod("wt", {mod_script, mod_data, mod_localization})`. VMF loads localization, then data, then script (`vmf_mod_manager.lua:118-124`).

`weapon_tweaker_data.lua` builds the widget tree (933 static `unlock_<career>_<weapon>` checkboxes plus 79 other ids), calls `_wt_weapon_overrides_widgets.build()`, reads `get_mod("character_weapon_variants")`, and returns through `_wt_history_catalog.decorate_menu` (`WT/weapon_tweaker_data.lua:1724`).

`weapon_tweaker.lua` is a 33-step manifest. Order is load-bearing and is documented only in comments at each `dofile`:

1. `_lib_weapon_appearance`, `weapon_tweaker_backend` (table only), `_safe_hook` (adds `mod:safe_hook` / `traced_hook`)
2. Pure policies: `_wt_axe_balance`, `_wt_fire_sword`, `_wt_grip_offset_policy`, `_wt_skullsplitter_hand`
3. `_wt_history_owner.install` (must precede every balance owner, `weapon_tweaker.lua:124-135`)
4. `_wt_brett_sword_shield_buff`, `_wt_sword_push_combo_owner`
5. `_wt_regression` (must precede every `_rt_register`), `wt_unlock_data`, `_wt_availability`, `_wt_trait_pools`, `_wt_master_toggles`, rework master policy/runtime, `_wt_diagnostics`, `_wt_weapon_action_lifecycle`, `_wt_bolt_staff_overcharge`
6. `_wt_anim_remap_data` + `_wt_anim_remap`, `_wt_reload_3p`, `_wt_flamestorm_fx`, `_wt_transform_runtime`
7. Four file-scope `Managers.package:load` force-loads (`weapon_tweaker.lua:484-496, 531-548, 589-601, 654-669`), `_wt_deepwood_runtime`
8. `_wt_cross_char_template_patches` (mutates `Weapons.*` at file scope), `_wt_cross_character_safety`, `_wt_weapon_balance_patches` (appends to `NetworkLookup.damage_profiles`), `_wt_moonfire_aoe` (appends to `NetworkLookup.explosion_templates`), `_wt_ingame_3p_swap_owner`, `_wt_menu_preview_owner`
9. `mod.on_game_state_changed` (`:927`), `mod.on_disabled` (`:992`), `_wt_settings_runtime` (defines `on_setting_changed`), `_wt_axe_balance.install`, `_wt_fire_sword_owner.install`, `_wt431_damage_profile_parity` (`:1050`), `weapon_backend.install`, `_wt_runtime_checks.install`

`mod:dofile` is not a singleton, so modules never load each other except through this manifest; cross-module values travel on `mod._wt` (35 distinct keys written) and on flat `mod.<field>` (55 distinct fields written). Both counts are script-measured.

### 2.4 Honest assessment

**`weapon_tweaker`**: accreted patches around a sound core idea, then a recent mechanical file split. The idea (1P is universal, remap only 3P events per receiver skeleton, keep state per unit) is coherent and mostly respected (one exception: F05). What is built on it is not one system: thirteen separate mechanisms rewrite or redirect 3P animation events (F02), eleven independent "owners" mutate the same `Weapons.*` tables with apply orders written out by hand at five call sites (F04), and the lifecycle contract with VMF is misunderstood (F01). The recent owner split (the v0.12.209 and v0.12.210 phases and issue #1159, per the module headers) moved code "verbatim" out of the former god file into `_wt_*` owners. It reduced file size, not coupling: the split modules still talk through 90 shared `mod` fields and depend on manifest position. Quality is very uneven by area. The newest code (`_lib_network_lookup`, the #431 wire contract, the history transaction) is careful, fail-closed and host-tested. The oldest and most important code (the animation funnel and its tables) has no behavioural test at all and every one of its 670 cross-career cells is recorded as "untested" by the project's own ledger (`qa/lua/tests/test_wt_kruber_coverage.lua:19-24`, `ANIMATION_COVERAGE.md:3-7`).

**`weapon_tweaker_dev`**: a true superset mirror. Outside 36 marked overlay blocks and 5 extra files it is byte-identical to public (verified by my script and by the gate). It is not a "runtime parity" copy: the overlays change gameplay data (section 5).

**`tools/weapon-history` + `qa/*wt_history*`**: an offline proof factory for one feature (#1436, still `verify-fix`). About 42k lines in total (12.3k shipped runtime/catalog Lua, 17.9k tooling, 7k QA PowerShell, about 5k host tests) and 14 blocking gates in `qa/run_all.ps1:288-470`. The engineering is rigorous for what it proves (catalog bytes equal historical source). It proves nothing about the running game, which is the owner's actual bottleneck (F12).

### 5.3 Does the parity gate enforce parity?

What it enforces (`qa/check_wt_stream_parity.ps1`, blocking in `qa/run_all.ps1:338`):
- every shared `.lua` is text-identical after removing overlay blocks and the stream identity (`:43-69, 83-109`);
- no unlisted dev-only file (`:21-27, 103-107`); the five listed files exist and their symbols are present (`:174-187`);
- the public tree contains no dev file, dev symbol, dev command or "Dev:" label, and its command set equals a 12-entry allowlist (`:28-41, 135-172`);
- every visible public setting has a localization key (`:160-171`);
- Workshop ids and visibility, and dev version = public version + 1 patch, read from the `itemV2.cfg` titles (`:249-262`);
- `.mod` and `.package` files identical modulo identity (`:263-271`).

What it does not enforce:
- It puts no limit on what an overlay block may contain. An overlay can redefine a shared local, add hooks, or change gameplay data, and the gate still passes. The universal unlock map is a deliberate example.
- It does not check `MOD_VERSION` in Lua (only the cfg title), docs, or bundles.
- It does not detect both streams being enabled together.

Conclusion: the gate proves "public is a textual subset of dev". It does not prove "exact runtime parity", which is the wording in the memory note `reference_wt_dev_parity_gate.md` and in the root `CLAUDE.md` mod table ("permits no gameplay-code drift"). The same memory note also says the gate does not check version strings; it does. Practical consequence: a tester result on `wt_dev` is valid evidence for public only for code paths that no overlay touches. For availability rows, wield patches touched by the picker, and anything measured through the dev funnel probes, it is evidence about a different configuration. Combined with F01 (a disabled `wt` still rewrites `can_wield` next to an enabled `wt_dev`), dev test sessions are not a reliable oracle for public behaviour today.
