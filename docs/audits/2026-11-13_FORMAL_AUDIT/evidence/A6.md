## 2. Architecture as built

### 2.1 `gt_dev` entry, load order, module map

- Entry: `general_tweaker_dev/general_tweaker_dev.mod` registers mod `gt_dev` with script, data and localization files. `MAIN` runs top to bottom and loads everything else with `mod:dofile` in a fixed manifest order (`MAIN:70`, `:869-1172` for godmode policies, `:1713-2036` for the feature modules). Three modules load sub-modules themselves (`_gt_bot_fixes.lua:2-3,304,306`, `_gt_level_control.lua:2-5`, `_gt_host_lag_comp.lua:2`).
- 93 files: 39 never call `get_mod` (25 `*_policy` / `*_core` modules, 4 shared `_lib_*` copies, 10 factories or injected-context modules such as `_gt_time_owner.lua` and `_gt_bot_aid_owner.lua`); the other 54 are the entry, data, localization, the in-game check module (`_gt_regression_checks.lua`, 2,343 lines, the largest file) and about 50 engine-facing feature modules.
- `MAIN` still owns four things besides the manifest: all of Godmode (`MAIN:744-1373`, 9 hooks on `DamageUtils`, `BuffExtension`, `StatusUtils`, `GenericStatusExtension`, `GenericStateMachine`), the enemy-spawn block (`MAIN:1428-1600`), the hand-written lifecycle dispatchers (`MAIN:491-557`, `:577-683`, `:685-715`) and the `/gt_regression_test` runner (`MAIN:384-421`). A comment says the chunk "lives near the 200-local ceiling" (`MAIN:4-6`), which is why state is pushed onto `mod._gt_*` fields instead of locals.

### 2.3 Lifecycle and state ownership (five different mechanisms)

1. `mod.update`: a named, pcall-isolated registry (`MAIN:357-383`, exposed as `mod._gt_register_update`). 21 consumers. One module still wraps `mod.update` by hand on top of it (`_gt_debug_probes.lua:964-975`).
2. `on_game_state_changed`, `on_setting_changed`, `on_disabled`: hand-written dispatchers in `MAIN` that call about 30 `mod._gt_<feature>_*` fields by name (`MAIN:491-557`, `:577-683`, `:685-715`). A new feature must edit `MAIN` to be reset or re-applied.
3. Wrap chains: five modules replace the dispatcher with `local prev = mod.on_...; mod.on_... = function ... prev(...)` (`_gt_debug_probes.lua:195-201` and `:950-958`, `_gt_debug_highlights.lua:659-669`, `_gt_bot_teleport_lab.lua:1530-1538`, `_gt_lobby_modded_manifest.lua:331-343`). Only the last one pcalls `prev`.
4. Join events: a second registry, `mod._gt_lobby_register_join_handler` (`MAIN:1740-1782`).
5. In-game checks: a third registry, `mod._gt_rt_register` (`MAIN:384-389`).
There is no `mod.on_enabled`. `mod.on_unload` is owned by `_gt_time_hooks.lua:48-50`.

### 2.4 Honest assessment per mod

- **gt_dev: accreted patches around a few well-built islands.** It is a merge of at least five other authors' mods (Creature Spawner, Hacks, Replicant Bots, Solo QoL, Neuter Ult Effects) plus the old lobby tweaker, bot fixes, cheats, and a large diagnostics layer. Cohesion is low: the only thing the features share is "host or solo utility". The newest code (time control, `_gt_time_*`, November 2026) is the opposite: engine-free factories with an injected API and 160+ real unit assertions (`GTD/_gt_time_control.lua:56-103`). The rest carries issue-number archaeology inside production hooks (one `BTBotTeleportToAllyAction.run` wrapper, `_gt_bot_fixes.lua:836-971`, holds instrumentation for #139, #384, #385, #492 and #515) and an always-on layer of nil-guards that changes engine behaviour for the whole game (finding F03).
- **stable gt: not a snapshot.** 36 files are identical to dev after id normalization, 22 differ, 35 dev files are absent, and one diagnostic probe exists only in stable (section 5). It is a selectively forward-ported hybrid that matches no dev build.
- **vdl_dev: small and coherent.** One file, two `hook_safe`, 27 tuning commands, per-level profile tables. Its two real defects are a missing world gate in the per-frame hook and per-frame allocation (F15).
- **`tweaker/`: dead.** Nothing depends on it at runtime (section 2.8).

### 2.5 `_gt_agent_bridge.lua` (issue #1338): exactly what it can do today

Read in full (273 lines). It is **outbound only**. There is no inbound command path of any kind: no clipboard read loop, no file read, no network listener, no `loadstring`, no hook. Every action is started by a human typing a chat command.

| Capability | Where | Detail |
|---|---|---|
| Heartbeat | `/agent_arm [seconds]` `:198-207`, tick `:172-187`, fields `:139-170` | One `printf` line per interval while armed: `[agent:hb] seq= t=(os.time) state=(game_mode_key) level=(level key) pos=(Unit.world_position of the local hero) hp=(current_health_percent)`. Default 2 s, minimum 0.25 s. Armed state defaults OFF and is not persisted. |
| Stop | `/agent_disarm` `:209-213` | |
| State dump | `/agent_dump <dotted.path> [depth 1-6]` `:215-238` | Resolves a dotted path from `_G` by plain indexing (`:118-134`), serializes with caps of 500 lines, 80 keys per table, 200 chars per string (`:61-113`), framed by `[agent:dump:N] BEGIN/END`, each payload line prefixed `[agent:d]`. It cannot call a method, pass arguments, index by a unit or userdata key, or evaluate an expression. So `Managers.player` works, but `Managers.player:local_player()` or "the buffs on the local unit" do not. |
| Clipboard probe | `/agent_probe_clipboard` `:240-271` | Tests whether `Clipboard.get/put` round-trips, logs a verdict, restores the user's clipboard, never logs content. This is only the gate for a future inbound channel. |
| Desktop half | `tools/agent-bridge/agent-bridge-watch.ps1`, `tools/agent-bridge/README.md` | Tails `console-*.log` and writes `stream.log`, `latest-hb.txt`, `dump-<seq>.txt` under `%APPDATA%\Fatshark\Vermintide 2\agent_bridge\`. |

Limits that matter for an automation plan:
- It has never produced evidence. Issue #1338 is `diagnostics-armed`; its live-test card was invalidated on 2026-08-20 and no result for the clipboard probe is recorded (`issues/open/1338.md`). Whether `Clipboard` is live in retail is unknown. The engine only stubs it when the global is absent (`V2SRC/foundation/scripts/util/patches.lua:117-121`).
- The heartbeat accumulates the `dt` given to `mod.update`. That `dt` is scaled game time: `Boot.game_update` passes `Managers.time:scaled_delta_time(real_world_dt)` (`V2SRC/scripts/boot.lua:747-752`, `V2SRC/foundation/scripts/managers/time/time_manager.lua:199-201`). Under gt's own freeze, which sets the scale to `1e-08` (`GTD/_gt_time_control.lua:66-67`), or any slow-motion preset, the heartbeat stalls or slows. Static evidence; confirm by arming, running `/time_slower`, and comparing `seq` against wall-clock `t`.
- It is dev-only by convention (absent from stable, `promote.ps1` skips files with no stable twin, `tools/promote/promote.ps1:21-22,104`).
- The retail sandbox has no `io` (`gui_tweaker_dev/scripts/mods/gui_tweaker_dev/_gut_config_file.lua:6-10`; `GTD/_gt_regression_checks.lua:588,646,1368` record the same), so console-log output is the only outbound channel and there is no file-based inbound channel.
