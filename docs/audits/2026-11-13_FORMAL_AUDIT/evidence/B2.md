# B2: Test and verification infrastructure audit

Auditor: B2. Date: 2026-11-13. Repo HEAD at audit start: `592253d1` (master). Status: COMPLETE.

Central question: how much of this project's BEHAVIOUR is verified by anything other than a human playing the game, and what test architecture would change that.

Short answer: the project has a large and mostly genuine offline unit suite (7,537 passing cases that execute 43% of the mods' logic lines), but **nothing automated ever runs mod code against the real engine or even against the real vanilla data tables**. The entry file of 11 of 15 mods (where every hook is wired) is never loaded by any test; at most a few suites run text spans cut out of it. The only runtime tier is a chat command a human must type, and only about 4% of its checks read live session state. Meanwhile 81% of the 228 `verify-fix` issues already have an offline test and 73% of their cards already name a machine-evaluable PASS line: the queue is waiting for a person to launch the game and type a command, not for a person's judgment. An empirical experiment in this audit loaded 743 real vanilla files (ItemMasterList 2,979 items, Weapons 183 templates, BuffTemplates 1,547, Breeds 79, CareerSettings 30) in plain Lua 5.1 in 0.5 s and validated real mod data on top of them, so the missing middle tier is feasible today.

All raw outputs and helper scripts are under `docs/audits/2026-11-13_FORMAL_AUDIT/evidence/scripts/` (`B2_*.py`, `B2_*.lua`, `B2_engfree\`, `B2_out\`).

## 4. Findings

Format: `ID | severity | category | title`, then evidence, impact, recommendation.

### B2-F01 | S0 | systemic process | No automated tier ever runs mod code against the engine or the real vanilla data; every runtime fact waits for a human

Evidence:
- `qa/README.md:147`: "No in-game smoke tests. Stingray engine has no headless runtime. Manual in-game verification is the only safety net for runtime bugs."
- `qa/CHECKS.md:458-469`: the project's own coverage table lists 0 automated detections for "Hooks / vanilla-API" (6 pre-ship review), 0 for "Network / multiplayer", 0 for "Vanilla-API drift", 0 for "Cosmetics-specific". `qa/CHECKS.md:835`: in-game smoke tests are listed as not covered.
- `PROJECT_STANDARDS.md:153` forbids mocking "a general VMF or Stingray runtime", and 5.4 (`:881-885`) sends hooks, RPCs, engine objects and multiplayer state to the in-game tier, which only a human can run.
- Measured: entry files 0-3% executed in 11 of 15 mods (3.3); only 31 of 792 in-game checks read live session state (F03); 228 of 329 open issues are `verify-fix`.

Impact: this is the direct mechanical cause of the 228-issue verification queue. A fix can pass 7,537 tests and 107 gates and still do nothing in the game, which is the failure PROJECT_STANDARDS 5.1a records three times (`PROJECT_STANDARDS.md:692-694`).

Recommendation: add the two missing tiers described in section 6: an engine-free integration tier (real vanilla data + recorded VMF surface) and an unattended in-game self-test tier with machine-readable verdicts. Work items W2-W5, W8.

### B2-F02 | S1 | test architecture | The in-game regression tier cannot be consumed by a machine: 15 copy-pasted runners, verdicts in chat and VMF log levels, never auto-run

Evidence:
- 15 separate runner implementations: `weapon_tweaker/scripts/mods/weapon_tweaker/_wt_regression.lua:28-49`, `chaos_wastes_tweaker_dev/.../chaos_wastes_tweaker_dev.lua:348-367`, `character_weapon_variants/.../character_weapon_variants.lua:226-250`, `general_tweaker_dev/.../general_tweaker_dev.lua:390-414`, `gui_tweaker_dev/.../gui_tweaker_dev.lua:151-170`, `crafting_in_modded_dev/.../_cim_bootstrap_runtime.lua:156-180`, `cosmetics_tweaker/.../_cos_command_owner.lua:42-77`, `career_tweaker/.../_crt_regression.lua:43-57`, `enemy_tweaker/.../_et_regression.lua:33-71`, `event_tweaker/.../_evt_regression.lua:24-38`, `modded_progression/.../modded_progression.lua:115-129`, `dynamic_cosmetic_portraits/.../dynamic_cosmetic_portraits.lua:154-172`, `verminious_dreams_lighting_dev/...lua:71-85`, `weapons_of_chaos/.../weapons_of_chaos.lua:119-132`, `character_dialogue/.../character_dialogue.lua:610`.
- Verdict vocabulary differs: seven runners count SKIP (wt, ct, gut, cim, cwv, woc, dcp), seven do not (gt, cos, crt, et, evt, mp, vdl); only cwv has XFAIL/XPASS; only gt_dev has the BAD-SHAPE verdict that 5.1d rule 3 requires.
- PASS goes to `mod:echo` + `mod:info`, FAIL to `mod:echo` + `mod:warning`, the summary only to `mod:echo` (for example `_wt_regression.lua:34-48`). Engine `printf` is used only for SKIP/XFAIL/XPASS in ct and cwv. This contradicts the project's own 5.1d rule 5 ("Any needle a test card relies on must be ALWAYS-ON and TEXT-STABLE. Bounded engine printf, never mod:debug / mod:info", `PROJECT_STANDARDS.md:819-821`) and NON-NEGOTIABLE 9. Tester logs have contained the echo lines (closure comments on #1637 and #959 quote `PASS: issue...`), so they reach the log under that tester's VMF settings; whether they do with echo-to-log disabled is [unverified].
- The lines carry no mod id (`  PASS: <name>`), so a log with several suites is only separable by the `=== <mod> regression_test (v...) ===` header.
- No mod runs its suite automatically; `tools/triage/triage-log.ps1` does not parse verdicts (no match for `regression` in the file except generic FAIL printing).
- The suites rot between human runs: #1637's closure comment records "six unrelated `/gut_regression_test` FAILs in the same log"; open issue #1656 lists 6 cim failures out of 97 from one tester run; closed issues #511, #512, #566, #1148, #1153, #1156, #1227 are all defects in the regression instruments themselves.

Impact: the one tier that sees the engine yields data only when a person types 15 commands, and its output needs a human reader. Checks fail for weeks unnoticed.

Recommendation: one shared runner in `tools/shared_lib` with one verdict vocabulary (PASS, FAIL, SKIP, XFAIL, XPASS, BAD-SHAPE) that prints one bounded `printf` record per check and one summary record, for example `[vt2test] v=1 mod=<id> ver=<MOD_VERSION> check=<name> verdict=<V> msg=<...>` and `[vt2test] v=1 mod=<id> done pass=N fail=N skip=N`. Dev streams run it automatically once per session when the keep is ready. A harvester turns a console log into JSON. W2, W3.

### B2-F03 | S1 | test architecture | Most in-game checks do not assert live engine state, some cannot fail, and none can see whether a hook is installed

Evidence (script classification of 792 literal registrations, `B2_out/rt_checks_classified.json`):

| Class | Count | Share |
|---|---|---|
| (iii-a) Reads live session/world state (`Managers.*`, units, backend mirror) | 31 | 3.9% |
| (iii-b) Reads engine data tables or classes after the mod's mutation (`Weapons`, `BuffTemplates`, `NetworkLookup`, ...) | 178 | 22.5% |
| Calls the mod's own logic with synthetic inputs; reads nothing from the engine | 333 | 42.0% |
| (i) Marker / source-text only | 78 | 9.8% |
| (ii) Existence / shape / constant only | 159 | 20.1% |
| Indirect (named function) | 13 | 1.6% |

145 checks (18.3%) contain a marker assertion somewhere. Mapped to the brief's three classes: (i) 10% (18% if any marker counts), (ii) 20%, (iii) 26% touch engine-owned state at all and only 4% touch live session state; the remaining 42% exercise real mod logic but on fabricated inputs, which the offline suite can already do.

Checks that cannot fail or prove nothing about behaviour:
- `career_tweaker/scripts/mods/career_tweaker/_crt_regression.lua:136-141` (`rawget_on_buff_templates_marker`): defines a local string and fails only if its length is 0.
- `chaos_wastes_tweaker_dev/scripts/mods/chaos_wastes_tweaker_dev/_ct_regression.lua:330-341` (`game_round_ended_swallows_error`): same pattern.
- `weapon_tweaker/scripts/mods/weapon_tweaker/_wt_runtime_checks.lua:36-48` (`husk_extension_hooked`): asserts the vanilla class has a `wield` function, then a local literal; its comment says "We can't easily introspect VMF's hook table portably". Six checks define their marker locally inside the check.
- `general_tweaker_dev/scripts/mods/general_tweaker_dev/_gt_creature_spawner.lua:1002-1003` sets `GT_CS_CLIENT_REQUEST_MARKER_v0_2_246` and `mod._gt693_cs_client_request_wired = true`; the check at `:1640-1647` compares them to the same literals. It fails only if those two lines are deleted.
- `chaos_wastes_tweaker_dev/.../_ct_regression.lua:861-880` (`cursed_chest_unique_trials`, the test for #463): a marker string compare plus `type(x) == "table"` on three globals.

No check drives the game: only 34 bodies even mention a verb such as spawn, wield, equip, rpc or network_send, and none starts a mission.

Impact: a green in-game suite says little about the features. The checks named after fixes for #463 and #693 would pass with the fix logic broken.

Recommendation: (1) add a hook census to the shared registrar: wrap `mod:hook*` once per mod so every registration is recorded with a fire counter, and give the suite one generic check "every registered hook target exists and its wrapper is installed"; (2) delete local-marker checks and move marker compares to `qa/rt_textual_invariants.psd1` (which exists for this, 350 rows); (3) move the 333 pure-logic checks to the offline suite; (4) require every remaining in-game check to read at least one engine-owned value. W4, W9.

### B2-F04 | S1 | coverage | The offline suite tests extracted policy modules, not the mods: entry files, hook wiring and composition are unexecuted

Evidence: section 3.3. 43.2% of logic lines executed; 11 entry files at 0%; 232 of 897 files never executed. The suite's own doctrine restricts it to "deterministic transformations ... on ordinary Lua values" (`qa/lua/README.md:71-80`), so the architecture responded by extracting `_policy`/`_core` modules (well tested) and leaving the hook bodies and load order untested. 1,064 hook sites exist; the unit tests that do touch hooks invoke the callback through a private fake `mod` (185 test files define one), never through the real target's signature.

Impact: the bug classes the project lists as its most expensive (dead hook target, upvalue capture, wrong class in the pair, load-order nil, duplicate hook) live exactly in the unexecuted code.

Recommendation: boot every mod's real entry file in the engine-free integration tier (section 6, tier 2) under a recording VMF with real vanilla classes loaded as data. Acceptance metric: entry-file line coverage. W5.

A limit that matters for the brief's "NetworkLookup appends are deterministic" idea: vanilla builds most lookups with `create_lookup`, which iterates `pairs(hashtable)` (`scripts/network_lookup/network_lookup.lua:36-45`). The numeric index a name receives therefore depends on the VM's hash iteration order. A PUC Lua harness can assert membership, counts and capacity budgets of each lookup, and that a mod's appends are a deterministic function of its inputs, but it cannot reproduce the engine's actual indices. Index identity between peers stays a runtime (R or C class) fact.

### 5.4 Is "do not mock a general VMF or Stingray runtime" right, and where is the line

Half right. The rule protects against the failure the project documented as "lying instrument" (5.1d): a simulated engine that renders nothing and syncs nothing would report green on features that do not work. That part should stay.

It is wrong in two places, and the cost is visible (F04, F11, F12):

1. VMF's registration surface is small, deterministic and already re-implemented privately 185 times. One shared recorder is safer than 185 private ones.
2. Vanilla data and class definitions are not "runtime": they are plain Lua that loads in half a second. Forbidding their use forced copied fixtures and frozen constants.

The line I recommend:

| Layer | Treatment in an offline harness |
|---|---|
| Vanilla data tables, settings, templates, pure helper code, class definitions as tables of functions | REAL, loaded from the pinned decompile revision |
| VMF API (`get_mod`, `hook`, `hook_safe`, `hook_origin`, `command`, `get`/`set`, `dofile`, `network_register`, localization lookup) | RECORDER: records registrations, exposes callbacks to the test, enforces VMF's known rules (second hook on the same pair is dropped), never simulates the menu or the network |
| Value math (`Vector3`, `Quaternion`), `bit`, table/string/math extensions | FUNCTIONAL shim or the real foundation file |
| Engine C API (`Unit`, `World`, `Managers.*` instances, `Network`, `Gui`, `Wwise`, package loading, flow) | INERT recording stub. A value obtained from it may be stored or passed along, never asserted on. A test whose verdict depends on a stub's return value is malformed |
| Frame updates, physics, animation, rendering, real transport, resource residency, timing | NEVER offline. These are R (in-game, unattended), C (two clients) or V (eyes) |

Offline assertions that become legitimate under this line: the mod's entry file loads without error with every setting off and with every setting on; every string-form hook target exists in this game version; no duplicate (class, method) per mod; every item a mod registers has a template that exists and an action table of the right shape; every buff, breed, career, item and skin key a mod names exists; append counts stay inside lookup capacity; settings defaults round-trip through the data file and localization.

What stays out: "the hook fires", "the weapon is in the hand", "the remote player sees it". Those need the engine.

## 6. Proposed target test architecture

Five tiers. Each issue and each check declares the verification class it serves (codes from the common brief).

| Tier | Class | What it verifies | Where it runs | Budget | What it gates |
|---|---|---|---|---|---|
| 1. Static | S | Syntax, lint, duplicate hooks, localization, cfg, asset contracts. Release paperwork moves to a separate release profile | pre-commit, CI | under 60 s for the product profile | Commit, PR |
| 2. Unit | U | Pure logic of modules, through one shared fake VMF; case isolation; sharded | pre-commit (changed mods), CI (all) | under 60 s | Commit, PR |
| 3. Engine-free integration (NEW) | S+U | Each mod's real entry file booted under the recording VMF on top of real vanilla data: hook census against the game version, item/template/buff/career cross-references, lookup budgets, settings on/off boot, cross-mod boot (all mods together) | Local (decompile present) and CI through a committed names-only oracle | under 15 s | PR merge. Also run on every new game version before anything else |
| 4. In-game unattended self-test (NEW) | R | The shared runner executes every in-game check automatically at keep-ready in dev streams and prints machine-readable records; scenario specs drive actions (equip, craft, spawn, enter mission) through an action library when a plan is supplied on the command line or through the agent bridge; a harvester converts the console log to JSON and posts verdicts | Any real session (testers' normal play gives passive results for free); an unattended launch on the owner's machine when authorized | one keep boot (minutes) | `verify-fix` to closed for R-class issues |
| 5. Human | V, C | Only what needs eyes, ears or two real clients. The card is generated from the same spec, already stripped of everything tier 4 asserted | Tester sessions | small | Closure of V and C issues |

Rules that make this work:
- A check belongs to exactly one tier. Pure-logic checks leave the in-game suite; marker checks leave it for the textual-invariant manifest or are deleted.
- Tier 4 records are the only accepted evidence format for R: `[vt2test]` lines from engine `printf`, bounded per session.
- A fix for an engine-side bug is complete when a tier 3 or tier 4 assertion fails on the pre-fix code. Tier 2 alone is not sufficient for that kind of bug.
- New game version procedure: regenerate the oracle, run tier 3, fix everything it reports, then ship.
