## 2. Architecture as built

### 2.1 ct_dev

**Entry and load order.** `chaos_wastes_tweaker_dev.lua` (1,597 lines) is a manifest plus leftovers. Order: bomb-cooldown display install (`:87-89`), regression harness + `/ct_regression_test` (`:335-367`), mutex (`:375`), loot fallback metatable (`:418-435`), `_adventure_pool` + `inject_pool()` (`:437`, `:593`), lobby hash shim (`:616-642`), then "owner" modules called as `mod:dofile(path)(mod, ctx)`: altar reuse (`:1072`), host-state transport (`:1088`), peer manifest (`:1121`), run runtime (`:1221`), adventure runtime (`:1262`), pickup spawn / spawn eligibility (`:1362-1380`), CoT cost / early reward (`:1398-1403`), chest revive (`:1429`), boon runtime (`:1439`, which loads registry, meta boons, trait boons, grant owner, peer parity), settings lifecycle (`:1473`), regression (`:1495`), then eleven small modules (`:1558-1595`). 101 `mod:dofile` calls in total.

**State ownership.** There is no single owner. State lives in (a) entry-file locals passed into owners as getter/setter closures (`:1229-1256`), (b) 201 distinct `mod._ct*` fields used as a cross-module bus, (c) 44 implicit globals in `_G` (see F11), (d) fields written onto vanilla objects (`self._ct_progcoin_last_logged` at `:1028`, `rc._ct_isha_active` at `_ct_peer_parity_owner.lua:482`). Late binding is done with forward-declared locals assigned after the consumer was constructed (`:765-768`, `:1483-1485`).

**Hook surface.** 137 sites in 42 files. Per-frame or hot-path hooks: `DeusChestExtension.update` (`_ct_altar_reuse_owner.lua:409`), `DeusCursedChestExtension.update` (`_ct_cot_early_reward.lua:25`), `PlayerBotBase.update` (`_ct_blessed_bots.lua:166`), `DeusShopView.update` / `DeusCursedChestView.update` (`_ct_boon_offer_view_owner.lua:497,508`), `IngamePlayerListUI._draw` (`_ct_tab_panel_owner.lua:206`), `CameraManager.shading_callback` (`_ct_curse_lighting_owner.lua:246`), `BuffExtension.add_buff` (`_ct_meta_trait_boons.lua:655`), global `Localize` (`_ct_adventure_runtime_owner.lua:312`), `GenericAmmoUserExtension.use_ammo` (`_ct_meta_boon_owner.lua:505`), `ConflictDirector._post_spawn_unit` (`_ct_progressive_elite_runtime.lua:167`), `PickupSystem._can_spawn` (`_ct_spawn_eligibility_owner.lua:193`).

**RPC channels (VMF `network_register`).** `ct_sync_host_settings_chunk` and `ct_graph_snapshot_chunk` (`_ct_host_state_transport_owner.lua:277,681`), `ct_peer_manifest_chunk` (`_ct_peer_manifest_owner.lua:203`), `ct_altar_uncollect` (`_ct_altar_reuse_owner.lua:351`), `ct_progdiff_start` (`_ct_progressive_difficulty.lua:64`), the bomb-cooldown display channel (`_ct_bomb_cooldown_display.lua:542`), and the parity beacon `ct_boon_catalog_exact_v1` (`_ct_peer_parity_owner.lua:60`, registered inside `_lib_peer_parity.lua:653`). All carry `CT_RPC_SCHEMA = 2` as first argument (`chaos_wastes_tweaker_dev.lua:82`) and drop on mismatch.

**Vanilla tables mutated.** `NetworkLookup.level_keys` and `.mission_ids` (+6 rows per adventure mission, `_adventure_pool.lua:542-555`), `NetworkLookup.deus_power_up_templates` (+12) and `.buff_templates` (+21) (`_ct_wire_policy.lua:32-83,217-243`; second appender `_ct_boon_registry.lua:124-133`), `LevelSettings`, `DEUS_LEVEL_SETTINGS`, `TerrorEventBlueprints`, `WeightedRandomTerrorEvents` (`_adventure_pool.lua:921-992`), `DeusPowerUps`, `DeusPowerUpsArray`, `DeusPowerUpsArrayByRarity`, `DeusPowerUpsLookup`, `DeusPowerUpBuffTemplates`, `BuffTemplates` (`_ct_boon_registry.lua:223-265`), `DeusPowerUpRarityPool` (`:294-297`), `DeusSoftCurrencySettings.loot_amount` metatable (`chaos_wastes_tweaker_dev.lua:418-435`), `ProcFunctions`, `BuffFunctionTemplates.functions`, `GenericTerrorEvents`, deus populate `config` during graph build (`_ct_campaign_graph_owner.lua:316-367`).

**Persistence.** VMF settings only (7 `mod:set` sites). No backend or save writes found by grep. The host's 545 synced settings are re-serialised to JSON and chunked at 400 bytes on run start and on debounced edits (`_ct_host_state_transport_owner.lua:375-442`).

**Cross-mod.** `get_mod("gut_dev")`/`get_mod("gut")` for Mod Tweaker runtime gates, dropdown categories and profile diagnostics (`_ct_wire_policy.lua:457-468`, `_ct_dev_mission.lua:287-300`); `get_mod("bt")` net-replay recorder (`_ct_host_state_transport_owner.lua:291,391`); implicit use of enemy_tweaker's `et_skaven_warlord` breed through `Breeds` (`_ct_combat_hooks.lua:846-893`). No guard against `ct` and `ct_dev` loading together.

**Host-only versus all-peer.** One mechanism: `effective_setting(name)` returns `mod:get(name)` on the host, the host-synced value on clients, and the client's own saved value when no sync has arrived (`chaos_wastes_tweaker_dev.lua:1142-1152`). Every setting is synced except two (`_ct_host_state_transport_owner.lua:44-76`). There is no per-setting scope label in data; 44 of 1,338 localization lines mention "host".

**The #426 "five-gate beacon", as built.** (1) Exact catalog: 12 power-ups + 21 buffs appended in sorted order and fingerprinted including numeric ids (`_ct_wire_policy.lua:296-313`, `_lib_wire_catalog.lua:34-93`). (2) Beacon: VMF channel with identity, epoch, challenge and echo; features start disabled, enable after 2 s of full acknowledgement, disable at once (`_lib_peer_parity.lua:157-771`). (3) Pool eject / inject on gate change (`_ct_peer_parity_owner.lua:364-385,747-775`). (4) Grant-time filters in the `add_power_ups` hook, bot picker, starting boons, Isha/Ulric miracles (`_ct_boon_grant_owner.lua:185-190,240-244,395-396,507-508`; `_ct_boon_registry.lua:728,771`). (5) Hot-join fence: strip all custom content from run state before native sync if the joiner has not acknowledged, kick if the strip fails (`_ct_peer_parity_owner.lua:790-820`). Findings F02 and F03 are about gates 3 and 5.

**Assessment.** Accreted patches under an active decomposition. The owner extraction is real (entry went from about 13k to 1.6k lines) and the pure `*_policy.lua` / `*_core.lua` kernels are good seams, but the extraction moved code without changing the coupling: owners receive 10 to 25 closures each, share state through `mod._ct_*` and `_G`, and the file is still pinned to the Lua 200-local limit (comments at `:86`, `:92`, `:731`, `_ct_combat_hooks.lua:864-870`). Of 37,664 lines, 9,888 are comment-only (26%), 2,204 are standing per-issue diagnostics modules (`_ct_diag_*`, `*_audit*.lua`, `_ct_profile_snapshot.lua`), 1,825 are the in-game regression modules, and 288 code lines call `printf`; further probes live inside production hooks (for example `_ct_altar_reuse_owner.lua:409-440`). The wire-safety layer is the most carefully written part and still has two holes that its own comments describe.

### 2.2 chaos_wastes_tweaker (public)

Not an older snapshot. It is a second implementation at the same version number: a 13,294-line monolithic entry, its own wire stack (`_ct_wire_runtime.lua`, `_ct_wire_bootstrap.lua`, a 588-line `_ct_wire_policy.lua`, 29-row `ct-public-wire-v1` catalog), eight `_ct_official_*.lua` modules, `_ct_diag_official_apply_evidence.lua` and eight `/verify_ct_*` commands that dev does not have. See section 5.

### 2.3 event_tweaker

**Entry.** `event_tweaker.lua` (70 lines) is a pure manifest of 14 `mod:dofile` calls in a documented order (`:45-68`); two diagnostics leaves are `require`d from `_evt_diagnostics.lua:27-28`. Shared namespace `mod._evt`; catalogs are `require`d single-source modules (`event_tweaker_catalog.lua`, `event_tweaker_curses.lua`, `event_tweaker_missions.lua`) because data and localization evaluate before the script.

**Mechanism.** Host-side injection into the live-events backend: `get_special_events` returns an extra `{name, weekly_event = "append", mutators}` row (`_evt_backend_hooks.lua:32-83`), which vanilla folds into the level's mutator list (`V2/scripts/managers/game_mode/game_modes/game_mode_base.lua:257-289`) and activates on the host only (`V2/scripts/managers/game_mode/mutator_handler.lua:45-48`). All selection funnels through `gather_mutators()` and its `add()` guard chain (`_evt_selection.lua:227-299`).

**Hooks.** 26 sites: 3 backend, 5 `MutatorHandler`/`StateIngame`/`CameraManager` in `_evt_cursed_adventure.lua`, 10 start-game menu hooks in `_evt_missions.lua`, 2 Tab-list hooks, 3 diagnostics, `MutatorHandler.conflict_director_updated_settings` (pacing guard), `GameModeBase.is_joinable` and `GameNetworkManager.remove_peer` (curse parity). One RPC channel: the beacon `et_curse_catalog_exact_v1` (`_evt_guard430_curse_parity.lua:71`). No `NetworkLookup` writes (`_evt_missions.lua:17-19`). No implicit globals. Persistence: one `mod:set`.

**Assessment.** Coherent design. Small single-purpose modules, a single funnel, pure policy modules with offline tests, explicit guards named after the crash they prevent. Its weaknesses are specific (F05, F15) rather than structural.

### 2.4 enemy_tweaker

**Entry.** `enemy_tweaker.lua` (103 lines), same manifest pattern, `mod._et` namespace, 42 `mod:dofile` calls. Engine-free cores are loaded first and stored on `mod._et` (`:55-65`).

**Mechanism.** Mutates conflict-director data (`HordeCompositions`, `HordeCompositionsPacing`, `Current*Settings`) with backup/restore (`_et_horde_presets.lua:210-272`), re-applied from wrapped `ConflictDirector.init` and `refresh_conflict_director_patches` (`_et_director_hooks.lua:33-86`). Two custom breeds (`et_skaven_warlord`, Chosen) are registered at load through a transactional registrar (`_et_custom_breed_registrar.lua`, 1,426 lines) that plans against shadow tables, commits three `NetworkLookup` axes together and can roll back (`:918-1332`). A sender floor substitutes a vanilla donor breed unless every peer proves the exact catalog (`_et_custom_breed_parity.lua:100-113`), and a hot-join fence holds or kicks unproven joiners while a custom breed is live or queued (`:329-436`).

**Hooks.** 15 direct plus 25 through `_hook_wrap` / `_hook_wrap_table` / `_hook_wrap_tick` / `_hook_resolve_first_once` (`_et_protect.lua:65-206`). Global hooks: `table.clone` (`_et_roaming.lua:271-275`), `Localize` (`_et_skaven_warlord_breed.lua:163`). RPC: personal handicap channel (`_et_personal_handicap.lua:70`) and the beacon. Lifecycle is owned by one module (`_et_lifecycle.lua:116-223`) with a bounded settings queue.

**Assessment.** Coherent at module level and the registrar is the best piece of engineering in this family, but the protective wrapper layer converts hard failures into silent partial state (F07) and the parity fence sits on the engine's peer state machine in a mod advertised as host-only (F08).

### A4-F01 | S0 | network-coop | The lobby hash shim lets peers with different `NetworkLookup.level_keys` into the same session, and nothing gates the level / graph axis
- **Evidence.** Vanilla folds `#NetworkLookup.level_keys` into the lobby hash (`V2/scripts/network/lobby_aux.lua:26`, used at `:32` and `:38`), which is the engine's own "different content" fence. ct_dev appends 6 keys per adventure mission unconditionally (`ct_dev/_adventure_pool.lua:542-555`, `:1002-1011`; projected 582 -> 792 keys per `qa/check_level_lookup_budget.ps1:15,39`) and then hooks `LobbyAux.create_network_hash` to hide the appended rows while the hash is computed (`ct_dev/chaos_wastes_tweaker_dev.lua:616-637`). The public mod does the same (`ct/chaos_wastes_tweaker.lua:457-458`). The transport comment states the consequence: "The LobbyAux hash shim above hides the count diff so peers with different values can still join, but each peer's resolved graph diverges as a result" (`ct_dev/_ct_host_state_transport_owner.lua:60-66`). The only parity gate in the mod covers the boon / buff axes (`_ct_wire_policy.lua:32-83`; every `_ct_wire_safe` call site is boon code). Graph mutation runs on every peer from the seed (`_ct_campaign_graph_owner.lua:284-478`) and the host's corrective snapshot travels on a VMF channel that a peer without the mod never receives. The peer manifest that records `num_levels` only logs at debug level (`_ct_peer_manifest_owner.lua:123,149-151,173-177`).
- **Impact.** A player without the mod (or with a different catalog size) can join a ct host. Static evidence suggests that player then computes a different map and, when the host travels to an injected adventure permutation, is asked to load a level key its `LevelSettings` does not contain. The mod's own comment records that crash shape from an earlier incident (`_adventure_pool.lua:909-916`). Wrong-map and wrong-curse reports (the #136-class dumps at `_ct_campaign_graph_owner.lua:244-282`) belong to the same cause.
- **Confirm by.** Two clients, one without ct: host enables one adventure mission and travels to it. Expected if the finding holds: client map differs from host map; client fails at level load. A solo runtime probe cannot show this.
- **Recommendation.** Decide the product rule first (Q1). Then either (a) delete the shim so the engine isolates modded lobbies, or (b) keep it and add a second gated feature on the existing beacon: adventure injection, shrine-to-mission conversion, curse-count and god overrides stay at vanilla values until every peer acknowledges an identity that includes the level-key rows. Reuse `_lib_wire_catalog.build_identity` with namespace `ct.level_keys`.

### A4-F02 | S0 | network-coop, correctness | The custom-boon parity gate and the `enable_boon_*` toggles edit a table the roller never reads; the shrine purchase path has no parity check
- **Evidence.** The vanilla roller iterates `DeusPowerUpsArrayByRarity[rarity] or DeusPowerUpsArray` (`V2/scripts/helpers/deus_power_up_utils.lua:138-146`); `DeusPowerUpRarityPool` is consumed once at boot (`V2/scripts/settings/dlcs/morris/deus_power_up_settings.lua:7121`). ct_dev inserts every custom boon into the two arrays unconditionally at load (`ct_dev/_ct_boon_registry.lua:255-259`), while "pool membership" (`_add_dormant_to_pool` / `_remove_dormant_from_pool`, `:274-322`), the toggle path (`_ct_meta_trait_boons.lua:180-190`) and the parity eject / inject (`_ct_peer_parity_owner.lua:364-385`, initial eject `:769`) all write only `DeusPowerUpRarityPool`. ### A4-F03 | S0 | network-coop, correctness | event_tweaker's hot-join lock hooks `GameModeBase.is_joinable`, which subclass instances never call
- **Evidence.** `evt/_evt_guard430_curse_parity.lua:130-135` installs `mod:hook("GameModeBase", "is_joinable", ...)` with the comment "Adventure inherits this implementation". Vanilla `class()` copies every parent method into the subclass table at definition time (`V2/foundation/scripts/util/class.lua:53-59`); `GameModeAdventure = class(GameModeAdventure, GameModeBase)` (`V2/scripts/managers/game_mode/game_modes/game_mode_adventure.lua:8`; same for `game_mode_deus.lua:23`, `game_mode_weave.lua:7`); only `GameModeInnVs` defines its own `is_joinable` (`game_mode_inn_vs.lua:344`). A hook placed on `GameModeBase` after boot therefore replaces a function no live game mode resolves. The repo documents this trap as a non-negotiable (`CLAUDE.md:359`, `docs/engine/01_foundation_and_oop.md:79-82,228`).
- **Impact.** The lock is the only thing that keeps a player without Tweaker: Events (or without the curse packages) from joining a mission where managed curses or the Shadow adapter are already active (`_evt_guard430_curse_parity.lua:80-88`; arming only checks peers pending at that moment, `:202-211`). - **Confirm by (solo, R).** With a managed curse active run: `rawget(GameModeAdventure, "is_joinable") == GameModeBase.is_joinable` (false means the hook is not on Adventure) and `Managers.state.game_mode:game_mode():is_joinable()` (true means not locked) while the log shows `[et:430] ... LOCKED`.
- **Recommendation.** Hook the derived classes that can host these mutators (`GameModeAdventure`, `GameModeDeus`, `GameModeWeave`), one hook each, or hook `GameModeManager.is_joinable` plus the `peer_states` consumer. Add a repo lint: a `mod:hook` whose class has subclasses in the decompile (`class(X, Base)`) is an error unless annotated.

### A4-F04 | S1 | network-coop, state-lifecycle | ct_dev's hot-join fence deletes every player's custom boons whenever the joiner is not already acknowledged, and acknowledgements expire after 15 s off-roster
- **Evidence.** The fence runs inside `GameNetworkManager.hot_join_sync`: if `inst:peer_has(peer_id)` is false it calls `_ct_strip_modded_content` (removes custom power-ups, party power-ups, persistent buffs, live server buffs for all players) before native sync, with no wait (`ct_dev/_ct_peer_parity_owner.lua:777-820`, strip `:447-515`). Vanilla calls `hot_join_sync` before the joiner is added to `PlayerManager` (`V2/scripts/network/peer_states.lua:432` then `:450`), so the roster-driven beacon cannot have seen a first-time joiner. For returning peers the acknowledgement is retained only while roster absence is under `ABSENCE_GRACE = 15.0` s (`_lib_peer_parity.lua:170`, `:360-363`, expiry `:705-712`), and vanilla removes every remote player at each `StateIngame` exit (`V2/scripts/managers/player/player_manager.lua:170-175`, called from `V2/scripts/game_state/state_ingame.lua:1934`). The beacon clock advances from `mod.update` (`_lib_peer_parity.lua:597-600,678-681`). The pinned live-test card accepts the loss as conditional: "if the positive parity acknowledgement arrived before native sync, the custom state remains active" (`issues/open/426.md:26`).
- **Impact.** Static evidence suggests two outcomes in an all-ct lobby: a mid-level joiner with the identical build still triggers the strip; and any level transition where the host sees a client off-roster for 15 s or more expires that client's proof, so the client's next `hot_join_sync` strips the party. Custom boons are paid for with run currency; nothing refunds them. Whether VMF re-establishes its handshake before `hot_join_sync` is [unverified: VMF source not available here].
- **Confirm by.** Two ct clients, one Chaos Wastes run with a `ct_meta_*` boon, two level transitions: search the host log for `[ct:426] parity-loss strip reason=hot_join_unconfirmed`. Offline first: `qa/lua/tests/test_peer_parity_transition.lua` can drive the lib with a 20 s roster gap followed by `require_peer`.
- **Recommendation.** Use the pattern enemy_tweaker implements: hold the joiner's native sync for a bounded window while waiting for the exact acknowledgement (`et/_et_custom_breed_parity.lua:298-310`), strip only on timeout, and key ack retention to connection state (`remove_peer`) instead of a wall-clock roster gap. If strip must remain, refund the purchase price.

## 8. Is event_tweaker a good template, and what a common module standard should take from it

**Yes, as a structural template; no, as a safety template.** It is the cleanest of the three and enemy_tweaker already follows the same shape. But its most safety-critical hook is one the repo's own rules forbid (F03), which shows that the template's rules are conventions with no enforcement.

Take from event_tweaker:
1. Entry file is a manifest only: version, banner, ordered `mod:dofile` list with a one-line purpose each (`evt/event_tweaker.lua:45-68`).
2. Catalog data in `require`d single-source modules shared by data, localization and script (`event_tweaker_catalog.lua`, `event_tweaker_curses.lua`).
3. One funnel for the feature's effect (`gather_mutators` / `add`), with guards as separate modules in front of it.
4. Pure `*_policy.lua` modules for decisions, with offline tests that execute them.
5. A short per-mod `CLAUDE.md` with "where new code goes" and the load-bearing rules.
6. Zero implicit globals; one regression module that owns the harness.

Take from enemy_tweaker:
7. One lifecycle module that owns `on_setting_changed`, `update`, `on_enabled`, `on_disabled`, with a bounded settings queue (`et/_et_lifecycle.lua`).
8. A transactional registrar with an injected runtime for every write to `Breeds`-class tables and `NetworkLookup` (`et/_et_custom_breed_registrar.lua`, `_lib_network_lookup.lua`): plan against shadow tables, commit together, roll back.
9. Engine-free cores loaded first and stored on the namespace (`et/enemy_tweaker.lua:55-65`).

Add, because all three lack it:
10. A hook registry: every hook goes through one function that records class, method, owner module, kind and a per-frame flag. That gives the runtime harness "is it installed and reachable", gives QA the base-class and duplicate lint, and gives a per-frame budget.
11. Declared module interfaces: each module returns `{ requires = {...}, exports = {...} }`; the manifest loader fails loudly on a missing requirement instead of leaving a nil in `mod._x`.
12. Setting scope in data (`host`, `all_peers`, `local`) with enforcement in one `effective_setting`, and a parity beacon gate for every `all_peers` feature, not only the one that crashed first.
13. Regression checks that print JSON rows, support SKIP, and may not be marker comparisons.
14. Diagnostics behind one switch, installed as modules that can be deleted when their issue closes; no probes inside production hooks.
15. Fences never sit on the engine's peer state machine without a bounded timeout and a "local peer" bypass tested offline (lesson of #1497); prefer "hold then degrade" over "strip" or "kick".
16. Dev and public builds generated from one tree.

File naming: name modules by responsibility, not by issue number (`_evt_guard430_curse_parity.lua` should be `_evt_curse_parity_gate.lua`); keep the issue number in the header.

## Addendum (round 2, 2026-11-13): corrections found while writing `plan/wp/CW.md`

1. **VMF source is available locally.** Section 1 said no VMF source was in these repos. A clone exists at `<repos>/Vermintide-Mod-Framework` (commit `81bb4ce`). It confirms what F04 marked [unverified]: VMF pings a peer only from its `PlayerManager.add_remote_player` hook and forgets the peer in `remove_player` (`vmf/scripts/mods/vmf/modules/core/network.lua:366-373,375-397`), and `network_send` reaches only peers in that table (`:186-198,234-264`). F08's 10 s hold cannot end in proof for a first-time joiner; it always ends in a kick. 2. **F02 scope.** The public tree already strips custom boons by parity at roll time (`ct/chaos_wastes_tweaker.lua:2595-2598`) and filters purchases. The `enable_boon_*` toggle defect exists in both trees (`ct/chaos_wastes_tweaker.lua:9055-9078` edits `DeusPowerUpRarityPool` only).

The host sends settings only at run setup and after edits (`ct_dev/_ct_run_creation_owner.lua:381`, `ct_dev/_ct_host_state_transport_owner.lua:250`), so a late joiner never receives them.
