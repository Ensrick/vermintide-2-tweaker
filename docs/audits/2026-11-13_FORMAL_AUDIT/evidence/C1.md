# C1 - Autonomous runtime verification of VT2 mods: feasibility and design

Auditor: C1. Date: 2026-11-13. Status: COMPLETE.

Desk research only. No game, launcher, Steam action, build or deploy was run. No write outside the audit workspace. Two small read-only helpers were run on PC-A and are listed in Appendix B (a string scan of the SDK's dev engine exe, and a child-process environment probe that starts only `powershell.exe -NoProfile`).

Verdict words used in this report:
- PROVEN-IN-SOURCE = the code path exists and is unguarded in the decompiled retail Lua (or in VMF / a shipped mod). It has not been observed by me at runtime.
- PROVEN-IN-USE = additionally seen working in the owner's own console logs or in a mod that players run today.
- LIKELY = the pieces are proven but the combination has not been observed.
- UNKNOWN-NEEDS-EXPERIMENT = cannot be decided from files on disk. Each has an experiment in section 6.
- NOT POSSIBLE = the retail build removes it.

## 1. Answer in plain words

1. Fully autonomous verification of the "R" class (a script inside the running game reads state and asserts) is feasible. Every building block is present in retail Lua. Most are already used by Fatshark's own test framework, which ships inside the retail game, or by mods the owner already runs.
2. What has never been observed on this machine: (a) starting the retail exe without the launcher window, (b) running the game on a private desktop so it cannot reach the owner's screen, keyboard or focus, (c) the hands-free path through the new 6.13.0 main menu. Three supervised experiments decide them: E1 and E2 take about ten minutes each, E3 needs a first driver build. If (a) fails there is a slower fallback through Steam and the launcher that only suits PC-B.
3. The game was not installed during this audit (Steam was still downloading: 29.8 of 45.4 GB at the last check), so nothing about the retail exe could be checked. The first experiment (E0) is a file scan that needs no launch.
4. Co-op needs two Steam accounts on two machines. Retail has no LAN or offline mode. A single orchestrator can still drive both machines, because the in-game driver can talk HTTP.
5. Purely visual and audio checks stay with live players. A screenshot channel can move part of them to AI review, but capturing a window on a private desktop is unproven.

Expected yield: one boot reaches the keep in about 67 s on PC-A with the full 27-mod stack (measured from the owner's log, N11). A keep-only batch costs about 1.5 minutes plus 5 to 30 s per check. A mission batch costs about 2.5 minutes plus checks. The whole R-class backlog fits in a few hours of unattended machine time once scripts exist. Writing the scripts is the real cost, not running them.

## 3. Findings

Severity counts: S0 = 1, S1 = 3, S2 = 5, S3 = 1.

**F1 (S0, process). There is no autonomous runtime verification path, and the one in progress is stalled on its first human step.** 228 issues wait for a human who is not playing. The agent bridge (issue #1338, opened 2026-08-16) shipped only outbound telemetry. Its next phase is gated on a human typing `/agent_probe_clipboard` in the keep (`tools/agent-bridge/README.md:44-46`). The current card dates from 2026-08-20 (`issues/open/1338.md:41`) and no result was ever recorded: no comment carries a verdict, none of the ten console logs on disk contains an `[agent:probe] verdict` line, and the watcher's inbox folder `%APPDATA%\Fatshark\Vermintide 2\agent_bridge\` does not exist, so the watcher has never run on PC-A. The bridge as designed still needs a human to launch the game, start a watcher in a terminal and type commands (`README.md:10-27`). It observes; it cannot drive.

**F2 (S1). 831 in-game regression checks exist and none can run without a human typing a chat command.** Count of `rt_register("` call sites in the active trees: ct_dev 115, gt_dev 114, cwv 104, cim_dev 97, wt 76, gut_dev 76, cosmetics 68, enemy 54, crt 44, mp 26, WOC 20, events 20, dcp 12, vdl_dev 5. Each suite is reachable only through `mod:command("<mod>_regression_test", ...)` (for example `general_tweaker_dev/scripts/mods/general_tweaker_dev/general_tweaker_dev.lua:390`). Results are printed with `mod:echo` and `mod:info`/`mod:warning` (same file, lines 392-412), which the repo's own rule 9 says are invisible when mod logging is off (`CLAUDE.md` non-negotiable 9). So the largest existing body of runtime assertions is neither started nor collected by any tool. The harness below runs all of them on every boot at zero extra authoring cost (section 5.3, "suite sweep").

**F3 (S1). The documented remote-automation recipe takes over the owner's desktop and conflicts with standing owner rules.** `DEVELOPMENT.md:1432-1465` prescribes `steam://rungameid/552500`, a UI Automation click on the launcher's PLAY button, `AttachThreadInput` + `SetForegroundWindow`, and `SendInput` scan codes to type chat commands. `send_keys.ps1:42-50` does `FindWindow` by title, `SetForegroundWindow`, then `SendKeys.SendWait`, which types into whatever window has focus if the focus change is refused (its own header comment says so, lines 6-8). Both steal focus and input. The owner's rules say verification runs must never reach his screen (memory `feedback_shcde_silent_background_verification`, `feedback_skyrim_launch_private_desktop_not_interactive`, `feedback_no_agent_gui_binary_execution`). Neither piece can be the basis of an unattended harness on PC-A.

**F4 (S1). A test run on the normal profile writes the owner's settings and save, and nothing isolates or restores them.** All mod settings live in one file, `%APPDATA%\Fatshark\Vermintide 2\user_settings.config` (1.57 MB; `mods` list at lines 70-1946, `mods_settings` at 1947-29094), saved on every state change (VMF `vmf_loader.lua:107-112`, `modules/core/settings.lua:18-33`). The local save is rewritten many times during boot by loadout-touching mods (`console-2026-08-19-22.44.16-*.log` has 68 `[Save] Saving save_data` lines in a 76 s session that never left the keep, 12 of them in lines 6370-6460). A harness that changes the mod list, mod options or loadouts for a test would change them for the owner. Section 5.2 isolates the profile; the fallback is hash-verified backup and restore.

**F5 (S2). The planned inbound channel (OS clipboard) is the wrong choice for unattended use.** The clipboard belongs to the window station, so it is the owner's clipboard even when the game runs on a private desktop. A REPL (a read-eval-print loop, a channel that accepts typed commands) that writes frames to it would overwrite whatever the owner copied, and the bridge would read whatever he copies. The memory note `project_vt2_agent_bridge` picks it "without focus stealing", which is true, but it is not without side effects. Three safer inbound channels exist and are proven in source: a key in `user_settings.config` read at boot, the command line, and HTTP to localhost through `Managers.curl` (section 4, rows 48-50).

**F6 (S2). The watcher binds to "newest log file", not to a run.** `agent-bridge-watch.ps1:50-65` picks the newest `console-*.log` by write time and restarts at offset 0 when a newer one appears. With two sessions, a second game instance, or a stale file touched later, it reads the wrong session. Frames carry no run identity. A run nonce and the process id in every line fix this (section 5.4).

**F7 (S2). Live-test cards are prose for a human; nothing turns them into runnable checks.** `docs/PLAYTEST_SCRIPT.md` (generated 2026-09-01) lists 258 checks: 48 keep menus, 20 keep world, 88 Adventure, 57 Chaos Wastes, 2 scoreboard, 21 boot/log, 22 co-op, with an estimated 373 minutes of solo play. Many cards already name an exact receipt line and a regression check (for example #1143: `[gt:1143] heal result=ok route=host` and `issue1143_dev_heal_command`), and `tools/github/check-lifecycle-cardinality.ps1` already validates card commands and receipt markers against source. The missing piece is a machine-readable block that says how to reach the state (section 5.5).

**F8 (S2). Project rules have no place for a harness verdict.** `CLAUDE.md` rule 10: never claim a runtime issue fixed until the user confirms in-game. Rule 13: `verify-fix` means human live testing, and status labels must not be invented. Without an owner decision, a harness PASS cannot close anything, so the backlog would not shrink even with a working harness. This needs one explicit policy change (section 9, decision D1).

**F9 (S2). Third-party mods in the owner's load list write to Steam Cloud, which a local profile copy does not isolate.** `Steam/userdata/250855163/552500/remotecache.vdf` lists exactly two cloud files, `loadout_manager_vt2.data` and `Peregrinaje-beta.data`, both written by third-party mods. The game's own save is not there, so it is local (consistent with `scripts/managers/save/save_manager.win32.lua:7-14` falling back to `SaveSystem`). A test profile must load only VMF, the driver and the mods under test, never the owner's full third-party list.

**F10 (S3). `docs/PLAYTEST_SCRIPT.md` is ten weeks old** (2026-09-01) against 329 open issues today. It is generated (`tools/verify/generate_playtest.ps1`), so this is a rerun, not a rewrite.

## 5. Proposed harness

### 5.1 Shape and rules

Three parts:
- **Orchestrator** (host side, PowerShell 7 plus one small C# helper): builds a throwaway profile, starts the game where the owner cannot see or feel it, watches it, collects evidence, proves nothing of the owner's was changed.
- **Driver** (one small in-game mod module): does nothing unless a test run is requested; then walks the game from boot to keep to level, runs test cases one by one, prints results, quits.
- **Test scripts** (one small Lua file per issue or per check): plain text in the repo, delivered to the driver at boot. No build, no upload per script.

Rules the design holds to:
1. Nothing reaches the owner's screen, keyboard, mouse, focus, clipboard, settings or saves on PC-A.
2. One game instance at a time. Never start if any Vermintide process exists. Never kill a process the harness did not start.
3. Every run has a random id (the nonce). Every evidence line carries it and the process id.
4. A case ends in exactly one of: PASS, FAIL, ERROR (script bug), TIMEOUT, SKIP (requirement not met), INCONCLUSIVE (precondition not reached, or the environment ended the run). Only FAIL says the product is wrong. This follows the owner's SHCDE rule that a resource-floor kill is INCOMPLETE, not FAIL.
5. Where possible the pass condition is read from engine state, not from the fixed code's own log line (memory `feedback_instruments_need_a_signal_the_fix_cannot_move`). The mod's receipt line is second evidence, not the oracle.
6. Only the coordinating session runs the game binary, serially (memory `feedback_no_agent_gui_binary_execution`). Sub-agents write scripts and read results.

### 5.2 Orchestrator: `tools/harness/run.ps1` (new)

Per run:

1. **Preflight, refuse unless all hold.** The owner's standing authorisation file exists (decision D3). No process named `vermintide2`, `vermintide2_dx12` or `vermintide2_launcher` exists (use PowerShell `Get-Process`, not Git Bash `tasklist`, per memory `reference_gitbash_tasklist_fi_trap`). Steam is running. `appmanifest_552500.acf` has `StateFlags 4` (installed, no update pending). Free RAM and commit headroom are above the floors. The harness lock (a named mutex plus a lock file holding session id and time) is free.
2. **Prepare the profile and the run folder.** Two harness-owned folders outside the repo, for example `%USERPROFILE%\.claude\vt2-harness\profile\` (kept between runs) and `...\vt2-harness\runs\<utc-stamp>-<nonce>\` (evidence for one run). The profile folder plays the part of the user profile: it holds `AppData\Roaming\Fatshark\Vermintide 2\` with (a) a `user_settings.config` regenerated for every run: low graphics, `screen_resolution = [1280 720]`, `fullscreen = false`, `borderless_fullscreen = false`, `max_fps = 30`, all volumes 0, the `mods` list holding only VMF, the mods the plan needs, and the driver last, `mods_settings` holding VMF logging-to-log plus every option value the plan asks for, and the key `vt2_test_plan`; (b) a copy of the owner's `save_data.sav`, refreshed before each run, so first-run flows (tutorial, gamma) do not trigger; (c) the shader cache the game builds there once (about 200 MB in the owner's profile), which is why the profile is kept and not recreated per run. Retention: keep the last 20 run folders and every run cited on an issue; a run folder is logs and small tables (a few MB). Check free space under the owner's storage rules before the first run.
3. **Record identity** in `run.json`: repo commit, plan hash, game build id and exe version, for each mod the Workshop folder's bundle hash and the version the plan expects.
4. **Launch** with the pattern in `CrusaderDEHandicap/scripts/HiddenDesktopProcess.cs:83-114`: create a private desktop that is never switched to, create the process suspended, put it in a job object with kill-on-close and no crash dialog, below-normal priority, then resume. Program: `<game>\binaries_dx12\vermintide2_dx12.exe` (or `binaries\vermintide2.exe`), working directory = that folder. Arguments: `-eac-untrusted --bundle-dir ../bundle --ini settings --silent-mode -skip-splash -vt2-test-run <nonce> -vt2-test-port <port>`. Environment for this child only: `USERPROFILE`, `APPDATA`, `LOCALAPPDATA` pointing into the harness profile folder, `SteamAppId=552500`. Nothing is written to the persistent environment.
5. **Watch every 250 ms.** Process alive. Any visible window of the job's processes on the owner's desktop ends the run at once (INCONCLUSIVE plus an incident note), as in `test_headless.ps1`. Tail the run's console log for boot markers and `[vt2t:<nonce>]` lines. Heartbeat older than 30 s in play, or 180 s in loading, means TIMEOUT. Per-case and whole-run time caps. A new `crash_dump-*.dmp` in the run profile means CRASH. Available RAM under 4 GB means stop, INCONCLUSIVE.
6. **Serve the live channel** on `127.0.0.1:<port>` (loopback only, so no firewall prompt): the driver fetches the next step and posts results and screenshot requests. The plan in `user_settings.config` is the fallback when the port is closed.
7. **End.** Wait for `RUN END` and for the process to exit (20 s), else close the job (which ends the process tree).
8. **Collect** into the run folder (moved out of the profile): console log, crash dump, the results table the driver saved into the run's `user_settings.config`, screenshots, the output of `tools/triage/triage-log.ps1 -LogFile <log>`. Write `summary.json` and `summary.md` (one row per case: issue, verdict, the assert lines, the matching log receipts).
9. **Prove isolation.** SHA-256 of the owner's real `user_settings.config`, `save_data.sav`, `launcher.config` and the Steam Cloud `remotecache.vdf` `ChangeNumber`, taken in step 1, must be unchanged. A difference is a harness defect and stops the queue.
10. **Release the lock.**

The orchestrator never comments on GitHub. The coordinating session reads `summary.md` and posts under the owner's policy (decision D1).

### 5.3 Driver: `_test_driver.lua` (new, dev-only)

**Gate.** The module returns before registering anything unless all three hold: `MODDED_REALM` is true; `Development.application_parameter["vt2-test-run"]` is a string; `Application.user_setting("vt2_test_plan")` exists and names the same nonce. For every normal player it is inert: no hooks, no commands, no per-frame work.

**At load, when armed** (this is before the first game state, row 21):
- `GameSettingsDevelopment.skip_start_screen = true` (row 6, bypass A).
- `Development._hardcoded_dev_params["skip-start-menu"] = true` (row 25).
- Print `[vt2t:<nonce>] RUN BEGIN ...` with `Application.process_id()`, the plan id, and one `MOD` line per loaded mod with its version.
- If the plan asks for it: `Window.has_focus = function() return true end` so local-hero input is not refused (row 36). Test profile only.

**State machine** (driven from `mod.update` and `mod.on_game_state_changed`):
`BOOT` -> `KEEP_READY` (in `StateIngame`, local hero unit alive, backend profiles loaded) -> run `boot` cases, then `keep` cases -> for each level group in the plan: `LOADING` (`Managers.mechanism:debug_load_level(level)`) -> `MISSION_READY` (hero and bots alive, inventory ready, as in `state_ingame_testify.lua:63-76, 223-231`) -> run that group's cases -> next group -> `QUIT` (`Boot.quit_game = true`).

**Case runner.** Each case is a coroutine started under `pcall` with its own timeout. Between cases the driver runs cleanup: destroy units the case spawned, restore options the case changed, heal and reposition the hero, clear AI if the plan says so (`TestifySnippets.disable_ai` lists the `script_data` switches: `scripts/tests/testify_snippets.lua:52-74`). A Lua error inside a case becomes verdict ERROR with the traceback; it never reaches the game's update loop.

**Built-in case: suite sweep.** In `KEEP_READY`, and again in the first mission, the driver calls every loaded mod's regression command through `get_mod("VMF").run_command("<id>_regression_test")` (row 23) while capturing that mod's `echo` output, and prints one `ASSERT` line per check. This runs all 831 existing checks (finding F2) on every boot with no new script.

**Helper API given to scripts** (`T`):

| Call | Meaning |
|---|---|
| `T.step(label)` | Names the next action; printed for the evidence trail. |
| `T.wait(seconds)`, `T.frames(n)` | Pause the case; the game keeps running. |
| `T.wait_until(fn, timeout, label)` | Pause until `fn()` is true; TIMEOUT verdict with the label if not. |
| `T.require(cond, label)` | Precondition. False ends the case as INCONCLUSIVE, not FAIL. |
| `T.expect(cond, label)`, `T.expect_eq(got, want, label)`, `T.expect_near(got, want, tol, label)` | Assertions. Each prints one `ASSERT` line. The case continues after a failure so all asserts report. |
| `T.cmd(name, ...)` | Run a mod chat command (row 23). |
| `T.expect_rt(mod_id, check_name)` | Assert that one named `_rt_register` check passed in the last suite sweep. |
| `T.local_hero()`, `T.first_bot_unit()`, `T.bots()` | Units, waiting until alive. |
| `T.ext(unit, system)` | `ScriptUnit.extension`, or INCONCLUSIVE if absent. |
| `T.set(mod_id, setting, value)` | Change a mod option for this case; restored in cleanup. |
| `T.spawn(breed, offset)`, `T.pickup(name, offset)` | Rows 31 and 32; tracked for cleanup. |
| `T.as_bot(bot_unit)` | Returns the bot's `PlayerBotInput` wrapper: `tap_attack`, `hold_attack`, `defend`, `fire`, `charge_shot`, `activate_ability`, `wield(slot)` (row 36). |
| `T.open_view(name, params)`, `T.widget(view, name)` | Rows 39 and 40. |
| `T.shot(label)` | Ask the orchestrator for a screenshot and wait for its reply (section 5.7). |
| `T.note(key, value)` | Free evidence line. |

### 5.4 Results protocol

One line per event, printed with engine `printf` (visible with mod logging off, per repo rule 9), all prefixed `[vt2t:<nonce>]`:

```
[vt2t:7f3a] RUN BEGIN plan=keep-and-military-01 driver=0.1.0 pid=41288 realm=modded
[vt2t:7f3a] MOD gt_dev 0.2.279-dev
[vt2t:7f3a] HB seq=17 state=StateIngame level=military case=gt-1143-host
[vt2t:7f3a] CASE BEGIN id=gt-1143-host issue=1143 seq=3
[vt2t:7f3a] STEP id=gt-1143-host n=3 label="run /heal"
[vt2t:7f3a] ASSERT id=gt-1143-host n=4 PASS label="full permanent health" got=150.00 want=150.00
[vt2t:7f3a] CASE END id=gt-1143-host verdict=PASS asserts=5 failed=0 t=14.2
[vt2t:7f3a] RUN END cases=12 pass=11 fail=1 error=0 timeout=0 skip=0 inconclusive=0
```

The same table is saved with `Application.set_user_setting("vt2_test_results", ...)` + `save_user_settings()` before quitting (row 46), and posted over HTTP when the port is open. The orchestrator accepts a verdict only when the log line, the saved table and (if used) the HTTP post agree, the `MOD` version matches the plan, and `RUN END` was seen. A run without `RUN END` marks every unfinished case INCONCLUSIVE.

### 5.5 Plans and scripts: how a weaker agent writes one

Location: `qa/runtime/<mod>/issue_<N>_<slug>.lua` in the repo. Each file returns one table. A plan is a JSON file listing script paths, the mod set, and option values; the orchestrator groups cases by `arena` and `level`, reads each script file, and embeds its text (hex-encoded, to be independent of the settings file's quoting rules) in `vt2_test_plan`. The driver decodes it and runs `loadstring` (row 24).

Procedure for one issue:
1. Open the newest `## CURRENT LIVE TEST` card. Copy the banner line, the numbered steps, the Expected paragraph.
2. Classify each step: reachable by a command or engine call (list in section 4.3), or needs eyes/ears, or needs a second player. If any step needs a second player, split: script the solo part, leave the rest `coop-required`.
3. Pick the arena: `boot` (log only), `keep`, `mission` + level key, `deus`.
4. For each "do" step write `T.step` + the call. For each "confirm" step write a `T.wait_until` and `T.expect` that reads engine state directly. Put every state the card assumes into `T.require`.
5. Copy every exact log receipt the card names into `host_expect_log`, and every "no error" clause into `host_forbid_log`.
6. Run `luacheck` and the offline loader test (a plain-Lua stub of `T` that executes the file's top level and checks the table shape; it cannot check engine calls).
7. Add the case to a plan, run the harness, attach `summary.md` to the issue under the D1 policy.

### 5.6 Worked example: issue #1143 "Dev heal command" (General Tweaker, `verify-fix`, `coop-required`)

Newest card (`issues/open/1143.md`, comment 2026-11-06, official stream): banner `[gt:LOAD] v0.2.180`; enable official Tweaker: General only. Steps: (1) host a private Adventure game; (2) damage the host and wound them by downing and reviving, then the host runs `/heal`; (3) confirm full permanent health and cleared wounded state; (4-5) the same on the client; (6) both run `/gt_regression_test`. Expected: both heroes reach full permanent health with wounds cleared, the result rows name their route and report `wounded_after=false`, the developer-heal regression passes, no custom network event or direct health-state error.

Split: steps 1-3 and the host half of step 6 are class R. Steps 4-5 need a second peer (class C). The script below closes the host half and leaves the client half in the co-op queue.

Source facts used (repo): `/heal` is registered at `general_tweaker/scripts/mods/general_tweaker/_gt_dev_heal.lua:235` (mod id `gt`, `MOD_VERSION = "0.2.180"` at `general_tweaker.lua:3`); its receipt line `[gt:1143] heal result=... route=... wounded_after=...` is built at `:87-103`; the regression check `issue1143_dev_heal_command` is at `:240-262`. The dev stream has the same file at the same lines (`general_tweaker_dev/.../_gt_dev_heal.lua:235, 240`), so the earlier dev card (2026-08-13, `v0.2.279-dev`) uses the same script with `mods = { "gt_dev" }`. The stable tree has no `/down` command (only the dev tree does, `general_tweaker_dev/.../_gt_level_control.lua:587`), so the script downs the hero with the engine call instead.

Engine facts used: `StatusUtils.set_knocked_down_network` and `set_revived_network` (`scripts/helpers/status_utils.lua:21-34, 36-56`, host only); `GenericStatusExtension.is_knocked_down`, `is_disabled`, `is_wounded` (`scripts/unit_extensions/generic/generic_status_extension.lua:2091, 2158, 2222`); `PlayerUnitHealthExtension.current_permanent_health`, `get_max_health` (`scripts/unit_extensions/default_player_unit/player_unit_health_extension.lua:1073, 1107`).

```lua
-- qa/runtime/gt/issue_1143_dev_heal_host.lua
return {
    id      = "gt-1143-host",
    issue   = 1143,
    covers  = "card steps 1-3 and the host half of step 6; the client route stays coop-required",
    arena   = "mission",
    level   = "military",
    bots    = true,
    mods    = { "gt" },                                   -- VMF ids that must be loaded (card: official General only)
    banner  = { marker = "[gt:LOAD]", exact = "0.2.180" }, -- from the card's Build/banner line
    timeout = 90,

    -- Checked by the orchestrator in the console log after the run.
    host_expect_log = {
        { pattern = "%[gt:1143%] heal result=ok route=host .*wounded_after=false", count = 1 },
    },
    host_forbid_log = {
        "%[gt:1143%] heal result=error",
        "%[gt:1143%] heal result=timeout",
    },

    run = function(T)
        local unit   = T.local_hero()
        local health = T.ext(unit, "health_system")
        local status = T.ext(unit, "status_system")

        T.step("down the host (card step 2)")
        StatusUtils.set_knocked_down_network(unit, true)
        T.wait_until(function() return status:is_knocked_down() end, 10, "host is knocked down")

        T.step("revive the host (card step 2)")
        StatusUtils.set_revived_network(unit, true, T.first_bot_unit())
        T.wait_until(function()
            return not status:is_knocked_down() and not status:is_disabled()
        end, 20, "host is living and controllable")

        -- States the card assumes. If they do not hold, the case is INCONCLUSIVE, not FAIL.
        T.require(status:is_wounded(), "host is wounded before /heal")
        T.require(health:current_permanent_health() < health:get_max_health(),
                  "host is below full permanent health before /heal")

        T.step("run /heal (card step 2)")
        T.cmd("heal")

        -- Card step 3. Oracle = engine state, not the mod's own receipt line.
        T.wait_until(function()
            return health:current_permanent_health() >= health:get_max_health() - 0.01
               and not status:is_wounded()
        end, 10, "full permanent health and wound cleared")
        T.expect_near(health:current_permanent_health(), health:get_max_health(), 0.01,
                      "full permanent health")
        T.expect(not status:is_wounded(), "wound cleared")

        -- Card step 6, host half.
        T.expect_rt("gt", "issue1143_dev_heal_command")
    end,
}
```

What the run produces for the issue: verdict PASS or FAIL for the host route, the `ASSERT` lines, the one matching `[gt:1143]` receipt line, the `[gt:LOAD]` version, the run id and the log path. The card's "ordinary healing conditions" clause is met by loading only VMF, General and the driver, with no heal-blocking mutator. The script has not been run; the down-and-revive steps are the part most likely to need adjustment at E7, and `T.require` reports that as INCONCLUSIVE instead of a false FAIL. The client route remains for a two-machine run (section 5.8) or a live pair.

Side observation for the lead: the stable tree lacking `/down` while the dev tree has it is dev-to-stable drift in the test-verb set. Scripts for official-stream cards should use engine calls, not dev-only commands.

### 5.7 Screenshot channel

Purpose: turn part of class V into "AI-judged with evidence". Flow: the script calls `T.shot("kruber_keep_preview")`; the driver prints `[vt2t:<nonce>] SHOT REQ id=... label=...` (and posts it over HTTP), then waits; the orchestrator captures the game window, saves `shots\<case>-<label>.png`, answers; the script goes on. After the run a vision-capable agent gets each image with the card's Expected sentence and must answer PASS, FAIL or CANNOT-TELL with a reason. CANNOT-TELL goes to a human.

Capture options, in order of preference: an engine call if E3 finds one (row 59); window capture on the private desktop (row 60, E6); the game on a virtual display or on PC-B's own desktop (row 61).

Rules: fixed 1280x720; the script must place the camera or open the UI view itself so the picture is repeatable; one still per check, or a short strip of stills for a pose. Never a redraw or animation loop on PC-A (memory `feedback_no_dwm_stress_probes`).

Limits, stated plainly: an AI can judge presence or absence (icon shown or placeholder, text clipped, item missing, widget overlapping), gross pose errors in a still, wrong hand, missing mesh. It cannot judge motion quality, timing, sound, voice lines, "feel", or small colour and glow differences. Those stay human. An AI verdict on a picture is evidence for the owner's policy to weigh, not a measurement.

### 5.8 Co-op extension

Hard facts: retail is Steam-only (row 62); two instances need two Steam accounts that both own the game (row 63); so real co-op needs PC-A plus PC-B (or PC-A plus RainReligion). Whether PC-B has its own account with the game is [unverified] (decision D4).

Two-machine run:
1. Each machine runs the same orchestrator with a role (`host` or `client`). Both drivers poll one control endpoint (the host machine's orchestrator, reached over the tailnet), or each polls its local orchestrator and the two orchestrators exchange steps over SSH. The second form needs no firewall change.
2. Host: boot to keep, set the game private (row 66), print its lobby id. Client: boot to keep, find the host lobby, `Managers.matchmaking:request_join_lobby(lobby, { friend_join = true })` (row 64).
3. Steps are tagged with a role and a barrier name. A barrier is a named point both sides must reach before either continues (for example `both_in_mission`). Example for #1143: host runs the host script; at barrier `host_done` the client runs the same steps with `route=client` expected; each side asserts on its own log.
4. Husk checks (how another player's hero appears on your machine): the client asserts on the host's hero unit as it exists on the client: which units are attached, item and skin names, animation state names, no error lines. That is state, not looks.

What one machine can cover without a second peer:
- Wire-safety of mod data: every mod-added `NetworkLookup` entry maps both ways and stays inside the engine's limits. Pure table checks; several mods already do this in their regression suites.
- RPC packing: send each mod RPC to self through the real queue (`network_transmit.lua:99`, `mod_manager.lua:593-595`) and assert the handler receives equal arguments, including strings near the 500-character cap (`docs/VMF_RECIPES.md`).
- Host-side logic for a "remote" player using bots as stand-ins.
Not covered on one machine: husk extension classes (they are separate classes, `CLAUDE.md` "Self-owned vs husk extension classes"), hot-join sync order, anything that depends on real latency or on two different mod versions. Those are class C and need two machines or live players.

Batching the backlog. `docs/PLAYTEST_SCRIPT.md` (2026-09-01) sorted 258 cards into 48 keep-menu, 20 keep-world, 88 Adventure, 57 Chaos Wastes, 2 scoreboard, 21 boot/log, 22 co-op. If every solo card were class R (they are not; the D-series auditors are classifying them), grouping 15 cases per boot gives about 5 keep boots, 6 Adventure boots, 4 CW boots and 1 boot-only run: 16 boots, roughly 45 to 60 minutes of machine time. Cases that need a mod option that only applies at load need their own boot; allow 10 to 20 extra boots. So a full R-class pass is a two-hour unattended job, and a single-issue recheck after a fix is about three minutes.

Keep groups small (15 or fewer) and independent: one case's leftovers must not decide the next case's verdict. A FAIL is re-run once alone in a fresh boot before it is reported; if it passes alone, it is reported as "order-dependent", which is itself a finding.

## 8. Honest limits and the fallback

Cannot be automated with this design:
- How anything looks in motion: animation quality, timing, blending, first-person feel, camera feel.
- Sound and voice: that a sound is the right one, at the right moment, at the right volume.
- Fine visual judgment: glow, colour, material response, small clipping.
- Real-network behaviour: latency, packet loss, hot-join races, mismatched mod versions between real peers, more than two peers.
- Official-realm behaviour: the driver refuses to arm there, and unsanctioned mods do not load there.
- Anything that needs the Steam overlay, the launcher, Workshop subscription state, or a Steam restart (the stale-version trap in memory `reference_vt2_stale_version_restart_trap` is outside the game process).
- Bugs that only appear after long sessions or with the owner's full third-party mod list, unless a plan loads that list on purpose (and then F9 applies).

Partly automatable: "the right mesh, icon, text is shown" (state assertions on unit names, texture names and widget contents, plus a still for AI review); "no crash and no error line when doing X" (fully automatable and worth a lot: many cards end with "no errors, no crash").

What a PASS means: the scripted steps produced the stated engine state in a lean profile on this build. It does not mean the feature is pleasant, complete, or correct in a full stack. Report it as "auto-verified (R)", never as "works".

Fallback for the rest: live players. Give RainReligion and the owner a short list that contains only class V and C items, with the harness's stills and state dumps attached so the human only judges what needs judging. The existing `tools/verify/generate_playtest.ps1` can produce that list once cards carry the class.
