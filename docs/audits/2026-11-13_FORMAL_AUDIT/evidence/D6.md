# D6: closed-issue audit (613 closed issues)

Auditor D6, 2026-11-13. Repo state audited: `origin/master` = `master` = `592253d1`. No repo writes, no GitHub writes, no game launch.
Ledger: `findings/D6_ledger.tsv` (613 rows, 10 columns). Scripts and raw data: `scripts/D6_*.py`, `scripts/D6_out/`.

## 0. Headline

- The premise "PRs with `Fixes #N` closed issues without verification" is mostly wrong. Of 613 final closes, 586 were manual (`gh issue close` or web UI, all under the single `Ensrick` account), 20 were commit-keyword auto-closes and 7 were PR-merge auto-closes. All 27 auto-closes happened between 2026-07-02 and 2026-07-19; none since the guard landed on 2026-07-22 (`5ea3d48b`, `.github/workflows/pr-autoclose-audit.yml`, `pr-autoclose-authorization.yml`).
- Of 384 closed-COMPLETED runtime issues, 296 (77%) carry a human in-game confirmation (class A), 11 real-session log evidence (B), 31 static evidence only (C), 35 nothing (D), 11 were not really fixes (not-a-bug, superseded, feature removed).
- The real weaknesses are narrower than "hundreds of unverified closes": (1) one 0-critical crash closed against the owner's last verdict (#406); (2) 66 closes with no runtime evidence, 18 of them crash-class; (3) 102 of the 296 class-A closes rest only on an agent's sentence that the user confirmed; (4) Chaos Wastes and General Tweaker fixes mostly exist only in the `_dev` tree; (5) 25 closed runtime issues and 42 not-planned/duplicate closures have an OPEN issue tracking the same or regressed symptom.

| Fix-on-master | (a) automated: identifiers ADDED by commits citing `#N` on master, tested for survival in master `.lua` (`scripts/D6_fixcheck_all.py`); (b) manual grep with `path:line` | (a) all 613, conclusive for 188 runtime rows; (b) 45 crash/critical issues |
| Open-issue back-references | regex over all 329 open threads for closed numbers plus regression wording, then manual review of the 100 flagged pairs | 369 closed issues are referenced by an open issue |

Human versus agent text: every comment and every close is by `Ensrick`. The owner's own typing is recognisable (short, no markdown, no version strings, attachments, e.g. "Working!", "Seems to be fixed.", "fixed. 9 tests failed."). The `Fixed` label was applied one issue at a time (168 of 222 `Fixed` label events are isolated in time), usually seconds before such a comment, so it is the owner's web-UI verdict. The pre-scored `has_confirmation_text` column misses both and must not be used.

Not done / limits: no in-game check of anything; 146 script-class-A threads were not read; "read" mostly means the dossier, not the whole thread; timelines of currently OPEN issues were not fetched, so auto-closes that were reopened and are still open are not counted; `fix_still_on_master=yes` from the automated check means "the identifiers the fix commit added still exist", not "the fix works".

## 8. "Closed but never runtime-verified": size and handling

- Hard core: 66 closed runtime issues with class C or D (estimate 66 to 78), 18 crash-class, 9 with priority 0/1.
- Soft: 102 class-A closes with agent-only attribution; 11 class-B.
- Existing cover: master has 846 distinct `_rt_register` runtime checks, 434 with an issue number in the name. 119 of the 384 closed runtime issues have a number-named check, but only 4 of the 66 C/D issues and 1 of the 56 REVERIFY rows do. [unverified] whether each named check really asserts the issue's invariant; the match is by name.

Recommendation (do not reopen in bulk):
1. Reopen #406 only. Add the 25 + 42 cross-links (section 5.3) as comments on the open issues so the closed numbers are searchable from the live tracker.
2. Build one regression registry: a row per closed runtime issue with `issue, mod, verification class (U/S/R/V/C), check id, last pass build, last pass date`. Seed it from the ledger. A closed issue is "verified" only while its row has a passing check on the current build.
3. Fill the registry in this order: (a) the 18 crash-class C/D rows (most are nil-guards: U or R); (b) the remaining 48 C/D rows; (c) the 9 auto-closed unverified rows; (d) the 102 agent-attributed A rows; (e) everything else as a by-product of the existing checks.
4. Run the registry inside the in-game harness on every dev build; a failing row automatically files or reopens the issue with the log. Class V/C rows go to live players as a short checklist generated from the registry.
5. Gate the stable promotion on the registry for that mod (fixes present in the stable tree and passing), which closes the dev-only gap in section 6.
6. Tracker hygiene, deterministic and scriptable: strip waiting lifecycle labels from closed issues; require a closing comment; set `state_reason` correctly (11 "completed" rows are not fixes: #3, #21, #62, #66, #104, #311, #396, #410, #484, #496, #608; plus #534 closed "completed" on "no change").
