### 2.4 Lifecycle model
VMF calls one function per event per mod (`VMF/core/events.lua:10-15`, a single `safe_call_nr` around `mod[event_name]`). gut multiplexes by capture-prev chaining: `local prev = mod.update; mod.update = function(dt) if prev then prev(dt) end ... end`. Measured chain sites: `mod.update` 11 files, `mod.on_setting_changed` 10, `mod.on_game_state_changed` 11, `mod.on_disabled` 7, `mod.on_all_mods_loaded` 3, `mod.on_user_left` 2. Every `mod.update` site calls `prev` first and unguarded (e.g. `_gut_freecam.lua:342-343`, `_gut_camera.lua:416-417`, `_gut_cutscenes.lua:717-718`, `_hide_ui.lua:249-250`). Only the exit-snapshot wrapper isolates its predecessor (`_gut_loadout_lifecycle_owner.lua` `_previous`).

### 2.8 Assessment
`gut_dev` is not one design. It is roughly fifteen unrelated features that share a mod id: a backend persistence layer, a camera suite migrated from General Tweaker, a second settings UI for every Tweaker mod, a compendium, scoreboard repairs with their own network transport, HUD editing, a partial fork of another author's mod, and a set of crash guards for third-party mods. Individual recent modules are carefully written (pure policy cores, bounded diagnostics, explicit dependency tables, real offline tests for the policy halves). The whole is accreted: the entry file is a manifest of 60 loads ordered by lifecycle-chain accident, 144 distinct issue numbers are cited in code comments, and the riskiest module (`_gut_native_loadouts.lua`, 2,130 lines) is a monolith in which hooks, state, commands and diagnostics share file-local upvalues, so its behaviour cannot be executed outside the game. The repeated loadout bugs (#375, #387, #402, #353, #354, #954, #1033) are the visible cost: each was fixed by adding another writer, another marker flag or another trace to the same shared table rather than by giving the table an owner.

### A7-F01 | S1 (S0 if a tester log confirms) | state-lifecycle | The exit-time snapshot can permanently replace a stored modded item id with the official fallback id
Evidence:
- The store's design rule is "never destructively sanitize; an id that does not resolve right now is served from official for this read only and the store is left intact to self-heal" (`_gut_native_loadouts.lua:70-84`, `:788-794`). The read hook implements that: on `RESOLVE_NO` it returns `_official_gear_fallback(...)` (`:813-821`, fallback at `:596-613`).
- `M.exit_snapshot` (`:1576-1640`) runs for EVERY career in the store on three edges (`exit StateIngame`, `enter StateTitleScreen`, `on_unload`; `_gut_loadout_lifecycle_owner.lua` `bind_snapshot_edges`). Its "live" value is `BackendUtils.get_loadout_item_id(career, slot, false)` (`:1541`), which is the items-interface cache built from `backend_mirror:get_character_data` (`VT2SRC/.../backend_interface_item_playfab.lua:108-124`, `:447-452`, `:511-523`), which is gut's own read hook. So when the stored id X did not resolve at the last interface refresh, "live" is already the official fallback O.
- `_live_slot_value` then accepts O because O resolves (`:1546`), the pure diff treats any non-nil live value that differs from the store as a divergence to write (`_gut_exit_snapshot_core.lua:61`), and the caller overwrites the selected row and persists (`_gut_native_loadouts.lua:1599-1603`).
- Deterministic static scenario: play one session with the providing mod of X disabled (CWV, cim, LA, a WT cross-character unlock). The first level transition fires `ingame_exit`, and every career whose selected row holds X gets O written over it. A second scenario is a late-registering id that is not followed by an interface dirtify before an exit edge [unverified whether providers dirtify on registration].
- The offline test for the snapshot (`qa/lua/tests/test_gut_exit_snapshot.lua`) exercises `diff_row` with hand-made "live" tables, so it cannot see that the live value is contaminated by the fallback.

Impact: static evidence suggests silent loss of modded weapons/jewelry from saved loadouts across restarts, on all careers at once. This is the symptom family of #354 (WT weapon disappears after restart), #353 (LA cosmetics not persisted) and the residual of #375; the backstop added to cure them is itself a writer that violates the store's central rule.

Runtime confirmation that needs no eyes: in any tester log, a `[gut:persist] edge=<e> career=<c> idx=<i> reconciled=<n> slots -> store` line for a career/slot that earlier printed `[gut_dev:NATIVE_LOADOUTS] #387 gear-read career=<c> slot=<s> ... source=official-fallback-resolve-no`, in a session with no `BU equip capture` line for that slot.

Recommendation: the snapshot must never overwrite a non-nil stored gear id unless the stored id itself resolves `RESOLVE_YES` right now (then the live value really came from another writer). Simplest correct rule: skip the slot when `_resolve_item_raw(stored_id) ~= RESOLVE_YES`. Add the unit test first (work item 2).

### A7-F02 | S1 | architecture | The loadout mirror has one persistence call but no state owner; the load-bearing module cannot be executed offline
Evidence:
- Nine mutation paths in two files write the same closure-held table (table in 2.3), each with its own row-index rule: `optional_loadout_index or entry.selected_index` (`_gut_native_loadouts.lua:927`, `:1054`), always `selected_index` (`:683`), official index for the overlay (`:238-242`), live re-read (`:1599`), designation index (`_gut_bot_loadout_snapshot.lua:491-493`).
- One equip writes the store twice by two routes: the outer `BackendUtils.set_loadout_item` capture (`:699-713`, value canonicalized by `_bu_canonical_value`) and then, through the wrapped vanilla call, the mirror `set_character_data` hook (`:894-931`, value as the interface passed it). They agree only while both canonicalizations stay identical.
- Entry shape is implicit and versioned by ad hoc flags on each career entry: `_seeded`, `_slot_integrity_v2` (`:389`, `:397-398`, `:426-427`), `_bot_designation_snapshot_v2` (`_gut_bot_loadout_snapshot.lua:8`). The bare entry literal `{ selected_index = 1, bot_index = nil, loadouts = {} }` is created in six places (`:682`, `:924`, `:949`, `:972`, `:1053`, `_gut_bot_loadout_snapshot.lua:487`).
- `get_career_loadouts` returns the live store array by reference (`:870`); a caller that mutates the returned rows mutates the store without `_persist`.
- The recursion hazard (an interface method called from inside a mirror read re-enters `_refresh`, the 1 GiB heap incident) is prevented only by comment discipline ("RAW FIELD READS ONLY", `:436-467`); the hook has no re-entrancy guard.
- No offline test loads `_gut_native_loadouts.lua`. `test_gut_native_loadout_policy.lua` executes the pure policy modules and asserts facts about the hook file by `source:find(...)` (its lines 242-263, 305-334, 763, 800, 892, 911).
- The in-game check `native_loadouts_official_write_chokepoint` (`:1870-1888`) compares wanted method names with `M.HOOK_TARGETS`, a list the module writes itself; it does not ask whether a hook is installed.

Impact: every loadout issue in the bucket (#375, #402, #353, #354, #954, #1033, #231, and closed #387/#372) lands in this module; three are labelled `0-critical`. Each fix has been another writer, flag or trace, and no fix can be proven without a human because the state machine only runs in the game. A weaker agent editing this file cannot know which of nine writers it affects.

Recommendation: extract a pure `LoadoutStore` (no `mod`, no `Managers`) as the only code that touches the table: `ensure_seeded(career, official_rows, selected)`, `get(career, slot, index)`, `set(career, slot, value, index)`, `select`, `add`, `delete`, `set_bot_snapshot`, `reset`, `reconcile(career, live_row, resolver)`, `export/import` with one integer `schema` and one migration function replacing the three marker flags. Hooks become adapters that translate vanilla arguments to store calls. Add a re-entrancy counter to the read hook that falls through to `func` when re-entered. Work item 1.

### A7-F04 | S1 | crash-safety | Lifecycle callbacks are capture-prev chains with no per-handler isolation; one throw disables every later-loaded handler for that event, including safety cleanup
Evidence: chain counts in 2.4. VMF wraps the whole event in one protected call (`VMF/core/events.lua:10-15`), so a throw anywhere aborts the rest of the chain for that dispatch, every frame in the case of `update`. Handlers that must run to keep the game controllable are outer links: the freecam force-exit on state change (`_gut_freecam.lua:433-452`; if skipped, `_freecam_active` stays true and the `PlayerInputExtension.is_input_blocked` hook at `:395-407` keeps returning true in the next level), the third-person reset (`_gut_camera.lua` state-change chain), the cutscene deferred-skip processor (`_gut_cutscenes.lua:717`). The innermost `on_game_state_changed` calls `mod._gut_apply_keep_menus()` unguarded (`gui_tweaker_dev.lua:655-657`). The only in-game proof, `lifecycle_chain_integrity` (`gui_tweaker_dev.lua:214-245`), shows the `on_setting_changed` chain is linked; it does not show that a chain survives an error and does not cover `update` or `on_game_state_changed`. ENGINE_SURFACE records the same defect for the HideBuffs update list as "backlog P1".

Impact: a nil dereference in any feature tick silently turns off unrelated features (camera, cutscene skip, HUD-hide enforcement, scoreboard sync, reset reconcile) and can leave the player input-locked. The owner runs with mod logging off, so the VMF error line is not seen.

Recommendation: one dispatcher module owning `mod.update`, `mod.on_setting_changed`, `mod.on_game_state_changed`, `mod.on_disabled`, `mod.on_unload`, `mod.on_all_mods_loaded`. Features call `Lifecycle.on(event, name, fn)`; each handler runs under `pcall` with one bounded `printf("[gut:LIFECYCLE] event=%s handler=%s error=%s")` per handler per session. Work item 4.
