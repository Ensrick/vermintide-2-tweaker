## 2. Architecture as built

### 2.0 The engine fact that changes the risk picture for all three mods

In game 6.13.0 the modded realm is no longer a separate, empty backend:
- `MODDED_REALM` is a native global set from the launch parameter (`Vermintide-2-Source-Code/foundation/scripts/util/application_parameter.lua:150-152`).
- It sets `GameSettingsDevelopment.read_only_backend = true` and `achievements_disabled = true` (`Vermintide-2-Source-Code/scripts/settings/game_settings_development.lua:49-52`); both realms use `BackendSettings.dev_steam_playfab` (`:55`), and the client only stamps `realm = "modded"` metadata (`Vermintide-2-Source-Code/scripts/managers/backend_playfab/backend_manager_playfab.lua:69`).
- `PlayFabMirrorBase._commit_internal` skips statistics, weave data and pose skins when read-only (`Vermintide-2-Source-Code/scripts/managers/backend_playfab/playfab_mirror_base.lua:2826, 2839, 2857`) but still builds and sends `updateHeroAttributes` (career loadouts, talents, selected career; `:2875-2909`) and user data (`:2911`). Whether the server rejects a modded-realm write is not visible in client source [unverified].
- A loadout id that is not in `_inventory_items` at sign-in is a "broken slot" and is replaced with starting gear (`playfab_mirror_base.lua:1579-1721`, `:3277`; restated in `docs/engine/11_backend_and_loadouts.md` section 4).

Consequence: the mirror the mods mutate in the modded realm is the player's live official account mirror, and any modded backend id written into a career loadout can reach the official account. Open issue #402 (0-critical, reopened) records exactly this symptom. The mods cannot load in the official realm (`Mod.start_scan(not MODDED_REALM)`, `Vermintide-2-Source-Code/scripts/managers/mod/mod_manager.lua:273`), so the exposure is entirely "what a modded session leaves behind".

### 2.1 crafting_in_modded_dev (`cim_dev`)

Entry: `crafting_in_modded_dev.mod` -> `crafting_in_modded_dev.lua`. The entry is a load manifest plus four inline hooks; the rest is 60+ modules loaded with `mod:dofile` in a fixed order (order is load-bearing: comments at `crafting_in_modded_dev.lua:76-78, 113-118, 141-143`). Each module is either a pure policy table (`_cim_*_policy.lua`, `_cim_synthetic_item_contract.lua`) or an "owner" installer `return function(context)` that receives accessors for entry-local mutable state.

Load order (abridged): realm authority -> preview policy -> `_cim_bootstrap_runtime` (version banner, regression registry) -> CW trait residency -> `modded_rarities` -> synthetic item contract + temper transaction -> trait/property policies -> illusion apply -> `standard_forge` -> icon/residency policies -> `illusion_swap` -> `saveweapon_import` -> accessory panel -> Ranald's Gift browser -> `cim_debug` -> inventory filter, mission forge safety, keep forge interaction, dump commands, tab preview -> bulk cleanup core -> favorite persistence -> `_cim_forge_state_owner` -> `_cim_loadout_wire_owner` -> `_cim_modded_loadout_owner` -> Athanor hooks (entry) -> preview/picker/accessory/UI owners -> weave economy -> immutable relic UI -> weave loadout owner -> commit hook -> weapon list hook -> mirror injection -> direct craft owner -> Ranald import -> temper runtime -> seed owner -> command owner -> three regression modules.

State ownership:
- Crafted-item registry `forged_weapons` (backend id -> record): owned by `_cim_forge_state_owner.lua`; persisted with `mod:set("forged_weapons", ...)` (`:65-91`), re-read and re-injected on every `BackendManagerPlayFab._create_interfaces` (`:505-511`).
- `_custom_forge_active` (Athanor open) is an entry local (`crafting_in_modded_dev.lua:339`); `mod._cim_standard_forge_active` (keep bench open) is a field set by window `on_enter`/`on_exit` hooks (`standard_forge.lua:222-244`). Both gate the single `BackendManagerPlayFab.commit` hook (`crafting_in_modded_dev.lua:732-735`).
- Persisted settings keys with no widget: `forged_weapons`, `modded_loadout`, `persist_modded_loadouts` (forced false at load, `_cim_loadout_wire_owner.lua:76`), `vanilla_skin_overrides_by_backend_id` (`illusion_swap.lua:165`), `allow_in_mission` (written by gui_tweaker, `gui_tweaker_dev/scripts/mods/gui_tweaker_dev/gui_tweaker_dev.lua:615-624`).

Hook surface by class (top): `BackendInterfaceWeavesPlayFab` 30, `HeroWindowWeaveProperties` 13, `HeroWindowWeaveForgeWeapons` 10, `HeroWindowItemCustomization` 9, `HeroViewStateWeaveForge` 6, `HeroView` 4, `BackendInterfaceItemPlayfab` 4, `BackendInterfaceCraftingPlayfab` 4, `LootItemUnitPreviewer` 4, plus `BackendManagerPlayFab.commit`/`_create_interfaces`, `PlayFabRequestQueue.enqueue`, `PlayerManager.rpc_sync_loadout_slot`, `LoadoutUtils.sync_loadout_slot`, `_G.Localize`, `DeusRunController.get_weapon_pool`. Full list: `scripts\A5_cim_dev_hooks.txt`.
Doc disagreement: root `CLAUDE.md` says "106 hook sites", `crafting_in_modded_dev/ENGINE_SURFACE.md:155` says "139 hook sites + 1 VMF RPC channel", the source has 122 registration statements (several inside loops over 2-4 classes).

Vanilla tables mutated: `NetworkLookup.rarities` (appends `modded`, `promo`; `modded_rarities.lua:120-127`, `crafting_in_modded_dev.lua:275-281`), `RaritySettings`, `RarityIndex`, `ORDER_RARITY`, `UISettings.item_rarity_*`, `Colors.color_definitions` (`modded_rarities.lua:60-137`), `ItemMasterList[key].mechanisms = nil` with no restore (`crafting_in_modded_dev.lua:906-922`), `InventorySettings.inventory_loadout_access_supported_game_modes` (scoped, restored; `:546-577`), `InteractionDefinitions.forge_access.client.can_interact` (table replacement), weave trait/property category arrays (restored on forge exit, `:581-593`).

RPC: one VMF channel `cim_modded_slot(schema, peer_id, local_player_id, slot_name, is_modded)` (`_cim_loadout_wire_owner.lua:95-98, 119-131`), schema 1, mismatches dropped.

Cross-mod: calls `get_mod("mp")` (realm fallback and EAC bracket, via the shared lib), `character_weapon_variants` (icons, preview, temper source), `cosmetics_tweaker` (glow notice, tab preview), `WOC` (tab preview, relic gate), `MoreItemsLibrary` (legacy injection path). Consumed by cosmetics_tweaker, character_weapon_variants, weapons_of_chaos and gui_tweaker via `get_mod("cim_dev") or get_mod("cim")`.

Assessment: the decomposition is real and recent. Pure policy modules with injected dependencies are a good base and most have host tests. But the product is still an accretion: the Athanor is a vanilla Weaves screen held open by about 60 hooks that fake an economy and suppress keep-only resources, the keep bench is a second parallel implementation, and a third dormant subsystem (loadout persistence, about 700 lines) stays wired "so the regression sandbox can exercise it". Correctness depends on three session flags, load order, and transaction armour whose strictness has itself caused a user-visible loss (F04). There is no isolation of career-loadout writes (F01).

### 2.2 modded_progression (`mp`)

Entry `modded_progression.lua` (1,496 lines) loads 17 modules: realm authority, `mp_dailies` (local daily roster + Silver Shilling ledger), Emporium policy/UI, fresh-profile state/runtime, daily UI/reroll runtimes, calendar login guard, quest boundary, hook-target self check, loot diagnostics.

State (all VMF settings under `mods_settings.mp`): `schema_version`, `seeded`, `currency`, `unlocks`, `inventory` (`modded_progression.lua:177-265`), `mp_daily_v2` (`mp_dailies.lua:14`), `mp_profile_v1` (fresh profile), loot-diagnostic ledger. Runtime-only: Emporium overlay records (`modded_progression.lua:566`).

Hook surface: 75 `mod:hook`, of which 22 are a class-wide route over `BackendInterfaceItemPlayfab` for the Fresh profile (`_mp_fresh_profile_runtime.lua:556-577`), 11 on `BackendInterfaceQuestsPlayfab`, 5 on `BackendInterfacePeddlerPlayFab`, 14 on store/achievement UI classes, 8 diagnostic observers (`_mp_loot_diag_runtime.lua`). No RPC (single-player by design).

Writes to the live native mirror: Emporium overlay only (`modded_progression.lua:589-624`: `add_unlocked_weapon_skin`, `add_unlocked_cosmetic`, `add_unlocked_weapon_pose`, `add_item(..., true, true)`), tracked for reversal. The Fresh profile route never writes the mirror (`_mp_fresh_profile_runtime.lua:146-156`).

Cross-mod: exports `mod.is_modded_realm`, `mod.with_eac_off`, `mod.is_eac_window` (consumed through `_lib_modded_realm_authority.lua` copies in cim, cim_dev, cosmetics_tweaker, general_tweaker(_dev)). The economy API (`is_unlocked`, `grant_item`, `spend`, `credit`, `has_currency`, `mark_unlocked`, `get_currency`) has zero callers outside mp (repo-wide grep).

Assessment: honest scaffolding with one small working loop (local dailies -> Silver Shillings -> plain-SM Emporium cosmetics) and one isolated slice (Fresh items/loadouts). The original plan (flip the EAC flag at about ten UI gates and overlay the mirror) was invalidated by game 6.12, which the in-code comments acknowledge; the retained brackets are now inert against the current game (F10). Roughly a third of the code is diagnostics for features that do not exist yet.

### 2.3 career_tweaker (`crt`)

Entry `career_tweaker.lua` (1,213 lines). Load order: pure policies (damage classification, Focused Spirit, wire policy/catalog, buff icons, network lookup) -> `career_tweaker_balance` (pre-registers 34 `crt_*` buff names, builds the 75-entry catalog, installs balance hooks) -> `career_tweaker_tourney` -> rework-master policy -> umbrella audit -> Foot Knight -> armor/overcharge -> OE cooldown -> mutex -> talent-menu guard -> diagnostics -> regression. Most loads are `pcall`-wrapped with stub fallbacks (`career_tweaker.lua:131-135, 164-168, 174-207`).

How an edit is defined: a catalog row keyed by setting id with `character`, `career`, `patches = { {buff=..., field=..., value=...} }` and optional `custom_apply(saved)` / `custom_restore(saved)` closures (`_crt_balance_catalog_early.lua:27-90`). How it is applied: one apply/restore engine in `career_tweaker_balance.lua` snapshots originals and re-runs on `on_game_state_changed` and `on_setting_changed` through `_reconcile_rework_engines` (`career_tweaker.lua:214-224, 772-790`); some features are live hooks reading `mod:get` (armor/overcharge, Flagellation, Focused Spirit).

Coverage (measured by `A5_crt_catalog.py`): 75 balance rows across 18 of 20 careers (none for `bw_scholar` or `we_thornsister`); 51 rows carry code closures, 12 are pure data patches, 3 use a builder, 9 are empty owner rows for hook-owned toggles. So the catalog is data-indexed but only about 20 percent data-driven. Tourney port: 46 leaves + 17 presets (`career_tweaker.lua:160-163`).

Vanilla tables mutated: `BuffTemplates` (34 `crt_*` stubs, always registered, `career_tweaker_balance.lua:41-97`), `NetworkLookup.buff_templates` (same 34 + Tourney names), `Talents[...]` description values, vanilla buff template fields (snapshotted/restored).

RPC: `crt_peer_parity_present` beacon (schema 3, `career_tweaker.lua:1024-1030`) gates every network-visible rework on all peers running an identical catalog; Focused Spirit consensus channel `crt_focused_spirit_config` (`_crt_focused_spirit.lua:6, 163-290`).

Persistence: VMF settings only (111 `rework_*` toggles, 5 `level_override_*`, `unlock_all_careers`, armor/overcharge toggles). Backend reads are overridden, never written: `ExperienceSettings.get_experience` (`career_tweaker.lua:686-692`) and `get_read_only_data` on three mirror classes (`:712-732`).

Assessment: the most coherent of the three. One apply/restore engine, unconditional registration with a peer-parity floor, pure policies with tests. Debt: the headline feature (talent/ability swapping) is switched off (F13), 405 of 804 data lines and about 330 localization entries belong to the retired Big Rebalance, and 51 closure-based rows cannot be validated as data.

## 4. Findings

Format: severity | category | title, then evidence, impact, recommendation. Every runtime consequence below is "static evidence suggests" unless a tester log is cited.

### A5-F01 | S0 | correctness, state-lifecycle | CIM writes crafted backend ids into career loadouts and owns no isolation of that write
- Evidence: Athanor craft auto-equips by default (`CIMD/crafting_in_modded_dev_data.lua:112-114` default true) via `items.set_loadout_item(crafted_guid, career, slot, index)` (`CIMD/_cim_modded_loadout_owner.lua:519-526`); the Ranald importer does the same (`:632`); a player equipping a crafted item from the inventory takes the vanilla path. Vanilla `set_loadout_item` writes `_career_data` with `set_mirror = nil` (`Vermintide-2-Source-Code/scripts/managers/backend_playfab/backend_interface_item_playfab.lua:635-665`, `playfab_mirror_base.lua:1928-1941`), which the commit diff pushes as `updateHeroAttributes`, a payload that is not gated by `read_only_backend` (`playfab_mirror_base.lua:2875-2909`). Grep of `CIMD/` (outside the regression modules) for `set_character_data`, `_career_data`, `PlayFabMirrorAdventure` finds only a debug read (`cim_debug.lua:156-157`). CIM's only commit control is suppression while a forge window is open (`CIMD/crafting_in_modded_dev.lua:732-735`). The isolation that exists lives in another mod (`gui_tweaker_dev/.../_gut_native_loadouts.lua`, issue #402).
- Impact: with cim installed and the gut isolation absent, disabled, or an older build, a crafted GUID sits in the shared `characters_data`. At the next official sign-in that id is not in the inventory, so the slot is "broken" and replaced with starting gear (`playfab_mirror_base.lua:1579-1721`). This is the symptom recorded in open issue #402 (0-critical). Server acceptance of the modded-realm write is [unverified]; #402 is evidence that it has happened.
- Recommendation: make the isolation a shared library (`tools/shared_lib`) bundled by every mod that mints backend ids (cim, cim_dev, cwv, woc, mp), or have cim refuse to write a loadout slot unless it can prove the write chokepoint is owned. Add one runtime invariant, checked just before any commit: no id in `mirror._career_data` is a key of `forged_weapons`.

### A5-F02 | S0 | crash-safety | `/cim_craft_standard` and the standard-crafting keybind transition to a HeroView screen that does not exist
- Evidence: `mod.open_standard_crafting` calls `transition_with_fade("hero_view_force", { menu_state_name = "forge" })` (`CIMD/crafting_in_modded_dev.lua:516-518`; stable `crafting_in_modded/scripts/mods/crafting_in_modded/crafting_in_modded.lua:470`). Vanilla stores the params (`Vermintide-2-Source-Code/scripts/ui/views/hero_view/hero_view.lua:302`), then `post_update_on_enter` calls `_change_screen_by_name(menu_state_name, ...)` (`:504-508`), which asserts on an unknown name (`:477-480`). The only screen names are `overview`, `achievements`, `loot`, `keep_decorations`, `weave_forge`, `handbook` (`.../hero_view/hero_view_definitions.lua:74, 92, 112, 130, 148, 166`). Vanilla opens the bench with `menu_state_name = "overview", menu_sub_state_name = "forge"` (`Vermintide-2-Source-Code/scripts/unit_extensions/generic/interactions.lua:2203-2207`); the sibling mod uses the same two-field form (`gui_tweaker_dev/scripts/mods/gui_tweaker_dev/_gut_mission_inventory.lua:98-100`). Reachable from the command (`CIMD/_cim_modded_loadout_owner.lua:964-966`), the keybind (`CIMD/crafting_in_modded_dev_data.lua:102`), and the Athanor refusal message that tells players to run it (`CIMD/crafting_in_modded_dev.lua:406-408`). No other mod in this repo adds a `forge` screen (grep `settings_by_screen`: only gut's `gut_compendium`).
- Impact: an unprotected Lua assert in the view update path, in both the dev and the public stable mod. The existing rt checks for this function only inspect that it is defined (`CIMD/_cim_regression_forge_surfaces.lua:1248-1290`).
- Recommendation: use `menu_state_name = "overview", menu_sub_state_name = "forge"`. Confirm first with one runtime observation: run the command in the keep and look for `Could not find state by name` in the log.

### A5-F03 | S0 | state-lifecycle, crash-safety | The commit-suppression hook drops completion callbacks, including the one that shows the end-of-mission screen
- Evidence: `mod:hook("BackendManagerPlayFab", "commit", ...)` returns nothing when either forge flag is set and never calls `commit_complete_callback` (`CIMD/crafting_in_modded_dev.lua:732-735`). Vanilla returns an id and registers the callback (`Vermintide-2-Source-Code/scripts/managers/backend_playfab/backend_manager_playfab.lua:933-937`, `playfab_mirror_base.lua:2714-2752`). `StateInGameRunning.gm_event_end_conditions_met` puts `ingame_ui:activate_end_screen_ui(...)` inside that callback and passes it to `commit(true, callback)` (`Vermintide-2-Source-Code/scripts/game_state/state_ingame_running.lua:718-737`); the mechanism switch does the same (`.../game_mode/game_mechanism_manager.lua:523-528`). Mid-mission forges are a supported path (`allow_in_mission`, `CIMD/crafting_in_modded_dev.lua:405, 494`). The standard-forge flag is one boolean shared by three window classes and cleared by whichever exits first (`CIMD/standard_forge.lua:213-244`).
- Impact: if a forge window is open when the mission ends, or the flag is left true after an error skips `on_exit`, the end screen is never activated: a soft-lock. Separately the suppression is incomplete: a commit queued before the forge opened fires from the mirror's own timer without passing through this hook (`playfab_mirror_base.lua:1826-1829`). And its stated purpose (hide item mutations from PlayFab) does not match 6.13: no commit payload contains inventory items (`:2826-2911`).
- Recommendation: never swallow a callback. Either call through with the callback preserved, or queue and replay on forge exit. Replace the shared boolean with a per-window-instance set. Re-derive, against 6.13 source, whether any suppression is still needed.

### A5-F04 | S1 | correctness, architecture | Restore-time "exact postcondition" removes a saved craft from the inventory whenever its stored form differs from what the engine parses
- Evidence: `inject_mirror_item` adds the row, compares it to an expectation built from the record, and on any mismatch deletes the row and returns an error (`CIMD/_cim_synthetic_item_contract.lua:1113-1131`). The same function serves boot-time restore (`CIMD/crafting_in_modded_dev.lua:924-990, 1082-1130`). A comment records the first known trigger: a double that re-encodes as `0.2` fails the comparison (`CIMD/_cim_synthetic_item_contract.lua:316-321`). Issue #1654 (open, 1-major): a tester's crafted weapon vanished after restart with zero Lua errors.
- Impact: a guard written to keep the mirror clean hides the player's item instead. The record survives in settings, so the loss is invisible rather than permanent, but nothing tells the player. Any future representation drift (a property key the engine normalises, a skin fallback, a trait filtered by a provider) reproduces it.
- Recommendation: split the two uses. For a brand-new craft, strict postcondition with rollback is fine. For restore of an already-saved record, a mismatch must keep the row, log the differing field with `printf`, and count it in a restore summary. Add a host test that feeds restore a record with a perturbed float and asserts the row stays.

### A5-F05 | S1 | performance, state-lifecycle | Every boot re-adds every saved craft with full side effects: game-save autosave per item, "new" marker per item, full inventory refresh per item
- Evidence: restore calls `mirror.add_item(mirror, backend_id, payload)` with no `skip_autosave` / `skip_mark_as_new` (`CIMD/_cim_synthetic_item_contract.lua:1113`). Vanilla then runs `ItemHelper.mark_backend_id_as_new(backend_id, item, nil)`, which writes `PlayerData.new_item_ids` and calls `Managers.save:auto_save(SaveFileName, SaveData, nil)` (`Vermintide-2-Source-Code/scripts/managers/backend_playfab/playfab_mirror_base.lua:2494-2545`, `.../helpers/item_helper.lua:128-158`). Each item also triggers `dirtify_interfaces()` plus `items:_refresh()` (`CIMD/crafting_in_modded_dev.lua:968-988`), and `_refresh` walks the whole inventory and may autosave again (`.../backend_interface_item_playfab.lua:37-105`). This runs on every `_create_interfaces` (`CIMD/_cim_forge_state_owner.lua:505-511`). mp passes both skip flags for the same call (`MP/modded_progression.lua:619`).
- Impact: boot cost grows as saved crafts x inventory size; crafted GUIDs are written into the game's own save file (shared with the official realm; vanilla prunes unknown ids at `_refresh`, `backend_interface_item_playfab.lua:83-91`); static evidence suggests every restored craft is re-flagged as new on each start.
- Recommendation: restore with `add_item(bid, payload, true, true)`, batch all rows, refresh once. Runtime assertion after boot: no restored bid in `PlayerData.new_item_ids`.

### A5-F06 | S1 | architecture, state-lifecycle | A player's whole crafted collection lives in one VMF setting, with the failure modes that implies
- Evidence: `mod:set("forged_weapons", save_data)` is the only store (`CIMD/_cim_forge_state_owner.lua:65-91`). VMF keeps all mods' settings in one table in `user_settings.config`, flushes only on game-state change, options close or reload, and if any mod stores a mixed table the whole save call fails for every mod (`VMF/scripts/mods/vmf/modules/core/settings.lua:5-7, 20-34`). `mod:get`/`mod:set` deep-clone the table on every call (`:48-55, 64-70`), and `load()` then `save()` runs on every backend interface rebuild (`CIMD/_cim_forge_state_owner.lua:92-137, 505-506`). Settings are namespaced by mod id, so `cim_dev` and `cim` hold separate collections; neither tree references the other (grep `get_mod("cim` in both trees: none besides self). Records rejected at load are dropped and the drop is persisted by the trailing `save()` (`:92-137`); today that covers malformed rows and `woc_*` relics by design (`CIMD/_cim_synthetic_item_contract.lua:210-231`).
- Impact: no backup, no versioned export, no path from dev to stable, and a tester who promotes from dev to stable silently starts with an empty collection. Removal of the mod leaves the data in the config (harmless) and the items vanish from the inventory; any loadout slot still pointing at one is the F01 case.
- Recommendation: add `/cim_export` and `/cim_import` (JSON to a file under the mod's data dir or to the log), a one-time import of the other stream's store with a visible prompt, and a rotating last-good copy written before every destructive transaction. Add a co-install warning when both `cim` and `cim_dev` are enabled.

### A5-F07 | S1 | testability | The in-game regression runner cannot serve an automated pipeline as built

- Impact: 169 runtime checks exist across the three mods (99 cim, 26 mp, 44 crt) and none can be consumed by a script. This is the direct cause of the verify-fix backlog for this family.
- Recommendation: section 6 and work items 1 and 2.
