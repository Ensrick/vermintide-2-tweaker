### 3.3 Against a context budget

A common agent window is 200k tokens (1M on extended-context models); the harness, tool schemas and system prompt already consume a part of it (in this session the auto-loaded instruction layer alone is about 13.7k tokens before tools). The minimum legal chain to ship a one-line change is about 45% of a 200k window; any chain that includes the mod's own required docs or the bug path does not fit in 200k at all. The rule set therefore cannot be followed as written by any agent with a 200k window, and agents necessarily read a private subset. Which subset is not defined anywhere, so two agents (or two vendors) follow different rules. `PROJECT_STANDARDS.md:33` itself states that file sizes "exceed Claude's effective working memory" for code; the same is true of the rulebook.

### 6.2 Is the lifecycle-card system proportionate?

No. Evidence:

1. **It has no reader.** 846 of 858 cards on open issues (98.6%) were never followed by a comment from anyone but the owner account (which agents also use; see the caveat in 2.4). The only tester, RainReligion, last commented on 2026-09-23 (51 days before this audit). The brief states the owner is not playing. 282 issues sit in a ready state whose newest card has a median age of 60 days.
2. **It keeps consuming work with no reader.** 111 cards were posted and 335 cards were rewritten in place in November 2026. 67% of all cards have been edited after posting; a carded issue names 3.46 different versions across its cards on average (max 24), because every ship of a mod makes every card that names that mod stale and `tools/ship/refresh-cards.ps1` (2,692 lines) rewrites them.
3. **It couples the tracker to every merge.** `docs/BUG_TRIAGE_RUNBOOK.md:390-393`: "A single issue carrying `verify-fix` or `diagnostics-armed` without exactly one correctly formatted pinned card therefore fails qa-gate for the whole repository - including PRs that never touched that mod." Recorded instances in memory files: a tester comment newer than the card turned every PR red within minutes (`reference_vt2_live_test_card_offline_validation.md`, 2026-09-21); one label edit that left #1025 without a lifecycle label blocked every PR (#1025 comment 2026-09-12T22:51Z); after every ship the pin file must be landed by its own PR or "qa-gate fails for ALL pull requests" (`reference_vt2_ship_pin_repoint_gate.md`); a deployed `printf` swap inside a regression check deadlocked the repository until an exception PR landed ("Trap 8", #1643).
4. **Its specification is not followable.** The card grammar occupies about 50 lines of dense prose in PS 11 (`:2315-2367`), again in the runbook (`:347-383`), again in the template comment, and the prose defers to four scripts of 407 KB. About 60 violation codes exist. The offline procedure to validate a draft card before posting exists only in a Claude memory file.
5. **Cost per issue.** Open issues carry 12.5 comments on average (median 11); 858 cards and about 1,600 ship or lifecycle notes (keyword classification of comment text) were written to 329 issues. The tracker holds 6.94 MB of comments, 98.3% from the owner account, 4,247 of them in July alone. Memory `reference_vt2_ship_pin_repoint_gate.md` budgets "about 40 min per ship (ship 10 + pin PR CI 15 + master QA 15)" and notes that back-to-back ships of different mods are impossible.
6. **It captures the wrong class of issue.** #321 (Big Rebalance retirement) has been `verify-fix` since 2026-07-14 with 6 successive cards asking a human to confirm that options are absent, while a blocking static check (`qa/check_retired_big_rebalance.ps1`) already proves the same thing. The card system has no path for "a machine can prove this".

The repository's own rule describes the failure: PS 11b, "An unconsumed probe is the runtime twin of a standing warning: signal with no reader."

What the cards are good for: each one is a compact, mostly well-formed test specification (build, topology, steps, expected result, sometimes an exact log receipt). That content should be kept as input for an automated harness. The pinning, the per-ship rewriting, the deployed-source "authority" proof and the repo-wide gate should not.

**Who reads the cards today:** `tools/verify/generate_playtest.ps1` (to build `docs/PLAYTEST_SCRIPT.md`, last generated 2026-09-01), `tools/ship/refresh-cards.ps1` and the CI guard. No person.

### 9.4 Simplified issue lifecycle for an autonomous harness

States (one label each): `todo` -> `needs-evidence` (a change is merged and deployed to the test target) -> closed. Side state: `needs-human` (verification class V or C only). `blocked` stays a modifier.

- **The verification spec lives in the repo, not in a pinned comment.** One file per issue, `verify/specs/<issue>.json`: class (U/S/R/V/C), mods and minimum version, setup, the check to run (unit test id, static check id, or an in-game harness script and the state or log line it asserts), expected result. It is reviewed in the PR that adds the fix, so CI validates it as a file. The 282 existing cards convert almost mechanically: `Build/banner`, `Topology`, numbered steps and `Expected` are already structured.
- **Evidence is attached by a machine.** The harness writes one result record (spec id, mod version and source commit read from the load banner, pass or fail, log excerpt, run id, timestamp) and a bot keeps a single "Verification status" comment per issue, edited in place. No pinning, no per-version re-issue: the record names the version it ran against; a newer ship only marks it "evidence older than deployed build" and queues a rerun.
- **Closure rule.** U/S/R issues close when the newest evidence is a pass against the currently deployed version. V/C issues go to `needs-human` and appear in one generated volunteer list; they never block anything.
- **Tracker hygiene is advisory and separate.** A nightly job reports label problems as an issue comment or a dashboard. It never fails a pull request. The PR gate tests the tree in the PR and nothing else.
- **Issue text.** Free form for humans; agents write `Symptom / Evidence / Fix / Refs`. No three-fallback requirement, no word limits enforced by rule.
