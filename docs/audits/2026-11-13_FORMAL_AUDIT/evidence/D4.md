## 2. Clusters (2+ issues)

### 2.1 `gut-native-loadout-store` (#231 #232 #353 #375 #402 #954; plus #1688 from 2.2; outside this bucket #1033 #287 #354; closed #174 #175 #372 #379 #387 #1637)

**Answer to the lead's question on #954 and #1033:** they share a subsystem and an architectural cause with each other and with the issues above, but not one defective line.
- Shared cause: in the modded realm GUT replaces the game's saved-loadout mirror with its own store through hooks. Loadout truth then lives in five places: official `characters_data`, the GUT store (`entry.loadouts[selected_index]`, `bot_index`, `bot_loadout`), `PlayerData.loadout_selection`, the backend item cache, and the live unit. Each issue is two of those disagreeing.
- #954: the bot designation was an index into a row the player keeps editing (thread 2026-07-22). Fixed by a detached `bot_loadout` snapshot.
- #1033: Equipment DEFAULT rewrote the store but nothing refreshed the live unit (#1033 body).
- They interacted: the #1033 reset deleted the #954 snapshot (thread #954, 2026-08-02). That hole is closed on master: `clear_modded_loadouts` now calls `preserve_designation` (`gui_tweaker/scripts/mods/gui_tweaker/_gut_native_loadout_policy.lua:231-249`).
- #375 (row seeding and selected row), #402 (store leaking into official), #353/#354 (third-party ids at exit), #1637c (empty slot reaching spawn) are the same class.

One harness covers the cluster, as five invariants checked after every scripted equip, row switch, DEFAULT, bot designation and relaunch: (1) official `characters_data` is byte-identical before and after; (2) store row equals the hero-view row equals what the unit wields; (3) the bot snapshot changes only on designation; (4) `selected_index` equals the displayed row; (5) no unresolvable id reaches a spawn. One fix does not cover it: each member needed its own repair.

### 2.2 `realm-flag-6.12` (#624 #1465 #1671 #1684 #1688 #1693 #1694)

Root cause: game 6.12.0 replaced `script_data["eac-untrusted"]` with the global `MODDED_REALM`, and 6.13.0 gates UI on `GameSettingsDevelopment.read_only_backend` (`scripts/settings/game_settings_development.lua:49-52`). One shared library now answers the realm question; all six consumer copies are byte-identical to `tools/shared_lib/_lib_modded_realm_authority.lua` (sha1 `f0633ffc2657`, checked in cim, cim_dev, mp, cosmetics, gt, gt_dev). The library fix covers the realm question; each UI gate still needed its own repair (#624 forge prompt, #1465 Apply button, #1693 gamepad prompt). One harness check covers the realm half: assert `is_modded` in a modded boot. The static hook-target gate (F3) covers #1671.

## 8. Cross-cutting findings (severity per the common brief)

**F1 (S0) Official-realm saved loadouts could be overwritten by modded-realm edits.** The engine commits loadout changes to PlayFab without any modded-realm guard: `Vermintide-2-Source-Code/scripts/managers/backend_playfab/playfab_mirror_base.lua:2885-2900` builds `new_data[self._characters_data_key]` and sends `updateHeroAttributes`; only statistics, weave data and weapon poses are behind `read_only_backend` (`:2826`, `:2839`, `:2857`). GUT's modded loadout store exists to keep modded edits out of that path. Its realm test read `script_data["eac-untrusted"]`, which game 6.12.0 stopped writing (`foundation/scripts/util/application_parameter.lua:150-152` only sets `MODDED_REALM`). Static evidence suggests that from 6.12.0 (2026-08-26) until public GUT 0.2.290 (2026-11-02) the public store was inert and modded equips went to the official data (#1688, the #402 corruption path). A before/after comparison of the official `characters_data` around a modded equip on 0.2.289 would confirm it. The fix is present in both streams (`gui_tweaker/scripts/mods/gui_tweaker/_gut_official_loadout_boot_policy.lua:6-16`, `_gut_official_loadout_boot_guard.lua:28-32,98-158`). It has never been observed working in a game. #1688 is labelled 1-major; it should be 0-critical.

**F2 (S0) A crafted item was lost from a playtester's inventory and the cause is unknown (#1654).** The armed diagnostic cannot see the most likely branch. `issue1654_saved_crafts_restored` iterates the saved store (`crafting_in_modded_dev/scripts/mods/crafting_in_modded_dev/_cim_regression_checks.lua:445-469`), so a craft that was never written, or was removed from `forged_weapons`, yields PASS or skip. The diagnostic is dev-only (official changelog says it was not promoted, `crafting_in_modded/CHANGELOG.md:31-32`), and its card needs the tester to boot before crafting anything, seven weeks after the loss.

**F3 (S1) Game patches silently broke at least nine features and no gate noticed.** Members: #624, #1465, #1671, #1684, #1686, #1688, #1692, #1693, #1694, #1695 (and #1689c, #1690, #1691 in other buckets). All were found by a tester or by reading source weeks later. Two of these classes are checkable offline today:
- Hook targets: `scripts/D4_hook_targets.py` resolves every literal `mod:hook("Class","method")` against the decompiled source. Result on 6.13.0: mp 52/52, crt 24/24, gut 83/83, gut_dev 85/85, cim and cim_dev 108/109. The one miss is a `rawget`-guarded dead branch (`crafting_in_modded/scripts/mods/crafting_in_modded/_cim_standard_forge_presentation.lua:260-262`).
