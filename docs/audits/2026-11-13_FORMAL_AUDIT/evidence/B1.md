### 2.2 Flow for a dev-stream mod: "Lua fix written" to "a player has it"

Steps an operator (human or agent) must perform, in order. Citations show where each is required.

Prepare (must run on the one machine that has the VT2 SDK, the launcher, Steam and the claim store):
1. Create a write worktree with `tools/worktrees/worktree.ps1 -Action Create` (budget 8 trees, `tools/worktrees/worktree.ps1:17`).
2. Drop a `.in_progress/<mod>.md` sentinel (advisory; repo `CLAUDE.md`, "Multi-agent coordination").
3. Run `tools/ship/claim.ps1 -Mod <mod>`. It takes a machine-wide lock and picks the version number; the claim goes stale after 24 hours (`tools/ship/claim.ps1:25-27`, `PROJECT_STANDARDS.md:1066`).
4. Edit the Lua.
5. Set `MOD_VERSION` to the broker's number.
6. Edit `itemV2.cfg` so the title (and description banner) end in ` v<MOD_VERSION>` (enforced by `qa/check_versions.ps1`; owner note `reference_vt2_version_bump_cfg_banner_and_claim_order`).
7. Write the top CHANGELOG entry whose version equals `MOD_VERSION` exactly (`tools/ship/ship.ps1:1826`), with a lifecycle tag and issue numbers in the header (read by step 6 of the ship, `tools/ship/ship.ps1:2750`).
8. Add the regression test (`PROJECT_STANDARDS.md` section 15).
9. Run `tools/ship/ship.ps1 -Mod <mod> -BuildOnly`: 14 pre-build stages (see 2.4), a clean compile, and a schema-3 receipt.
10. `git add` source, root bundle and `.build-receipt.json` together and commit. The pre-commit hook runs 8 steps (`tools/hooks/pre-commit.ps1:113-269`, "step 0/7" to "step 7/7").
11. Push and open a pull request. The body must say `Refs #N`, never `Fixes #N` (`CONTRIBUTING.md`, "Pull requests").

Land:
12. Wait for three required checks; `qa-gate` takes a median of 21.9 minutes. If master moved, update the branch and wait again (`strict = true`, `tools/github/protect-master.ps1:33`).
13. Merge.
14. Wait for a second `qa-gate` run on the exact merge commit. The ship refuses without it (`tools/ship/publication-authorization.ps1:56`).

Ship:
15. Bring the ship worktree and the primary checkout to the exact live master commit, clean, under the same claim-owner identity.
16. Run `tools/ship/ship.ps1 -Mod <mod>`: 25 stages (see 2.4).

Aftercare:
17. The ship rewrites the pin file in the working tree (`tools/ship/ship.ps1:2727`). Commit it on a branch, open a second pull request, wait for `qa-gate`, merge, wait for master `qa-gate`.
18. Write or refresh the pinned `## CURRENT LIVE TEST` card on each issue, valid against deployed-source authority; without it the ship refuses to apply the ready label (`tools/ship/ship.ps1:2735-2747`, warning text at 2746).
19. Close the worktree, delete the branch, remove the sentinel (`PROJECT_STANDARDS.md:1949-1962`).

Delivery:
20. Each tester unsubscribes and resubscribes through the dev collection (`PROJECT_STANDARDS.md:1491`).
21. Each tester confirms `[<id>:LOAD] v<version>` in the newest console log.

Totals for a dev ship: 21 operator steps, 4 full CI cycles (feature PR, master, pin PR, master), about 10 persisted receipts or state records (claim file, allocation ledger, `.build-receipt.json`, `transaction_lease.json`, private launcher config, release zip plus manifest row, `publication-receipt-<mod>.json`, `workshop-upload-result-<mod>-<commit>-<hash>.json`, pin-file rewrite, issue labels and cards).

### 2.3 Extra steps for a stable public mod

The fix first completes the whole dev flow (`PROJECT_STANDARDS.md:948-958`). Then:
22. Port the change into the stable directory, by hand or with `tools/promote/promote.ps1` (`docs/PROMOTION_PROCESS.md`, modes A and B).
23. The owner names the version; write a rolled-up stable CHANGELOG entry that cites the issue numbers.
24. Claim and `-BuildOnly` the stable mod.
25. Open the pull request. Post a comment `VT2-Promotion-Approval: <dir>@<version> head=<40-char sha>`; a maintainer applies the `stable-promotion-approved` label; rerun checks. Any new commit voids the grant (`docs/PROMOTION_PROCESS.md`, "Protected-PR authorization").
26. `qa-gate` with the promotion gate (`qa/check_promotion.ps1`), merge, master `qa-gate`.
27. For a version without a suffix, a fresh owner signal that names the version (`PROJECT_STANDARDS.md:1391-1396`).
28. `ship.ps1 -Mod <stable> -AllowPublic`, then the pin pull request cycle again.
29. Players receive it through Steam's normal update.

Totals for a stable ship: 29 or more operator steps, 8 full CI cycles, 2 human approvals.

## 4. Findings

Format: severity | category | title, then evidence, impact, recommendation. Severity counts: S0 2, S1 7, S2 8, S3 4.

### B1-F01 | S0 | process | The pipeline's size and ceremony are out of proportion to the risk, and bookkeeping has displaced product work

Evidence:
- 58,057 lines in 129 files of release and tracker-paperwork tooling (section 2.1), plus a separate C# launcher, to publish 21 Workshop items whose usual payload is a 1 to 2 MB zip.
- A dev ship needs 21 operator steps, 4 full CI cycles and about 10 receipts (section 2.2). A stable ship needs 29 or more steps, 8 CI cycles and 2 human approvals (section 2.3).
- The doctrine a shipping agent must hold in mind is 484 lines (`PROJECT_STANDARDS.md:1029-1512`), with further binding text in `tools/ship/CLAIMS.md` (375 lines), `docs/BUNDLE_AUTHORITY.md` (123), `docs/PROMOTION_PROCESS.md` (225), `docs/PORTABLE_SETUP.md` (168) and `tools/publish-release/README.md` (456).
- In the last 90 days 25.7% of master commits changed only the pin file and 24.4% only tooling or QA; 46.9% touched a mod (section 3.1).
- 109 of 613 closed issues carry the `tooling` label, and 11 open ones do (`data\closed_index.tsv`, `data\open_issues.json`).
- All tooling must parse under two PowerShell hosts: Windows PowerShell 5.1 and PowerShell 7 (`.github/workflows/qa.yml:75-83`; ASCII-only rule at `tools/ship/ship.ps1:64`).
- The threat model is that of a multi-tenant build farm: native handle locks, kill-on-close process Jobs, ACL journals, reparse-point checks (46 mentions in `tools/ship`), three authorization reads per ship. Section 6.6 itself concedes the limit: "These checks do not claim protection against a malicious process" (`PROJECT_STANDARDS.md:1444`).

Impact: the cost of shipping a three-line fix is dominated by process, each incident has been answered with another gate, and each gate has become a new way to fail (section 5). The risks actually observed in this project are narrow: two sessions picking the same version, an upload that reports success without transferring, a wrong `published_id` hijacking another item, and a fix left unshipped. Four narrow risks do not need 58,000 lines.

Recommendation: adopt the target pipeline in section 7. Keep the handful of checks that map to an observed incident (list in 7.3) and delete the rest. Freeze new pipeline features until the target exists.

### B1-F02 | S0 | release | Every ship leaves master needing a second pull request, and one metadata file is touched by 59% of all commits

Evidence:
- The ship rewrites `tools/verify/live_test_contract_exceptions.psd1` in the working tree and cannot commit it: "Ship cannot commit to master: any rewrite remains a working-tree candidate for review" (`tools/verify/live_test_contract_exceptions.psd1:19-21`; call at `tools/ship/ship.ps1:2727`).
- The file pins the exact deployed source tree of each audited mod: "Any deployment that changes one byte in an audited mod fails closed until ... this pin is intentionally moved" (same file, lines 31-32).
- The next ship stops if pins are not current: "Current source pins require a reviewed metadata PR before this ship can continue" (`tools/ship/ship.ps1:1950`).
- 190 commits have touched this file since it was created on 2026-08-13. Since 2026-09-20, 79 of 134 master commits (59%) touch it and 34 (25%) touch nothing else.
- Owner note `reference_vt2_ship_pin_repoint_gate`: until the pin change merges, the lifecycle guard fails `qa-gate` for all pull requests; "back-to-back ships of different mods are therefore impossible, so budget ~40 min per ship". I did not trace that failure path in code `[unverified in code]`; the measured cycle (36 minutes to land the pin pull request, section 3.1) is consistent with it.

Impact: shipping is a two-pull-request operation by design. The second one is pure bookkeeping, blocks other work while open, and makes one file a merge-conflict point for every concurrent agent. A release tool that cannot finish its own transaction is a systemic process defect.

Recommendation: stop storing deployed-source identity in the source tree. The hosted release manifest already records the source commit of every shipped mod; let the card and lifecycle checks read it from there at check time. Acceptance: after a ship, `git status --porcelain` is empty in both the ship worktree and the primary checkout, and no follow-up pull request is needed for other pull requests to stay green.

### B1-F04 | S1 | source-control | Compiled bundles are tracked in git: 98.7% of history, a 15 GiB public repository

Evidence:
- 16.52 GiB of the 16.73 GiB of reachable blobs are `.mod_bundle` files, in 1,482 versions (section 3.4). GitHub reports 15.2 GiB.
- CI must use a blob filter to clone at all: runs "died INSIDE checkout at the 20-minute job timeout" (`.github/workflows/qa.yml:45-48`).
- The only stated reason is an unconfirmed AI review note: "bundleV2/ is INTENTIONALLY tracked (so other devs / git bisect can see the built bundle ...). Confirm with maintainer" (`.gitignore:83-85`).
- Issue #558 "Stop tracking generated bundle outputs" has been open since 2026-07-13 and is labelled `blocked`. Its own body states "Git tracking is not required by Vermintide or Stingray" and that only 25 of 77 tracked bundle hashes are unique.
- The replacement ("receipt" authority: commit a hash file instead of the bytes) was built across at least eight tooling issues (#1400, #1412, #1422, #1426, #1429, #1430, #1434, #1466) and is used by 0 of 21 mods: "All active inventory rows remain `tracked`" (`docs/BUNDLE_AUTHORITY.md:28`; `tools/mod-inventory.psd1`, 21 rows `tracked`, 0 `receipt`).
- Every ship already rebuilds from source and requires the result to equal the tracked bytes (`tools/ship/ship.ps1`, message "clean build exactly reproduces the ..."), so the tracked copy carries no information that source plus a hash does not.
- Every build is also archived as a release asset (114 releases, 11.37 GiB).

Impact: slow clones and fetches, CI that depends on a partial clone, binary churn in every product pull request, a merge-conflict surface no human can resolve, and a contributor barrier (F10).

Recommendation: not justified; stop tracking. Section 7.2 gives the alternative (build at ship time, hashes in the release record). Decide separately whether to rewrite history or start a fresh repository (owner question 2).

- The process doc names the failure the model produces: "a fix rotting in dev and never reaching public users" (`docs/PROMOTION_PROCESS.md:6-9`, issue #278).
- `chaos_wastes_tweaker` stable holds 12 Lua files that do not exist in dev, nine of them named `_ct_official_*` (for example `chaos_wastes_tweaker/scripts/mods/chaos_wastes_tweaker/_ct_official_shop.lua`). The stable tree is therefore a fork with its own code, not the "older promoted snapshot" the rule describes (`docs/PROMOTION_PROCESS.md`, "Invariants": "Stable is written only by a promotion").

Impact: every fix is written or copied twice, unit tests and QA scan both copies, promotions are large manual ports (20,271 changed lines for Chaos Wastes), and fixes strand in dev. For the weapon pair the two directories must stay byte-equal apart from identity, which is a build step being done by hand and enforced by a gate.

Recommendation: one source directory per mod. See section 6, question 3.

### B1-F06 | S1 | release | There is no rollback path; the only way back is a new version through the whole pipeline

Evidence:
- "If the version was already uploaded, ship a new forward-fix version rather than rewriting the published version or relying on an older bundle" (`docs/PROMOTION_PROCESS.md:189-193`).
- The recovery record is explicitly not usable: "It does not restore files and does not select a GitHub release" (`tools/publish-release/recovery-record.ps1:3-7`); "No updater, historical resolver, file replacement, deployment ... is enabled" (`docs/BUNDLE_AUTHORITY.md:119-123`).
- No rollback or revert procedure exists in `tools/ship`, `tools/publish-release`, `tools/promote` or section 6.6 (grep for "rollback", "roll back", "revert a ship": two hits, both quoted above or about branch protection).
- The fastest complete cycle I could measure is 86 minutes after the fix is already built and committed (section 3.1). A clean public version additionally needs the owner's version-named signal and the promotion label.

Impact: if a public build crashes players, the minimum outage is roughly 1.5 to 2 hours with every gate green, one specific machine available and Steam in a good state; longer if any of the failure modes in section 5 occurs. The path has never been rehearsed.

Recommendation: add a rollback verb that re-uploads the exact bytes of an earlier release asset (verified against the manifest's SHA-256), without a rebuild. Rehearse it once on a friends-only item. Target: under 15 minutes.

### B1-F07 | S1 | release | Shipping is bound to "exact live master HEAD with green CI", which serializes the whole repository

Evidence:
- Authorization requires the shipped commit to be the live default-branch head, to be a merged pull request, and to have a successful `qa-gate` on that exact commit (`tools/ship/publication-authorization.ps1:31-57`). It is re-read twice more during the ship (`tools/ship/ship.ps1:2450`, `:2532`), so a merge by anyone else during the build fails the ship after the local deploy.
- Branch protection is `strict`, so each merge puts every other open pull request behind and forces a fresh 22 to 27 minute run.
- 31 of 81 verified ships went out from a master commit that did not change the shipped mod: the operator had to wait for CI on someone else's merge.
- Landing one pull request takes a median of 36 minutes and up to 54 (9 samples in the helper log).

Impact: throughput is capped near one ship per 86 minutes for the whole repository, and concurrent agents block each other. This is the main reason a large fan-out of agents does not translate into shipped fixes.

Recommendation: authorize a ship when the mod's directory tree at the shipped commit equals the same directory's tree at a master commit that has a green `qa-gate`. Drop `strict` or use a merge queue. Make CI fast (F11).

### B1-F08 | S1 | release | Publication order allows half-published states

Evidence:
- The GitHub release is created and published (`tools/publish-release/publish-release.ps1:856-860`, called from `tools/ship/ship.ps1:2465`) before the Workshop upload starts (`tools/ship/ship.ps1:2570`).
- Since 2026-09-20, 2 of 68 mod-days have a publication receipt with no verified Workshop result that day (section 3.1). `tools/ship/CLAIMS.md` records the first: "The old version has a GitHub publication receipt, not an authenticated Workshop transfer".
- Owner note `reference_ship_pipeline_environment_traps` lists three ways this happened (Steam registration, a validator regression, a stale GitHub asset list), each "AFTER the GitHub release".
- Section 6.6 has a long recovery procedure for this state, starting at `PROJECT_STANDARDS.md:1209`.

Impact: friends who install through the updater (which reads the latest release) can receive a build that Workshop subscribers do not have, version claims are left stale, and the next ship needs pin recovery.

Recommendation: upload to the Workshop first, verify, then publish the release; or keep the release as a draft until the upload proof exists.

### B1-F09 | S1 | process | The real shipping procedure lives outside the repository, and `ship.ps1` is neither one command nor measurable

Evidence:
- Agents drive the pipeline with unversioned scripts in a user profile: `%USERPROFILE%\.claude\vt2-ship-helpers\` (`land-pr.ps1`, `ship-cycle.ps1`, `ship-chain.ps1`, `enqueue.ps1`, `round.ps1`, `pin_card.ps1`, 70 files). Owner note `reference_vt2_ship_helpers_durable_home` records that an earlier copy was lost in a temp-folder cleanup.
- 32 owner memory notes hold pipeline knowledge that the repo docs do not (section 5).
- `ship.ps1` covers only steps 9 and 16 of the 21 in section 2.2. It writes no machine-readable result (no JSON output; exit codes are only 0, 1, 2, 7), has no resume or checkpoint (0 occurrences of "resume" or "checkpoint"), and its success report is coloured console text (`tools/ship/ship.ps1:3090-3131`).
- No log of ship attempts exists. Successful ships can be counted from release assets; failed attempts cannot be counted at all.

Impact: a weaker agent cannot run a ship from the repository alone, and nobody can state the pipeline's failure rate. Section 6, question 2 gives what can be inferred.

Recommendation: one in-repo driver that performs all steps, writes a JSON result on success and on failure, and resumes (section 7).

### B1-F10 | S2 | release | A build receipt binds every file in the mod directory, including 208 Markdown files

Evidence:
- `tools/ship/build-receipt.ps1:122-135`: every path is an input except the receipt itself and `bundleV2/` ("intentionally an allow-by-default provenance boundary"). `PROJECT_STANDARDS.md:1320-1323` gives the reason: the builder passes the whole directory to the compiler.
- The 20 current receipts list 208 `.md`, 15 `.py` and several `.ps1` files as source inputs (inline census of `*/.build-receipt.json`).

- `CONTRIBUTING.md` says the opposite: "Contributors normally submit source and verification evidence; the maintainer owns deployment" (section "Build and release boundary"), under a "Five-minute setup" heading for a 15 GiB repository with no partial-clone instruction.

Impact: static evidence suggests that editing a CHANGELOG or a design note inside a mod directory invalidates the receipt and forces a rebuild on the release machine. Running `qa/check_build_receipts.ps1` after such an edit would confirm it. An outside contributor cannot get a source-only pull request through `qa-gate`.

Recommendation: disappears with F04. Until then, move non-compiled docs and tools out of the mod directories or exclude them by an explicit list.

### B1-F11 | S2 | ci | `qa-gate` runs 21.9 minutes at the median against a 30 minute timeout and is not scoped to the change

Evidence: section 3.2. p90 is 27.3 minutes; the November median is 3 minutes higher than October's. `run_all.ps1` runs about 88 checks one after another for every pull request, including fourteen weapon-history reproducibility checks (`qa/run_all.ps1:420-470`) and gates for subsystems the change does not touch.

Impact: the required check is about three minutes of growth away from timing out on a tenth of runs. Every extra minute is paid four times per ship.

Recommendation: select checks by changed paths, run independent checks in parallel, move slow reproducibility matrices to a nightly run. Target a median under 8 minutes. As a stopgap raise the timeout to 45 minutes.

### B1-F12 | S2 | testability | Pipeline self-tests assert the script's own source text

## 6. Answers to the six questions

**1. Is the complexity proportionate to the risk?** No. 58,057 lines of release and paperwork tooling (129 files) plus a C# launcher stand between a fix and a 1 to 2 MB Workshop upload. A dev ship takes 21 operator steps and 4 CI cycles; the best complete cycle on record is 86 minutes after the build is committed. In the last 90 days 46.9% of master commits touched a mod, 25.7% only moved pins and 24.4% only changed tooling or QA. The project's real release risks are four (version collision, false upload success, crossed Workshop ID, stranded fix). Process engineering has displaced product work.

**2. Can a weaker agent run a dev ship end to end, unattended? How often does it fail on mechanics?** Not reliably today. `ship.ps1` covers 2 of the 21 steps; the rest is spread over section 6.6, five other documents, 32 memory notes and unversioned helper scripts. A true failure rate cannot be computed because failed attempts are not logged (B1-F09). What the evidence shows: every one of the 21 recorded failure modes is pipeline or machine mechanics, none is a mod defect; 4 of 13 landing attempts in the helper log aborted (small sample); 5 of 11 failed `qa-gate` runs failed in process gates; 2 ships in 8 weeks stopped half-published; at least 5 claimed versions were abandoned. Top failure modes, in order of how often they recur in the record: (a) master moved, rerun CI; (b) pin pull request pending; (c) claim expired or owner mismatch; (d) Steam or SDK machine state, failing after the GitHub release; (e) receipt or version-identity mismatch; (f) a pipeline validator that is itself wrong.

**3. Dev/stable as duplicated directories?** It is the most expensive option. Cost today: 152,289 duplicated Lua lines, about 71,000 lines of copy-commits in 90 days, seven gates and tools, and stable trees that have forked (Chaos Wastes: 12 stable-only files, 57 dev-only, 20,271 changed lines). Risk: a fix that never reaches the public item, which already happened (#278). Recommended model: one directory per mod on master. The stable Workshop item is built from a tagged commit (`<mod>/v<version>`), the dev item from master. The identity differences (mod id, Workshop id, title, settings namespace) come from a small per-stream table applied when the build is staged, which is the same transformation `tools/promote/promote.ps1` already does by hand in the other direction. Dev-only diagnostics become a flag the stream table sets. Whether the launcher can build from a staged copy is `[unverified]`; pilot on `verminious_dreams_lighting` (3 files).

**4. Compiled bundles tracked in git?** Not justified. They are 98.7% of a 15 GiB public repository, the ship already rebuilds and compares, and every build is archived as a release asset. Alternative: build once at ship time from the merged commit, upload those bytes, and write their SHA-256 values into the release record. If a pre-merge compile check is wanted, run the build in the pull request preparation and throw the output away.

**5. Rollback?** There is no tested path. Policy is roll-forward only (`docs/PROMOTION_PROCESS.md:189-193`). Realistic time to replace a broken public build is 1.5 to 2 hours when everything is green, and it depends on one machine. An earlier build's exact bytes do exist (release assets), but no tool re-publishes them.

**6. Minimal robust target?** Section 7.

## 7. Target pipeline proposal

### 7.1 Shape

One command, run on the release machine: `tools/ship/release.ps1 -Mod <mod> [-Stream dev|stable] [-ConfirmVersion <x.y.z>] [-Resume] [-DryRun]`.

| Step | What it does | Already done? check (makes it idempotent) |
|---|---|---|
| 1 doctor | Steam running and registered, SDK present, launcher hash matches the pinned value, `gh` authenticated, mod directory clean | none needed; changes nothing |
| 2 version | Next version = highest existing git tag `<mod>/v*` plus one patch. Push the tag; the push is the lock (it fails if another session took the number) | tag exists and points at this commit |
| 3 check | Lua parse, duplicate-hook lint, unit tests and identity checks for this mod only; target under 3 minutes | result cached by commit |
| 4 build | Clean build of the tagged commit into a temp folder; record SHA-256 of each output file | hashes present in the run journal |
| 5 upload | Launcher upload; verify one complete transaction for this item in `workshop_log.txt` | Workshop manifest id recorded in the journal |
| 6 record | Attach `<mod>-<version>.zip` and `ship-result.json` to a per-mod GitHub release | asset exists with the same hash |
| 7 deploy | Optional copy to the local subscription folder with hash check | hashes equal |
| 8 announce | Separate, retryable: labels and test cards read `ship-result.json`. Never fails the ship and never writes to the source tree | idempotent by design |

Properties:
- Machine-readable result: `ship-result.json` with mod, version, commit, output hashes, Workshop manifest id, and per-step status and timestamps; written on failure too, with `failed_step`. Exit code 0 only when steps 1 to 6 are complete.
- Resumable: a journal file per run; `-Resume` continues from the first step that is not done.
- Source landing stays simple: pull request, fast CI (median under 8 minutes), merge. The ship needs a master commit with green CI for that mod's directory, not the live head of the whole repository.
- Stable: same command with `-Stream stable -ConfirmVersion <x.y.z>`; the argument must equal the version being shipped, which encodes the owner's "fresh signal naming the version".
- Rollback: `release.ps1 -Mod <mod> -Rollback <version>` downloads that release asset, verifies its hash, uploads it, records the result.

### 7.2 What replaces tracked bundles and receipts

The release record (`ship-result.json` plus the zip) is the single authority for "which bytes went out from which commit". Nothing compiled is committed.

### 7.3 Keep, simplify, delete

| Keep as is | Why |
|---|---|
| VMBLauncher as the only build and upload boundary | Solved the "deploy does not build" and Steam-clobber classes |
| `qa/check_published_ids.ps1` before any upload | Real incident: one mod's content pushed onto another's item |

## 9. Questions for the owner

1. Nobody reviews binary bundles. Do you need "reviewed bytes before merge" at all, or is "built from the merged commit at ship time, hashes recorded" enough? (Decides item 7.)
2. May git history be rewritten, or a fresh repository started, to shed 16.5 GiB of bundle history? It invalidates old commit hashes in issues and receipts and affects the 2 forks.
3. Is the deployed-source "card authority" worth one extra pull request per ship, or may the ship stop writing to the source tree and the checks read the release record instead? (Item 4.)
4. Dev and stable from one source tree: which mods truly need dev-only code, and are you willing to pilot the single-tree model on the lighting mod? Chaos Wastes stable now has its own `_ct_official_*` modules; is that fork intended?
5. May all tooling require PowerShell 7 and drop Windows PowerShell 5.1?
6. For clean public versions, is a required `-ConfirmVersion` argument (plus your chat signal) an acceptable replacement for the label-and-comment grant?
7. `LICENSE` states that no publisher assets are redistributed. Are the tracked textures, FBX files and the HideBuffs fork all original or licensed? Only `character_weapon_variants` has a notices file.
8. Should failed and abandoned ships (stale claims, half-published releases) be cleaned up now as a one-time action, and who decides which queued versions are dropped?
