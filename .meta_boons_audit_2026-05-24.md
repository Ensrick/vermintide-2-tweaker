# ct meta-boons audit — 2026-05-24

User report: several +1%-per-boon meta-boons aren't taking effect in-mission. Audited every meta-boon against vanilla source (`C:\Users\danjo\source\repos\Vermintide-2-Source-Code`).

**TL;DR**: All stat_buff keys used by ct meta-boons ARE valid — every one is read by vanilla via `apply_buffs_to_value(...)` at a real call site. There are **0 silent-no-op stat_buff key bugs**. The wiring of `apply_buff_func` (BuffFunctionTemplates.functions) and `buff_func` (ProcFunctions) for on_boon_granted is correct. The user-perceived "no effect" is almost certainly **perceptibility**, not registration: per-stack increments are tiny (1-5%) and most affect rarely-observed quantities (cleave thresholds, healing inputs, crit rolls, stagger). Recommend test commands per boon to PROVE the stat_buff fires, so we can distinguish "broken" from "too small to notice".

The single canonical broken pattern called out in the existing source comments (`stat_buff = "movement_speed"`) IS in fact ALSO valid for **enemy** character states (warpfire thrower, gutter runner, etc. — see grep below), but is NOT read by the **player** movement-speed code path. ct_meta_movespeed correctly sidesteps this by using `apply_movement_buff`. So that one's already fixed; the existing comment in the lua file is accurate.

## BROKEN (silent no-op — needs fix)

**None.** No stat_buff key in any meta-boon is a ghost key. No `apply_buff_func` name in any meta-boon references a missing function. The registration plumbing (DeusPowerUpTemplates, BuffTemplates, BuffFunctionTemplates.functions, ProcFunctions, network lookup, dormant pool) is all in place and verified by the existing dormant_boons_preregistered / dormant_buff_dual_registered regression checks.

## SUSPECT (need runtime verify in-mission)

These are not broken — but the user may perceive them as broken because the effect is **too small to notice in normal play**, or because the math is correct but a downstream side-effect (HUD bar, ability fill time) doesn't visibly move. Each gets a `/verify_<name>` chat command stub + a `_rt_register` source-pattern check.

### 1. `ct_meta_health` — max_health (high suspicion)

**Why suspect**: `_calculate_max_health` (player_unit_health_extension.lua:176) IS recalculated per frame in `update()` (line 310) and pushed via `GameSession.set_game_object_field(..., "max_health", ...)`. The math is correct: at 10 boons, base 150 HP → ~165 HP. BUT current_health is NOT automatically scaled up — the player still has their old current HP, so the HUD shows `100/165` instead of `100/150` — a very small percent increase that is easy to miss on the green bar.

**Hypothesis**: stat_buff IS applied (HUD max_health DOES grow), user just can't see the small bump.

**Verify** — `/verify_ct_meta_health` command:
```lua
mod:command("verify_ct_meta_health", "Probe ct_meta_health stat_buff resolution + HP math", function()
    local pl = Managers.player and Managers.player:local_player()
    local unit = pl and pl.player_unit
    if not unit then mod:echo("no player unit"); return end
    local buff_ext = ScriptUnit.has_extension(unit, "buff_system")
    local health_ext = ScriptUnit.has_extension(unit, "health_system")
    local rc = Managers.mechanism and Managers.mechanism:game_mechanism()
        and Managers.mechanism:game_mechanism():get_deus_run_controller()
    local num_boons = (rc and pl) and #(rc:get_player_power_ups(pl:network_id(), pl:local_player_id()) or {}) or 0
    local stacks = buff_ext and buff_ext:num_buff_stacks("ct_meta_health_stack_1") or 0
    local unmod = health_ext and health_ext.unmodified_max_health or -1
    local resolved = buff_ext and buff_ext:apply_buffs_to_value(unmod, "max_health") or -1
    local healing_mult = buff_ext and buff_ext:apply_buffs_to_value(1, "healing_received") or -1
    mod:echo("[verify_ct_meta_health] boons=%d stacks=%d unmod_hp=%.1f resolved_hp=%.1f healing_mult=%.3f",
        num_boons, stacks, unmod, resolved, healing_mult)
    if stacks ~= num_boons then mod:echo("  WARN stacks!=boons -- proc/apply not in sync") end
    if math.abs(resolved - unmod * (1 + 0.01 * stacks)) > 0.5 then
        mod:echo("  FAIL stat_buff math: expected %.1f got %.1f", unmod * (1 + 0.01 * stacks), resolved)
    end
end)
```

### 2. `ct_meta_stagger` — power_level_impact / power_level_melee_cleave (high suspicion)

**Why suspect**: Both apply only at attack resolution time. `power_level_impact` modifies the stagger output of an attack via the staggered-target's mass thresholds — only observable when the player's hit fails-to-stagger one type of enemy and starts succeeding. `power_level_melee_cleave` modifies sweep cleave power thresholds — only observable when a sweep starts cutting through one more target.

**Hypothesis**: Working but player can't tell.

**Verify** — `/verify_ct_meta_stagger`:
```lua
local impact = buff_ext:apply_buffs_to_value(1, "power_level_impact")
local cleave = buff_ext:apply_buffs_to_value(1, "power_level_melee_cleave")
-- expected: 1 + 0.01 * stacks  for each
```

### 3. `ct_meta_crit` — critical_strike_chance / critical_strike_effectiveness (high suspicion)

**Why suspect**: Crit chance is a probabilistic check (action_utils.lua:756), and 1% per boon means at 10 boons +10% effective crit — visible only with statistical sampling. `critical_strike_effectiveness` is a multiplier on head_shot_boost damage applied only at the moment a crit lands. Both invisible to "did the buff apply?" eyeball.

**Verify** — `/verify_ct_meta_crit`:
```lua
local cc = buff_ext:apply_buffs_to_value(0, "critical_strike_chance")  -- bonus path, base 0
local ce = buff_ext:apply_buffs_to_value(1, "critical_strike_effectiveness")
-- expected: cc == 0.01 * stacks, ce == 1 + 0.05 * stacks
```

### 4. `ct_meta_cooldown` — cooldown_regen (moderate suspicion)

**Why suspect**: Career ability bar fills based on `cooldown_regen` multiplier (career_extension.lua:244). At 10 boons → +20% fill rate. Visible if the player times it, easy to miss otherwise. Career-only — bots don't run abilities visibly to host.

**Verify** — `/verify_ct_meta_cooldown`:
```lua
local cd = buff_ext:apply_buffs_to_value(1, "cooldown_regen")
-- expected: 1 + 0.02 * stacks
```

### 5. `ct_meta_movespeed` — apply_movement_buff (low suspicion, may be working)

**Why suspect**: Compounding `1.01^N` per stack mutates `PlayerUnitMovementSettings.get_movement_settings_table(unit).move_speed` directly. The base is 4.0, so 10 boons → 4 * 1.01^10 = 4.417 (≈+10.4%). Should be observable in a sprint test. The most-likely source of user-perceived "no effect" here is **the unit→table is cached at register_unit time** (player_movement_settings.lua:15-17) — if the player's unit changes mid-mission (revive, swap careers, hot-reload) the table may be stale.

**Verify** — `/verify_ct_meta_movespeed`:
```lua
local move_table = PlayerUnitMovementSettings.get_movement_settings_table(unit)
mod:echo("move_speed base=%.3f current=%.3f stacks=%d expected=%.3f",
    4.0, move_table.move_speed, stacks, 4.0 * (1.01 ^ stacks))
```

## Recommended fixes (prioritized by user impact)

Since no key is actually broken, "fixes" are diagnostic/UX changes rather than code rewrites:

### 1. (HIGHEST IMPACT) Ship `/verify_ct_meta_*` chat commands for every meta-boon
Mirrors the existing `/verify_meta_ammo`. Single command `/verify_all_meta_boons` that loops every CT_META_BOONS entry, reads `apply_buffs_to_value(...)` for each stat_buff, and emits PASS/FAIL with the expected vs actual value. Lets the user PROVE in-mission "the stat_buff applied" — distinguishes broken-registration from invisible-effect.

### 2. (MEDIUM IMPACT) Add `_rt_register` source-pattern checks for every meta-boon's `BuffTemplates` entry
Like the existing `ct_meta_ammo_uses_consumption_side` check at L7675 — for each meta boon, assert:
- `BuffTemplates[<name>_stack]` exists, has `buffs` array
- Each sub-buff has a known stat_buff (cross-check against `StatBuffApplicationMethods` from buff_templates.lua to catch typos)
- `DeusPowerUpTemplates[<name>]` exists with the expected event = "on_boon_granted"
- `ProcFunctions["<name>_granted"]` is a function (catches the v0.7.64 regression class)
- `BuffFunctionTemplates.functions["<name>_apply"]` and `"<name>_granted"` are both functions

These run on `/ct_regression_test` without needing to be in CW.

### 3. (LOW IMPACT — only if `/verify_ct_meta_health` shows a delta) Consider growing `current_health` proportionally when `ct_meta_health` apply fires
Strictly cosmetic — if the user is seeing "max grew but my green bar didn't follow", we can call `health_extension:add_heal(unit, ..., heal_type = "heal_from_proc", amount = delta)` inside the meta_health proc to keep the HUD percent steady. Only do this if step 1 confirms the stat_buff IS firing and the complaint really is "I can't see the difference".

## Suggested implementation shape for the fix-agent

```lua
-- Above the existing CT_META_BOONS table; reusable verifier factory
local function _make_verify_command(spec)
    local stack_key = spec.name .. "_stack_1"
    mod:command("verify_" .. spec.name,
        "Probe " .. spec.name .. " stat_buff resolution",
        function()
            local pl = Managers.player and Managers.player:local_player()
            local unit = pl and pl.player_unit
            if not unit then mod:echo("/verify_%s: no player unit", spec.name); return end
            local buff_ext = ScriptUnit.has_extension(unit, "buff_system")
            if not buff_ext then mod:echo("/verify_%s: no buff_extension", spec.name); return end
            local rc = Managers.mechanism and Managers.mechanism:game_mechanism()
                and Managers.mechanism:game_mechanism():get_deus_run_controller()
            local num_boons = (rc and pl) and #(rc:get_player_power_ups(pl:network_id(), pl:local_player_id()) or {}) or 0
            local stacks = buff_ext:num_buff_stacks(stack_key) or 0
            mod:echo("[verify_%s] boons=%d stacks=%d", spec.name, num_boons, stacks)
            if stacks ~= num_boons and num_boons > 0 then
                mod:echo("  WARN stacks=%d but boons=%d -- proc desync", stacks, num_boons)
            end
            for _, sb in ipairs(spec.stat_buffs) do
                local key = sb.stat_buff
                local base = sb.multiplier and 1.0 or 0.0  -- multiplier reads use base=1, bonus reads use base=0
                local resolved = buff_ext:apply_buffs_to_value(base, key)
                local per_stack = sb.multiplier or sb.bonus or 0
                local expected = base + per_stack * stacks
                local pass = math.abs(resolved - expected) < 1e-3
                mod:echo("  %s %s=%.4f expected=%.4f (per_stack=%+.4f stacks=%d)",
                    pass and "OK" or "FAIL", key, resolved, expected, per_stack, stacks)
            end
        end)
end
for _, spec in ipairs(CT_META_BOONS) do _make_verify_command(spec) end
```

Then a master `/verify_all_meta_boons` that calls each:

### Source-pattern checks (canonical shape, matches existing `ct_meta_ammo_uses_consumption_side`)

```lua
-- One per meta-boon. Place near the existing _rt_register block (~L7660).
local _META_BOON_EXPECTED_KEYS = {
    ct_meta_stagger   = { "power_level_impact", "power_level_melee_cleave" },
    ct_meta_crit      = { "critical_strike_chance", "critical_strike_effectiveness" },
    ct_meta_health    = { "max_health", "healing_received" },
    ct_meta_cooldown  = { "cooldown_regen" },
    ct_meta_ammo      = { "total_ammo", "reduced_overcharge", "ammo_used_multiplier" },
}
for name, keys in pairs(_META_BOON_EXPECTED_KEYS) do
    _rt_register("meta_boon_registered_" .. name, function()
        local stack = (rawget(_G, "BuffTemplates") or {})[name .. "_stack"]
        if not stack or type(stack.buffs) ~= "table" then
            return name .. "_stack missing or malformed BuffTemplates entry"
        end
        local seen = {}
        for _, sb in ipairs(stack.buffs) do seen[sb.stat_buff] = true end
        for _, k in ipairs(keys) do
            if not seen[k] then return name .. " missing stat_buff key: " .. k end
            -- Cross-check it's a real vanilla key:
            if not StatBuffApplicationMethods[k] then
                return name .. " uses ghost stat_buff key: " .. k .. " (not in StatBuffApplicationMethods)"
            end
        end
        local pu = (rawget(_G, "DeusPowerUpTemplates") or {})[name]
        if not pu or not pu.buff_template or not pu.buff_template.buffs then
            return name .. " DeusPowerUpTemplates entry missing"
        end
        local sub = pu.buff_template.buffs[1]
        if sub.event ~= "on_boon_granted" then return name .. " event != on_boon_granted" end
        local bft = rawget(_G, "BuffFunctionTemplates")
        local apply_fn = bft and bft.functions and bft.functions[sub.apply_buff_func]
        if type(apply_fn) ~= "function" then return name .. " apply_buff_func missing: " .. tostring(sub.apply_buff_func) end
        local pf = rawget(_G, "ProcFunctions")
        local granted_fn = pf and pf[sub.buff_func]
        if type(granted_fn) ~= "function" then return name .. " buff_func not in ProcFunctions: " .. tostring(sub.buff_func) end
    end)
end

-- Movespeed is special-cased
_rt_register("meta_boon_registered_ct_meta_movespeed", function()
    local stack = (rawget(_G, "BuffTemplates") or {}).ct_meta_movespeed_stack
    if not stack or type(stack.buffs) ~= "table" then return "ct_meta_movespeed_stack missing" end
    local sb = stack.buffs[1]
    if sb.apply_buff_func ~= "apply_movement_buff" then return "movespeed apply != apply_movement_buff" end
    if sb.remove_buff_func ~= "remove_movement_buff" then return "movespeed remove != remove_movement_buff" end
    local path = sb.path_to_movement_setting_to_modify
    if not path or path[1] ~= "move_speed" then return "movespeed path_to_movement_setting_to_modify != { 'move_speed' }" end
end)
```

### Runtime verification (mid-CW-mission)

Use the `_make_verify_command` factory shape above. Each meta-boon produces one `/verify_ct_meta_<name>` command. Run them from the chat box after picking 3-5 boons of varying types and reading the `OK`/`FAIL` per stat_buff.

## Caveats / known limits

- The audit covers stat_buff key validity and registration plumbing. It does NOT prove per-peer index alignment for the meta-boon's `BuffTemplates`/`NetworkLookup.buff_templates` entries — that's already covered by the existing `dormant_boons_preregistered` / `dormant_buff_dual_registered` regression checks (since meta-boons go through the same `inject_dormant_boon` path).
- `ct_meta_movespeed`'s compounding (1.01^N) is intentional per the comment at L5884 — users could perceive it as +1%/boon when it's actually slightly more, but that's a feature not a bug.
- `ct_meta_health` will NOT visually grow the player's current HP, only the max. This is consistent with every vanilla `max_health` boon (e.g. deus_special_farm_max_health_buff at deus_power_up_settings.lua:231). Don't "fix" it unless the verify command shows the math is wrong.
- The `apply_buff_func = "ai_update_max_health"` pattern seen across vanilla buffs (grudge_marks, belakor, geheimnisnacht_2021) is for AI extensions; `PlayerUnitHealthExtension.set_max_health` is a no-op stub (player_unit_health_extension.lua:1271-1273). Player max_health is recomputed per-frame in `update()` instead. Do not copy this apply_buff_func into ct_meta_health.
