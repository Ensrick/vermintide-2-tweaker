# ct network-bound mutation audit — 2026-05-24

After the v0.7.99-dev/v0.7.100-dev/v0.7.101-dev max_energy crash fix sequence (Necromancer-bot crash GUID `10764a92`), audited `chaos_wastes_tweaker` and every sibling tweaker mod for ALL direct mutations of engine-bounded resource fields and `stat_buff = "max_*"` patterns. The two known burns in this bug class are:

- **v0.7.80-alpha** (2026-05-22, dated in user prompt) — `stat_buff = "max_overcharge"` at +5%/boon stacked past `NetworkConstants.max_overcharge.max` (= 60). Sienna staff base 40 × (1 + 12*0.05) = 64 → fassert at `player_unit_overcharge_extension.lua:110` on both server + husk. Fix: switched to `stat_buff = "reduced_overcharge"` (per-cast, never network-synced).
- **v0.7.99-dev → v0.7.101-dev** (2026-05-23, today's chest crash) — direct `energy_ext._max_energy = N` write at +5%/boon stacked past `NetworkConstants.max_energy.max` (= 60). The PlayerUnitEnergyExtension is bolted onto every career's player unit (not just Kerillian / Moonfire), so on a Necromancer the default `max_value or 40` fell back to 40, and 40 × 1.6 = 64 tripped the fassert at `player_unit_energy_extension.lua:43` mid-game (`_update_game_object` is called every frame inside `update`). Fix: three-layer gate (weapon whitelist `we_deus_01` + base sanity `< 40` + engine ceiling clamp to `NetworkConstants.max_energy.max`).

Both crashes share the same root pattern: **a +5%/boon scaling factor that compounds to >50% with 12 active boons (a normal late-CW count), driven against a `NetworkConstants` cap of ~60 that vanilla designed around a single Sienna +50% talent.**

## RISKY-CRITICAL (must fix)

**None.** Both historical RISKY-CRITICAL findings are fixed and verified:

1. **v0.7.80-alpha `stat_buff = "max_overcharge"` crash** — fixed in v0.7.78-dev. Source has the post-mortem comment block at `chaos_wastes_tweaker.lua:5476-5497` (note the comment header still says "v0.7.78 (was v0.7.72 max_overcharge crash fix)" — the v0.7.80-alpha date in the user prompt refers to when the post-mortem was filed in CHANGELOG, not when the fix shipped). Mitigation: switched the meta-ammo boon to `reduced_overcharge` which is per-cast and never network-synced. The vanilla refresh path `_calculate_and_set_buffed_max_overcharge_values` is also no longer called by ct (it was removed in v0.7.78 — comment at line 5639).
2. **v0.7.99-dev / today's max_energy chest crash (GUID 10764a92)** — fixed in v0.7.101-dev (current). Mitigation: three-layer defence at `chaos_wastes_tweaker.lua:5650-5732`:
   - Layer 1 (`item_name ~= "we_deus_01"`): the player must actually be holding Moonfire Bow this frame — gates out every career that has the extension but no Moonfire (Necromancer, all of Bardin's, all of Saltzpyre's, etc.).
   - Layer 2 (`base >= 40`): if the stashed base is the 40-default-fallback, it's not Moonfire (Moonfire's base is 25 per `EnergyData.we_<career>.max_value`) — skip.
   - Layer 3 (`clamp_ceiling = NetworkConstants.max_energy.max or 60`): even on Moonfire with 25 base, 25 × 1.6 = 40 stays under 60. Clamp is belt-and-suspenders against future stat changes.

## RISKY-LATENT (harden when next touched)

**None identified.** The audit found no other direct mutations of engine-bounded fields, and no `stat_buff = "max_overcharge"` / `"max_energy"` / `"max_charge"` writes anywhere in the monorepo.

Two near-misses worth a watch (not findings, just monitoring):

- **`buff_funcs.functions.ct_meta_ammo_refresh_capacity` (the apply func)** — currently the only place that touches `_max_energy`. If a future feature adds another extension-write path (e.g. a separate altar that scales ranged weapon caps directly), it MUST reuse the same three-layer gate. The sentinel constants `CT_META_AMMO_WEAPON_GATE_MARKER` and `CT_META_AMMO_ENERGY_CLAMP_MARKER` are anchors for `/ct_regression_test` to pattern-match against.
- **CWV ammo bases pushed UP** (`_OUTRIDER_MAX_AMMO`, `_MUSKET_MAX_AMMO`, `_OLD_MUSKET_MAX_AMMO`, `_TJ_MAX_AMMO`) — if any of these constants are raised AND a future ct boon ever decides to scale `_max_ammo` directly (bypassing `total_ammo`), the same bug class would reappear. Today's writes go via `total_ammo` which is correct and recompute-only — keep it that way.

## Recommendation

**No further fixes required from this audit.** The v0.7.101-dev defensive trio (weapon gate + base sanity + NetworkConstants clamp) closes the max_energy hole the same way v0.7.78's `reduced_overcharge` swap closed the max_overcharge hole, and no other site in the monorepo has the same shape (direct extension-field write OR `stat_buff = "max_overcharge|max_energy|max_charge"`). The single remaining `_max_energy` write at `chaos_wastes_tweaker.lua:5726` is now strictly safer than any vanilla buff path because it tops out at `NetworkConstants.max_energy.max` regardless of base, gate, or boon count. Suggest adding a regression check `meta_ammo_energy_clamp_present` that asserts the two marker strings are present in the compiled bundle (mirroring the existing `dormant_setting_keys_not_consumed` sentinel check) — that catches a future refactor accidentally stripping the gate.
